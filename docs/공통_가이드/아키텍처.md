# 세이버스(SAVERS) 프로젝트 구조도

`CLAUDE.md`, `개발자_가이드.md`, `리스크.md`, `구현_범위.md`에서 정리한 내용을 바탕으로 시스템 구조를 mermaid로 도식화한 문서입니다. 아직 코드가 없는 기획 단계 기준의 설계도이며, 구현이 시작되면 실제 구조에 맞춰 갱신해야 합니다.

## 1. 전체 파이프라인 (6단계)

경보 발생부터 개인 맞춤 알림 도달까지의 흐름입니다. 기획서의 "6단계 작동 파이프라인"을 그대로 반영했습니다.

```mermaid
flowchart LR
    A["① 사전 등록<br/>전화번호·프로필·거주 행정동<br/>(보호자/복지관/지자체 대리등록)"] --> B["② 재난 감지·상시 모니터링<br/>기상청·소방청·행안부 Open API 폴링"]
    B --> C["③ 대상자 매칭<br/>경보 행정동 ↔ 등록자 행정동"]
    C --> D["④ 위치 1회 확인<br/>알림 링크 클릭 시 Geolocation<br/>(세션 단위, 미저장)"]
    D --> E["⑤ RAG 메시지 생성<br/>Chroma 검색 → 가드레일 → HyperCLOVA X"]
    E --> F["⑥ 알림 발송<br/>카카오 알림톡 · PWA 웹푸시"]
    F --> G["Interactive Care 챗봇<br/>후속 Q&A 대기"]

    style D fill:#f9d,stroke:#333
    style E fill:#bbf,stroke:#333
```

> 목표: ①~⑥ 전 구간 종단 지연 30초 이내 (근거: [리스크.md](리스크.md) ③ 참고 — 낙관적 추정이므로 실측 필요).

## 3. 위치 확인 → 알림 도달 임계 경로 (시퀀스)

지연시간 목표(30초)와 직결되는 구간만 떼어낸 시퀀스 다이어그램입니다.

```mermaid
sequenceDiagram
    participant U as 사용자(알림 링크 클릭)
    participant FE as PWA/알림톡 클라이언트
    participant LOC as 위치 매칭 엔진
    participant RAG as RAG 파이프라인(Chroma)
    participant LLM as 가드레일 + HyperCLOVA X
    participant NOTI as 알림 발송(알림톡/웹푸시)

    U->>FE: 알림 링크 진입
    FE->>LOC: Geolocation 좌표 1회 전송
    LOC->>LOC: 카카오맵 역지오코딩 → 위험구역/대피소 거리 계산
    LOC->>RAG: 재난유형 + 취약계층 프로필 전달
    RAG->>RAG: 시맨틱 검색 (국민행동요령 원문 발췌)
    RAG->>LLM: 검색된 근거 원문 전달
    LLM->>LLM: 가드레일 검증 (원문 밖 내용 차단)
    LLM->>NOTI: 개인 맞춤 메시지 생성 완료
    NOTI->>U: 알림톡/웹푸시 발송
    Note over U,NOTI: 목표 총 소요 30초 이내<br/>(알림톡 3~5s + LLM 생성 5~10s + 매칭 여유분)
```

## 4. 저장소(Repo) 구조 제안

역대 수상팀 GitHub 구조 조사(원본 PDF는 public 레포 밖 보관)의 본질적 결론(AI를 인라인 호출이 아닌 **독립 배포 가능한 엔진**으로 두고 배포·운영 문서를 함께 정리)을 반영하되,
6인·해커톤 단기·Tech Lead 초반 집중 조건을 고려해 **단일 모노레포**로 운영합니다. AI(`apps/ai-engine`)는 모노레포 안에서 자체 Dockerfile·README로 독립 배포 가능한 엔진으로 유지합니다. (근거: [개발자_가이드.md](개발자_가이드.md) 7절, [ADR-0001](../adr/0001-monorepo.md))

```mermaid
flowchart TB
    REPO[("모노레포<br/>savers-project")]
    REPO --> APPS["apps/"]
    REPO --> PKG["packages/contracts<br/>OpenAPI 스펙 · 공용 스키마(SSOT)"]
    REPO --> INFRA2["infra/<br/>docker-compose · .env.example · AWS 프로비저닝"]
    REPO --> DOCS["docs/<br/>ADR · 설계·운영 가이드"]
    REPO --> E2E["e2e/<br/>앱 가로지르는 관통 테스트(QA 소유)<br/>HTTP 전용 · non-required CI"]
    REPO --> TOOL["notebooks/ · scripts/<br/>실험 기록 · 품질 게이트/레포 도구"]

    APPS --> FE["frontend<br/>PWA · 알림톡 UI · 챗봇 UX · 접근성"]
    APPS --> BE["backend<br/>FastAPI · 위치매칭 엔진 · 재난 API 연동"]
    APPS --> AI["ai-engine<br/>RAG · LangChain · 가드레일<br/>eval/ = 평가 하네스<br/>(자체 Dockerfile·README = 독립 배포)"]

    AI -.HTTP 계약으로만 연결<br/>파이썬 import 금지.-> BE
```

> 앱 간 결합은 `packages/contracts`의 HTTP 계약으로만 허용합니다. `apps/backend`와 `apps/ai-engine`이 서로를 파이썬 import 하는 순간 "독립 배포 가능한 AI 모듈"이라는 구조의 근거가 사라집니다.
> `e2e/`에도 같은 제약이 적용됩니다 — 관통 테스트는 기동된 서비스에 HTTP로만 접근하며, 앱 패키지를 import하지 않습니다.
