# 실패 모드 시연 대본 (5종 + 보너스 1종)

**최종 수정일**: 2026-08-29 · **버전**: v0.5 · **작성**: PM(안은남) ·
**상태**: 검토 중 — 케이스 4는 도혁 님 확인으로 슬라이드 대체 확정,
케이스 1은 대체 시연 방식에 대한 Tech Lead 승인만 남음,
케이스 2·5·6은 실증 완료.

**v0.5 변경**: [PR #206](https://github.com/team-savers/savers-project/pull/206) 머지로
케이스 5가 curl-only가 아니라 **`/g/{token}` 실제 화면에서 라이브 시연 가능**해졌습니다
(소원 님 확인 + 브라우저 재실증 완료). 화면에 「확인할 수 없습니다」가 리터럴로 렌더되는 것도
확인 — 이전 버전의 "paraphrase일 뿐 화면에 없다"는 서술을 정정했습니다.

**v0.4 변경**: 케이스 5의 API 트리거(ai-engine 다운 → no_evidence 거절, 자유질문 → 422)를
origin/main 기준으로 실증하고, curl-only(A) vs UI 연동(B) 결정을 소원 님에게 요청하는
항목을 명시했습니다.

**v0.3 변경**: 케이스 2를 origin/main 기준 별도 환경에서 backend·frontend 실통합으로
직접 실증했습니다 — "브라우저-백엔드 통합 미검증" 우려가 해소돼 ✅ 실증 완료로 표시.

**v0.2 변경**: 케이스 4(경로 없음)와 관련해 도혁 님이 남긴 PR #118 코멘트를 검증했습니다.
코멘트 자체는 전부 실재하고 정확했지만, **PR #118은 경로 엔진이 아니라 별개의 안전 필터
케이스를 구현한 것**이었습니다 — 자세한 구분은 케이스 4·6 절 참조. 케이스 4는 여전히
미해결이고, 검증 과정에서 확인된 새 실재현 케이스를 케이스 6으로 추가했습니다.

## 케이스 1 — 특보 API 중단 → Redis 캐시

**재현 상태**: 대체 시연. 아키텍처.md가 말하는 "특보 API"·"Redis 캐시"는 코드에 없습니다.
`apps/backend/src/backend_core/ingest.py`는 `StaticDisasterSource`/`demo_flood_warning()` 스텁뿐이고,
저장소 전체를 검색해도 Redis 클라이언트는 `apps/` 어디에도 없습니다.

실제로 존재하고 동작하는 것은 **한 단계 아래, 대피소 데이터의 캐시 폴백**입니다.
`ShelterRepository._load()`([apps/backend/src/backend_core/shelters.py:178](../../apps/backend/src/backend_core/shelters.py))가
`UnavailableShelterSource.fetch()`(항상 `ShelterSourceUnavailableError`를 던지도록 고정)를
먼저 시도하고, 실패하면 커밋된 `fixtures/shelters.jsonl` 캐시로 폴백합니다.
이 폴백은 dev 환경에서 **기본값**입니다(`api/deps.py`의 `shelters()`:
"Live source is not wired yet, so every search falls back to the shipped cache").

**트리거**:
```bash
curl -X POST localhost:8000/v1/shelters/search \
  -H "Content-Type: application/json" \
  -d '{"sessionToken": "<발급받은 세션 토큰>", "dongCode": "1162064500"}'
```
별도 조작 없이 이미 이 상태이므로, "무엇이 대체됐는지 숨기지 않는다"는 원칙을 보여주는
용도로 씁니다.

**화면/응답**: `availability: "cache_only"`, `dataAsOf`는 `FIXTURE_AS_OF`
(`shelters.py:55`, 2026-07-27 고정) — 실시간 데이터가 아님을 필드로 명시.
캐시조차 없는 행정동(`dongCode: "9999999999"`, e2e 테스트의 `DONG_WITHOUT_DATA`)으로
바꾸면 `availability: "upstream_unavailable"`, `items: []`로 완전 장애 상태를 보여줄 수 있습니다.

**근거 테스트**: `test_cache_fallback_is_labelled_not_disguised`,
`test_upstream_down_and_nothing_cached_says_so`
(`apps/backend/tests/backend_core/test_shelters.py`).

**발표 멘트 포인트**: "특보 API·Redis 캐시 자체는 본선 범위 밖이지만, 같은 설계 원칙
(실패를 숨기지 않고 필드로 말한다)을 대피소 데이터 계층에서 이미 구현했습니다"라고
**정확히** 그렇게 말합니다. "Redis를 시연합니다"라고 말하면 안 됩니다.

**확인 필요**: 이 대체 프레이밍으로 발표해도 되는지 Tech Lead 승인 필요.

## 케이스 2 — 위치 실패 → 「등록하신 동 기준」

**재현 상태**: ✅ **실증 완료(2026-08-29)**. `origin/main` 기준 별도 worktree에서
backend(:8000, 실 HTTP)·frontend(:3000, `VITE_USE_MOCK=false`)를 둘 다 띄우고
`/internal/alerts/dispatch`로 얻은 실제 세션 토큰으로 `/a?t=...`를 열어
**엔드투엔드로 확인했습니다.** 브라우저 네트워크 로그에서 실제
`POST http://localhost:8000/v1/shelters/search` 호출(200 OK, CORS 정상)의
응답 바디에 `"basis":"dongCode"`가 찍혔고, 화면에 "등록하신 자택(서원동) 기준
가까운 대피소" 헤더와 실제 대피소 4곳(거리·계단 주의 포함)이 정상 렌더됐습니다.
자동화 브라우저의 geolocation 권한이 기본 `denied`라, 이 확인 과정 자체가
"위치 거부 → 행정동 기준 폴백"을 그대로 실행한 것입니다.
(과거 기록: 이전에는 "브라우저-백엔드 통합 경로가 검증된 적이 없다"는 우려가 있었으나
위 실증으로 해소됐습니다. 기본값 `VITE_USE_MOCK=true`에서는 `mock.ts`가 `basis` 필드를
다루지 않아 mock 모드로는 재현되지 않는다는 점은 여전히 유효 — 시연 시 반드시
`VITE_USE_MOCK=false`로 띄워야 합니다.)

**코드 경로**: 위치 처리는 `ShelterGuide.tsx`가 "브라우저 권한 상태"와
"등록 시점 동의 플래그" 두 신호를 조합해 셋 중 하나로 판정합니다(1~15행 주석) —
`refused`(동의 false 또는 권한 `denied` → 위치 미사용, 바로 `dongCode` 검색),
`auto`(동의 true + 권한 `granted` → 마운트 시 1회 자동 조회), `card`(그 외 전부 →
`LocationConsent` 카드를 보여주고 사용자가 눌러야 조회). `LocationConsent.tsx`가
유일한 `getCurrentPosition()` 호출부이며, 권한 거부·시간초과·미지원 환경 모두
좌표 콜백 없이 `onFailed(...)`로 빠집니다. 어느 경로로 오든 좌표가 없으면 서버는
`basis: "coordinate" if lat/lng present else "dongCode"`(`shelters.py:176`)를
응답에 싣고, 프론트는 `basis === 'dongCode'`일 때
`HEADER_KO = '등록하신 자택({dong}) 기준 가까운 대피소'`(`ShelterGuide.tsx:638`)를 렌더합니다.
⚠️ 원래 이 문서가 가정했던 "밖이에요 버튼 → 위치 권한 프롬프트"라는 별도 선택 화면은
실제 구현에는 없습니다 — `ShelterGuide`가 항상 이 판정을 거쳐 렌더되는 구조입니다.

**트리거(시연 순서, 실증 완료)**:
1. `apps/frontend/.env`에서 `VITE_USE_MOCK=false`, `VITE_API_BASE_URL=http://localhost:8000`.
2. backend를 `SAVERS_CORS_ALLOW_ORIGINS=http://localhost:3000`로 기동(:8000).
3. `curl -X POST localhost:8000/internal/alerts/dispatch`로 세션 토큰 확보,
   `http://localhost:3000/a?t=<토큰>`으로 PWA 진입.
4. 위치 권한을 거부한 상태(브라우저 설정 또는 사이트 권한에서 "차단")라면
   자동으로 `dongCode` 기준 목록이 뜹니다 — 별도 버튼 클릭 불필요.
   권한이 `prompt` 상태면 `LocationConsent` 카드가 뜨고, 그 카드의 거부 동작으로도 같은 결과.
5. 화면 헤더가 "등록하신 자택(○○동) 기준 가까운 대피소"로 뜨는지 확인.

**근거 테스트**: `test_basis_reports_which_origin_was_used`
(`apps/backend/tests/backend_core/test_shelters.py`) — 이제 수동 실증과 자동 테스트 둘 다 있습니다.

## 케이스 3 — 가드레일 이탈 → 최소안전문

**재현 상태**: 실재현 가능. AGENTS.md가 이미 예시 명령을 문서화해 뒀습니다.

**코드 경로**: `OFFICIAL_FALLBACK_BODY`
(`apps/backend/src/backend_core/fallback.py:20`):
> "지금 계신 곳이 침수 위험 지역입니다. 물이 차오르기 전에 지상에 있는 안전한 곳으로
> 이동하세요. 움직이기 어려우면 119에 연락하세요."

`pipeline.py`의 `_generate()`에서 두 경로가 여기로 모입니다 — 엔진 거절(`message: null`)과
`AiEngineUnavailableError`. 두 경우를 같은 문안으로 처리하는 것은 의도된 설계입니다
(fallback.py 모듈 docstring: "재난 상황에서는 '근거가 없었다'와 '물어볼 수 없었다'의
차이가 운영 관심사이지 중간에 설명할 일이 아니다").

**트리거**: ai-engine(:8100)을 기동하지 않은 상태에서
```bash
curl -X POST localhost:8000/internal/alerts/dispatch
```
seed 행정동에 데모 호우경보가 뿌려지고, 모든 수신자의 메시지가 `official_fallback`로 떨어집니다.

**화면/응답**: 세션 조회(`GET /v1/session/{token}`) 응답의
`message.messageMode == "official_fallback"`, `message.body`에 위 고정 문안,
`message.sources == []`(근거 인용 없음 — ADR-0006).

**근거 테스트**: `test_engine_refusal_becomes_the_approved_fallback`,
`test_ai_outage_lands_in_the_same_place_as_a_refusal`
(`apps/backend/tests/backend_core/test_pipeline.py`);
`test_no_shelter_data_still_leaves_guardian_path`
(`e2e/tests/test_failure_modes.py`, `FALLBACK_119_MARKER` 단언).

**⚠️ 발표 시 주의**: `fallback.py` 모듈 docstring이 "본 문안은 아직 QA/보안 검토 대기 중인
사전 승인 문안(ADR-0006)이며, 지금 문구를 승인된 카피가 아니라 자리표시자로 다루라"고
명시합니다. 발표에서 "이것이 최종 승인 문안입니다"라고 말하면 안 되고,
"안전 문구는 검토 절차를 거칩니다"로 표현합니다. `#77`(문안 검토, PM 인수 항목) 진행 상황을
발표 전에 재확인하세요.

## 케이스 4 — 경로 없음 → 대피소 재선정

**재현 상태**: ⚠️ **미구현 — 코드가 아예 없습니다.** `origin/main` 전체를 검색해도
`osmnx`/`networkx` 관련 코드가 `apps/` 어디에도 없고, `shelters.py`는 직선거리
`haversine_m()`(112행)만 계산합니다. 링크 등급(R0~R3) 필터링, 그래프 구축,
"경로 없음" 응답 형태 모두 코드·계약(`packages/contracts/openapi.yaml`) 어디에도 없습니다.
[ADR-0017](../adr/0017-route-engine-osmnx-networkx.md)은 **제안 상태**일 뿐 구현 여부와
무관합니다.

이는 [역할_일정/04-백엔드.md](../역할_일정/04-백엔드.md)의 계획
("경로 A안 완료 8/26, 「경로 없음」 폴백 8/27")과 어긋납니다 — 계획된 작업이
`origin/main`에 병합되지 않았습니다.

**8/29 재확인**: 도혁 님이 [PR #118](https://github.com/team-savers/savers-project/pull/118)을
이 케이스의 구현 완료로 언급했으나, 확인 결과 **PR #118은 경로 엔진과 무관한 별개의
안전 필터 케이스**였습니다(→ 케이스 6). 같은 확인 과정에서 원격 브랜치 60여 개의
이름을 전부 훑었지만 route/osmnx 관련 브랜치는 하나도 없었습니다 — 미병합 구현도
없다고 봐야 합니다.

**이 케이스는 지금 상태로 시연할 수 없습니다.** 오늘이 코드 프리즈 + 시연 환경 배포일이라
아래 옵션 중 2번(급히 최소 버전 구현)은 사실상 닫혔다고 봐야 합니다:
1. ~~Backend에게 미병합 로컬 브랜치에 구현이 있는지 확인~~ — 8/29 확인 완료, 없음.

## 케이스 5 — 근거 없는 질문 → 「확인할 수 없습니다」

**재현 상태**: ✅ **실증 완료(8/29) — UI 라이브 시연 가능, 문구까지 리터럴로 일치.**
[PR #206](https://github.com/team-savers/savers-project/pull/206)(오늘 머지, "보호자 Q&A
실제 API 연동 및 폴백 처리")이 `/g/{token}` 경로의 `AiScreen`을 실제
`POST /v1/guardian/{token}/ask`에 연동했습니다. 소원 님이 Discord로 알려주신 내용을
origin/main 기준 별도 환경(backend+ai-engine+frontend 전부 실기동, `VITE_USE_MOCK=false`)에서
브라우저로 직접 클릭해 재확인했습니다.

**코드 경로**: `Guardian.tsx`의 `AiScreen`은 `token === undefined`(파라미터 없는
`/guardian` 미리보기 경로)일 때만 `mocks/guardianStatus.ts` 고정값을 씁니다.
실제 `/g/{token}` 경로에서는 `token`이 항상 있으므로 `api.postGuardianAsk(token, ...)`를
그대로 호출하고, 타임아웃·422·오류·정상 응답을 각각 분기 처리합니다
(`Guardian.tsx:964~1000` 부근 `askRecommended()`). 문서 이전 버전이 인용한
"Screen 3 — 안전 확인 AI (mock Q&A)" 주석은 파일 맨 위(1~24행)에 남아 있는
**갱신 안 된 설명**입니다 — 실제 동작은 이미 그 설명을 앞질렀습니다.

**8/29 라이브 실증(브라우저)**:
1. `/internal/alerts/dispatch`로 얻은 `guardianToken`으로 `http://localhost:3000/g/<토큰>` 접속.
2. "상황 확인하기" → "안전 확인 AI" 순서로 진입.
3. ai-engine이 살아 있는 상태에서 질문 클릭 →
   실제 `POST .../ask` 200 확인, 화면에 "현재 세션의 사용자 행동은 기록에서
   확인되지 않습니다"(정상 grounded 답변, 로그에 해당 이벤트가 없다는 사실 자체를 보고) 렌더됨.
4. **ai-engine을 내린 뒤** 다른 질문 클릭 → 응답이
   `{"questionId":"help_request","answer":null,"sources":[],"refusalReason":"no_evidence"}`,
   화면에 **"확인할 수 없습니다"가 그대로 렌더됨**(`Guardian.tsx:1141`).

**⚠️ 문서 이전 버전 정정**: "「확인할 수 없습니다」는 화면에 없는 paraphrase"라고 적었던 건
**PR #206 이전 상태 기준으로는 맞았지만 지금은 틀립니다** — `Guardian.tsx:1141`에 이
문자열이 리터럴로 존재하고 실제로 렌더됩니다. 국민행동요령 챗봇 쪽(`chat.refusal.no_evidence`
= "확인된 지침이 없습니다", `i18n.ts:524`)과는 여전히 다른 문구이니, 어느 화면 얘기인지
구분해서 말합니다(보호자 Q&A는 "확인할 수 없습니다", 재난 챗봇은 "확인된 지침이 없습니다").

**코드 경로 (계약)**: `POST /v1/guardian/{token}/ask`는 고정 3문항
(`GuardianQuestionId`: `evacuation_progress`/`help_request`/`arrival_status`)만 받습니다.
자유 "기타" 질문은 계약에 없습니다 — `packages/contracts/openapi.yaml`이
"기타 자유질문은 본선 이후 계약 확장 대상"이라고 명시. 40건 골든셋의 기타 10건
(`g-031`~`g-040`)도 `--runtime` 채점에서 스킵됩니다. `AiScreen`에도 자유 입력 폼은
없습니다(추천 질문 버튼 3개뿐) — UI가 실연동됐다고 자유질문까지 열린 건 아닙니다.

거절 응답(`GuardianAnswer.no_evidence()`, `models.py:368` — `answer: null`,
`sources: []`, `refusalReason: "no_evidence"`)은 두 경로에서 나옵니다:
① ai-engine이 죽어 있을 때(`guardian.py:110`의 `AiEngineUnavailableError` 캐치) — **위 실증이 이 경로**,
② 로그 대조 검증기(`verify_guardian_answer_detailed`, `guardian_log_qa.py:547`)가
생성된 답변의 근거 없는 주장을 잡아낼 때 — LLM 호출이 실제로 환각을 내야 재현되므로
결정론적으로 시연하기 어렵습니다. **라이브 시연은 계속 ①로 갑니다.**

**시연 순서(라이브, curl 불필요)**:
```
1. /internal/alerts/dispatch 로 guardianToken 확보
2. 브라우저로 /g/<guardianToken> 접속 → 상황 확인하기 → 안전 확인 AI
3. (사전에 ai-engine을 내려 둔 상태에서) 추천 질문 아무거나 클릭
4. 화면에 "확인할 수 없습니다" 렌더 확인
```
curl 트리거(API 단독 확인용)는 아래에 그대로 남겨 둡니다 — 리허설 사전 점검이나
발표 백업 경로로 유용합니다.

```bash
# ai-engine(:8100)을 기동하지 않은 상태에서
curl -X POST localhost:8000/v1/guardian/<guardianToken>/ask \
  -H "Content-Type: application/json" \
  -d '{"questionId": "arrival_status"}'
```

**근거 테스트**: `test_guardian_ask_ai_failure_is_valid_whole_refusal`
(`apps/backend/tests/api/test_guardian_ask.py`).

**확인 필요**: ①(엔진 다운)과 ②(로그 대조 실패)가 계약상 동일한 응답 형태로 수렴한다는
설명이 fallback.py의 케이스 3 설계 철학과 같은 논리인지 — 발표 Q&A에서 나올 수 있는
질문이므로 Tech Lead(신호정) 확인 권장.

~~**확인 필요 — 시연 방식 결정, 소원 님**: curl-only(A) vs UI 연동(B)~~ →
**소원 님이 8/29 (B)로 이미 반영 완료를 확인해주셨고, 위 실증으로 재검증 끝났습니다.**

## 케이스 6(보너스) — 대피소 후보 전부 제외 → `all_excluded`

**재현 상태**: 실재현 가능, 단위 테스트로 고정됨. 아키텍처.md 5절 원표의 5케이스에는
없던 항목입니다 — 도혁 님이 케이스 4 대체로 제시한 [PR #118](https://github.com/team-savers/savers-project/pull/118)
검증 과정에서 발견한 **별개의, 진짜로 구현된** 실패 모드입니다.

**케이스 4와 다른 점**: 이건 "길이 막혀서 다른 대피소로 재선정"이 아니라, "**대피소
후보 전부가 이미 존재하던 서버사이드 안전 필터(호우·침수 시 지하 시설 제외 —
AGENTS.md 비타협 제약)에 걸려서 하나도 안내할 수 없음**"입니다. 라우팅(OSMnx/networkx)과는
무관하고, 재선정 로직도 아닙니다(제외된 뒤 대체 후보를 고르는 게 아니라 후보가 아예
동나는 상황). 발표에서 "이것이 경로 재선정입니다"라고 말하면 안 됩니다.

**코드 경로**: `_apply_safety_filter()`(`shelters.py:324`)가 `disaster_type == "flood"`이고
`is_underground`인 레코드를 제외하고, 남는 후보가 0건이면 `availability = "all_excluded"`
(`shelters.py:268`)로 표시합니다. 데모용 신림동(`UNDERGROUND_ONLY_DONG_CODE = "1162066500"`,
`registry.py:187`)은 픽스처상 대피소 2곳이 전부 지하라 이 경로가 100% 결정론적으로
재현됩니다.

**⚠️ 트리거 시 주의**: 기본 데모 특보(`demo_flood_warning()`)는 서원동만 덮으므로,
신림동 세션을 만들려면 `/internal/alerts/dispatch`에 `affectedDongCodes`를 명시한
이벤트 본문을 실어야 합니다 — 도혁 님 인계 노트 그대로입니다.

**트리거**:
```bash
curl -X POST localhost:8000/internal/alerts/dispatch \
  -H "Content-Type: application/json" \
  -d '{
    "eventId": "DEMO-ALLEXCLUDED-01",
    "type": "flood",
    "level": "warning",
    "issuedAt": "2026-08-29T09:00:00Z",
    "affectedDongCodes": ["1162066500"],
    "headline": "서울 관악구 호우경보"
  }'
# 응답의 deliveries[]에서 신림동 거주자(p003)의 sessionToken을 집습니다.

curl -X POST localhost:8000/v1/shelters/search \
  -H "Content-Type: application/json" \
  -d '{"sessionToken": "<위에서 얻은 p003 세션 토큰>", "dongCode": "1162066500"}'
```

**화면/응답**: `availability: "all_excluded"`, `items: []`,
`excluded: [{"reason": "underground", "count": 2}]` — "대피소가 없다"가 아니라
"후보는 있었으나 안전 필터로 전부 제외됐다"를 필드로 정직하게 구분합니다
(케이스 1의 `upstream_unavailable`과 다른 값인 것이 핵심 — 조회 실패와 안내 불가를
같은 빈 목록으로 뭉개지 않는다는 설계 원칙의 또 다른 예시).

**근거 테스트**: `test_underground_only_seed_dong_is_all_excluded_from_the_fixture`,
`test_all_excluded_is_distinct_from_no_data`
(`apps/backend/tests/backend_core/test_shelters.py`) — PR #118에서 추가,
리뷰 2건(안은남 승인 — 테스트 98건 통과 확인, 신호정으로 추정되는 리뷰어 승인 — 재현
직접 확인) 완료.

**⚠️ e2e 미커버**: PR #118 리뷰에서 "e2e 자동화는 이 PR 범위 밖(#68 DoD가 허용한 분담)"으로
명시적으로 남겼습니다. QA(PM) 몫으로 남아 있으니, 시연 전 수동 재현은 되지만
CI 회귀 그물은 아직 없다는 점을 인지하고 진행합니다.

**발표 멘트 포인트**: "이건 대피소를 다시 고르는 기능이 아니라, 위험한 곳으로 안내하지
않기 위한 안전 필터가 극단적으로 작동한 사례입니다"로 케이스 4와 명확히 구분해 말합니다.

## 발표 진행 순서(제안)

1. 케이스 3 (curl, 가장 안정적·결정론적) → 2. 케이스 6 (curl, 안전 필터 — 결정론적) →
3. 케이스 2 (브라우저, 사전 리허설 필수) → 4. 케이스 5 (브라우저, 사전 리허설 필수) →
5. 케이스 1 (curl, "설계 원칙의 확장" 프레이밍) → 6. 케이스 4 (슬라이드, 사실상 확정).

케이스 순서는 "결정론적으로 재현되는 것부터, 설명이 필요한 것을 나중에" 원칙입니다.
**브라우저 조작이 들어가는 케이스 2·5는 무대에서 실패할 확률이 가장 높으므로**
리허설(8/31~9/1) 때 각각 최소 3회 반복 확인합니다 — 특히 케이스 5는 ai-engine을
껐다 켜는 조작이 시연 중간에 들어가므로, 그 타이밍(질문 클릭 전에 확실히 내려가 있는지)을
리허설에서 맞춰봐야 합니다. **케이스 6과 4를 마지막에 붙여서
설명합니다** — "이건 실제로 작동하는 안전 필터입니다(케이스 6 시연) → 반대로
경로 재선정은 아직 설계만 확정됐고 구현은 후속 과제로 남았습니다(케이스 4 슬라이드)"
순서로, 라이브 데모의 여운이 남은 채로 미달 항목을 정직하게 짚는 마무리가 됩니다.
