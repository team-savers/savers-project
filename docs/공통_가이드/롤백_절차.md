# 롤백 절차 — 시연 배포를 이전 정상 상태로 되돌리기

이 문서는 [배포_절차.md](배포_절차.md)로 올린 **본 VM**이 새 배포 이후 망가졌을 때,
그 배포 직전의 정상 상태로 되돌리는 절차입니다. 새 VM을 만들지 않고,
같은 VM 위에서 코드와 컨테이너만 되돌립니다.

**전제**: 이 절차가 되돌리는 것은 코드(git 커밋)와 컨테이너 상태뿐입니다.
세션 DB(`savers_sessions` named volume)는 되돌리지 않습니다 — 아래 4절 참고.

## 0. 언제 쓰는가

- 배포 직후 검증(배포_절차.md §1-5·§2-4)에서 실패가 나왔는데,
  원인을 그 자리에서 못 고칠 때.
- 리허설·본선 도중 새 배포(핫픽스 등)가 기존에 되던 것을 깼을 때.
- **판정 불가 상태를 롤백으로 덮지 않습니다** — 예: 특보 API 중단, 대피소 `all_excluded`.
  이건 설계된 폴백이고([AGENTS.md](../../AGENTS.md) `Non-negotiable design constraints`),
  코드가 아니라 외부 의존성 문제라 되돌려도 안 고쳐집니다.

## 1. 사전 준비 — 배포마다 해 둘 것

롤백은 "되돌아갈 지점"이 있어야 성립합니다. **배포 직후 검증을 통과하면 그 커밋에 태그를 답니다.**

```bash
# 배포_절차.md의 검증 8개(§1-5) 또는 본 VM 검증(§2-4)을 통과한 직후, VM 안에서
cd ~/savers-project   # 배포_절차.md가 클론한 경로
git tag -f demo-verified
git log -1 --format="%H %ci" demo-verified   # 태그가 가리키는 커밋과 시각을 기록해 둔다
```

`-f`로 태그를 계속 최신 정상 커밋에 옮깁니다 — 과거 태그를 다 남기지 않고,
"지금 되돌아갈 곳" 하나만 유지합니다. 새 배포를 검증 없이 태그 없이 올리면
그다음 배포가 실패해도 되돌아갈 지점이 없습니다.

## 2. 롤백 실행 — VM SSH 안에서

```bash
cd ~/savers-project
git fetch origin
git status   # 워킹 트리가 지저분하면(로컬 .env 편집 등) 먼저 확인 — .env는 git 추적 밖이라 안전
git checkout demo-verified

docker compose -f infra/docker-compose.yml --profile tls up -d --build
docker compose -f infra/docker-compose.yml --profile tls ps
```

`--build`를 반드시 포함합니다 — 이미지가 태그 관리되지 않으므로,
빼면 옛 커밋 소스에 새 이미지가 안 만들어지고 컨테이너만 재시작돼 아무것도 안 바뀝니다.

**`down -v`를 쓰지 않습니다.** `-v`는 `caddy_data`(TLS 인증서)와
`savers_sessions`(세션 DB) 볼륨을 함께 지웁니다 — 배포_절차.md §4가 이미 경고하는 것과 같은 함정입니다.

## 3. 확인 — 축약 검증

전체 8개(배포_절차.md §1-5)를 다 돌 시간이 본선 현장엔 없습니다. 최소 3개만:

1. **컨테이너가 살아 있는가** — `docker compose ... ps`에서 셋 다 `Up`
2. **엔드투엔드 한 번** — `curl -X POST localhost:8000/internal/alerts/dispatch` (VM 안에서),
   200과 `messageMode`가 기대한 값인지
3. **발송 채널** — `docker compose ... logs backend | grep "push channel selected"`로
   되돌린 커밋의 `SAVERS_PUSH_CHANNEL` 설정이 의도한 값(대개 `fcm`)으로 떴는지
   ([ADR-0023](../adr/0023-explicit-push-channel-selection.md))

셋 다 통과하면 그 자리에서 `demo-verified` 태그를 그대로 두거나(문제의 새 배포를 버렸으므로),
필요하면 1절 명령으로 다시 찍습니다.

## 4. 롤백 후에도 남는 것 / 사라지는 것

| 항목 | 롤백에 영향받는가 | 이유 |
|---|---|---|
| 세션 DB (`savers_sessions` 볼륨) | **아니요, 그대로 남습니다** | named volume은 `down -v` 전까지 컨테이너·이미지 교체와 무관합니다 (ADR-0022) |
| 발급된 세션 토큰·보호자 링크 | **아니요, 유효합니다** | 위와 같은 이유로 SQLite 파일이 살아 있습니다 |
| 보호자 FCM 기기 등록 | **아니요, 유지됩니다** | 같은 이유입니다. 리허설에서 등록한 폰이 롤백으로 풀리지 않습니다 |
| `infra/.env` 값 | **아니요, 그대로입니다** | git 추적 밖이라 `git checkout`의 영향을 받지 않습니다 |
| 코드(라우터·검증 로직·프롬프트 등) | **예, 되돌아갑니다** | `git checkout`이 바꾸는 대상 그 자체입니다 |
| **되돌린 커밋 시점 이후 스키마 변경** | ⚠️ **미해결** | 세션 DB에 마이그레이션 체계가 없습니다. 되돌린 코드가 그 사이 늘어난 컬럼을 모르면 어떻게 실패하는지 확인되지 않았습니다 - `불확실`. 본선 전 최소 1회 이 케이스로 리허설 필요(후속 조치) |

## 5. 실행 주체

**9/1 리허설**: PM(안은남)이 이 절차서를 들고 실행하고, Backend(김도혁)도 같은 세션에서
최소 1회 직접 실행해 봅니다 — 절차서가 작성자 없이도 따라 할 수 있는지 확인하는 것이
목적이라, 두 사람 다 해 봅니다. (기존 역할_가이드 01·04, 역할_일정 00-overall의
문구 차이는 서로 다른 사람이 한다는 뜻이 아니라 같은 합동 세션을 각자 관점에서 적어
생긴 표현 차이였습니다 — 이 PR에서 세 문서 표현을 통일합니다.)

**9/2 본선 현장 실행자: PM(안은남).**
⚠️ 2026-09-01, 안은남 확인 — 본선 발표자는 김도혁(Backend)입니다. 이 절차의 원래 전제
("무대에 없는 사람이 롤백을 실행한다")를 그대로 적용하면, 무대에 없는 쪽이 PM이므로
실행자도 PM입니다. `역할_가이드/04-백엔드.md`·`README.md`·`역할_일정/00-overall.md`·
`01-기획총괄.md`·`04-백엔드.md`가 반대로 적고 있던 것을 같은 커밋에서 정정했습니다.

**다만 이 정정은 [ADR-0019](../adr/0019-role-scope-after-2026-08-11-reshuffle.md) 결정
2번을 뒤집는 것이라, 김도혁(Backend)의 확인이 아직 없습니다** — ADR-0019 자체가 세운
"누군가의 일을 정하면 그 일을 할 사람의 확인도 함께 받는다"는 기준([ADR-0018](../adr/0018-three-layers-three-core-technologies.md))에
따라, 원래 Backend에게 있던 실행 몫을 PM으로 옮기는 결정은 Backend 확인이 있어야
ADR 결정 본문으로 굳습니다. 그 전까지는 PM 제안 단계입니다.
**후속 조치**: 김도혁 확인 후 ADR-0019·ADR-0015의 "김도혁 확인 대기" 표기를 정리.
