## 1. 대원칙: 설정은 파일로 따라오지 않는다

저장소를 구성하는 것은 두 트랙이고, **git이 추적하는 것은 한쪽뿐**입니다.

| 트랙 | 예 | 어떻게 유지되나 |
|---|---|---|
| **파일** | 워크플로, 이슈/PR/Discussion 템플릿, `labels.yml`, pre-commit 설정, 코드, 문서 | git이 추적 — PR diff에 보이고 자동으로 따라옴 |
| **설정** | 브랜치 보호 규칙, 라벨 실체, 머지 전략, Secrets/Variables, Discussions 활성화·카테고리, Code security, 협업자 권한 | GitHub 서버에만 존재 — **diff에 보이지 않고**, `scripts/setup-github.sh` + 수동 설정(§3)으로만 재현 |

이 비대칭이 이 문서가 존재하는 이유입니다. 설정 쪽은 누가 콘솔에서 바꿔도 기록이 남지 않으므로,
**바꿨으면 스크립트에도 반영**해야 다음 사람이 같은 상태를 재현할 수 있습니다.

## 2. 저장소 하드닝 (admin, 1회)

```bash
gh auth login                                              # 대상 레포 admin 권한 필요
bash scripts/setup-github.sh team-savers/savers-project     # 브랜치 보호 + 머지 전략 + 라벨
```

`--solo` 옵션을 붙이면 PR 승인 요구를 끕니다(1인 작업용 — 승인자가 없어 머지가 막히는 상황 방지).

**재실행이 필요한 시점**

- CI 잡 이름을 바꾸거나 앱을 추가했을 때 → `setup-github.sh`의 `contexts`를 **같은 PR에서** 고친 뒤 재실행 (§4)
- 루트 `CODEOWNERS`에 경로를 추가/변경했을 때 → 새 경로에 오너가 **3명 이상**인지 확인 후 재실행
  (`require_code_owner_reviews`는 계정 배정이 끝나 이미 `true`입니다)
- 브랜치 보호가 403으로 실패했을 때 → 원인 해소 후 재실행. 스크립트는 보호 적용에 실패해도
  머지 전략·라벨은 계속 적용하고, 무엇이 빠졌는지 마지막에 출력합니다.

## 3. 수동 설정 체크리스트 (스크립트가 못 하는 것)

**현 저장소(team-savers/savers-project)에서는 아래 항목이 모두 적용 완료**입니다. 이 목록은 저장소를
새로 만들거나 설정이 초기화됐을 때를 위한 절차로 남겨둡니다.

- [x] **Settings → General → Features**: Discussions 활성화
- [x] **Discussions → 카테고리 `CollaborationLog` 생성** — Discussion 카테고리는 API가 없어 수동 생성만
      가능합니다. 만들지 않으면 이슈 config의 협업 일지 링크와 `DISCUSSION_TEMPLATE`이 동작하지 않습니다.
- [x] **Settings → Code security**: Secret scanning + Push protection 활성화 (public 저장소 전용 기능)
      — ⚠️ 이것만 믿으면 안 됩니다. GitHub의 탐지는 **제휴 발급사 패턴 위주**라 이 프로젝트가 쓰는
      카카오·HyperCLOVA X(NCP)·솔라피 키는 사각지대일 가능성이 높습니다(추정).
      실질 방어선은 pre-commit의 **gitleaks** 훅과 CI의 전체 트리 스캔입니다.
- [x] (팀) Collaborators/Teams 권한 부여 → 루트 `CODEOWNERS`에 실제 계정 배정 완료
      — 팀원이 바뀌면 collaborator 권한(write 이상)과 `CODEOWNERS`를 **함께** 갱신하세요.
      write 권한이 없는 계정은 오너로 인정되지 않아 조용히 무시됩니다.
- [ ] (필요 시) Actions Secrets/Variables 등록 — 워크플로가 참조하는 secret이 없으면 등록 전까지 CI가 실패합니다

## 4. CI 계약 유지 규칙

required status check는 **브랜치 보호 설정(서버)과 워크플로 파일(git)이 문자열로 맺은 계약**입니다.
한쪽만 바꾸면 모든 PR이 조용히 막히므로, 아래 세 가지는 규칙으로 취급하세요.

- **required check에 `paths:` 필터를 걸지 말 것.** 필터가 걸린 워크플로는 해당 경로를 건드리지 않은
  PR에서 **체크 자체가 생성되지 않고**, 머지는 영원히 `Expected` 상태로 대기합니다.
  그래서 `ci.yml`은 필터 없이 모든 PR에서 돌고, 경로 필터형인 `frontend-ci.yml`·`notebook-check.yml`
  등 4종은 required로 지정하지 않습니다. CI 비용을 줄이려면 `dorny/paths-filter` 같은 **잡 내부** 필터를 쓰세요.
- **required check의 context 이름 = 잡의 `name:`.** `setup-github.sh`의 `contexts` 배열과 `ci.yml`의
  잡 이름은 문자열이 정확히 일치해야 합니다. 매트릭스 잡이라 이름이 전개되어 현재 5종입니다 —
  `Pre-commit hooks`, `Lint & Type Check (backend)` / `(ai-engine)`, `Unit tests (backend)` / `(ai-engine)`.
  **앱을 추가하면 `ci.yml`의 matrix와 `setup-github.sh`의 contexts를 같은 PR에서 함께 늘리세요.**
- **브랜치 보호는 첫 CI가 돈 뒤에 적용.** GitHub가 아직 본 적 없는 체크 이름을 required로 걸면
  PR에서 `Expected` 대기가 생길 수 있습니다. 스크립트는 이름 문자열로 직접 지정하므로 동작하지만,
  가능하면 첫 push 이후에 실행하세요.

## 5. 라벨 동기화

`.github/labels.yml`이 **원천**입니다. 라벨을 바꾸려면 콘솔이 아니라 파일을 고치고 동기화하세요.

```bash
bash scripts/apply-labels.sh team-savers/savers-project
```

PR 템플릿의 '변경 유형' 체크박스와 라벨 목록은 짝을 이루므로 **함께** 갱신합니다.

## 6. 태그·시연 브랜치 명명

저장소에 태그가 하나도 없던 상태에서 코드 프리즈를 위해 정한 규약입니다.

근거: [ADR-0025](../adr/0025-freeze-tag-and-demo-branch-naming.md) (승인, 2026-08-30).

| 대상 | 형식 | 예 |
|---|---|---|
| 프리즈 태그 | `freeze-YYYYMMDD`, 프리즈 후 승인된 수정마다 `.N` 증분 | `freeze-YYYYMMDD` → `freeze-YYYYMMDD.1` → `freeze-YYYYMMDD.2` |
| 시연 브랜치 | `demo/finals` — 고정 이름 하나, 날짜를 붙이지 않습니다 | `demo/finals` |

**형식의 근거**

- **사람이 만든** 브랜치가 전부 `<목적>/<영문-케밥>`이고
  (`docs/` `feat/` `fix/` `chore/` `qa/` `contracts/` `test/` `ci/`
  `refactor/` `integration/` `infra/` `eval/` 12종),
  날짜가 들어간 브랜치는 `YYYYMMDD` 압축형을 씁니다
  (`docs/adr-approvals-20260828`). 태그도 같은 축을 그대로 씁니다.
  사람이 짓지 않은 이름은 규약의 반례로 치지 않습니다 — 자동 생성분이 19건 있습니다.
  Dependabot 17건(`dependabot/pip/apps/backend/...`처럼 슬래시가 여러 개라
  애초에 `<목적>/<영문-케밥>`이 아닙니다)과
  GitHub 웹 편집기가 만든 `eunnamahn-patch-N` 2건입니다.
- 하이픈은 이미 「목적-날짜」 구분자로 썼으므로, 연번은 `.`으로 갈라야 날짜와 섞이지 않습니다.
- 사전순 정렬이 곧 시간순이라 `git tag -l 'freeze-*' | tail -1`이 항상 최신 프리즈입니다.
- **태그는 한 개가 아닙니다.** 프리즈 이후에도 시연 경로 버그 수정은 전 역할 합의를 받아
  태그로 남기므로([역할_가이드/02-테크리드.md](../역할_가이드/02-테크리드.md) 코드 프리즈 항),
  연번 자리가 규약에 처음부터 있어야 합니다.
  합의 근거는 어노테이트 태그(`git tag -a`)의 메시지에 적습니다.
- **semver(`v0.10.0`)는 쓰지 않습니다.** 이 저장소에서 `v0.10`은 이미
  계약 개정판을 가리키는 이름입니다 — `packages/contracts/openapi.yaml`이
  `version: 0.10.0-draft`를 싣고 있고,
  ADR 2건이 「계약 v0.10」으로 인용합니다 —
  [0014](../adr/0014-closed-loop-second-dispatch-channel.md),
  [0021](../adr/0021-guardian-qa-korean-only.md).
  태그에 같은 문자열을 붙이면 한 이름이 두 가지를 뜻하게 됩니다.
  `apps/*/pyproject.toml`의 `0.1.0`은 한 번도 올린 적이 없어 판번호 노릇을 하지 못합니다.

**운영상 주의**

- ⚠️ **시연 브랜치에 직접 push하면 CI가 돌지 않습니다.**
  워크플로의 push 트리거가 전부 `branches: [main]`이기 때문입니다.
  프리즈 후 수정은 **`main`으로 PR을 거친 뒤 새 태그를 찍는** 경로여야 합니다.
  시연 브랜치는 「무엇을 시연했는가」를 가리키는 포인터이지 작업 브랜치가 아닙니다.
  ⚠️ **`demo/finals`로는 PR을 열지 마십시오.**
  이 저장소는 머지 시 head 브랜치를 자동 삭제하므로(`delete_branch_on_merge: true`),
  누가 그 PR을 머지하는 순간 시연 브랜치가 사라집니다.
  리허설이나 본선 당일의 실수를 경고문으로 막을 수는 없으므로, 열 이유 자체를 없앱니다 —
  검사가 목적이라면 이미 끝나 있습니다. 프리즈 커밋은 `main`을 거쳐 왔고,
  `main`은 브랜치 보호가 required check 5종을 `strict: true`로 요구해
  검사를 통과한 커밋만 받습니다.
- ⚠️ **Vercel은 시연 브랜치를 보긴 봅니다 — 다만 빌드까지 갈지는 마지막 커밋이 정합니다.**
  [배포_절차.md](배포_절차.md) 79행은 Deployment Branches를 `main` 단독으로 지정하고
  프리뷰를 끄라고 적어 두었는데, `main`이 아닌 브랜치의 PR에도
  `Vercel`·`Vercel Preview Comments` 체크가 붙습니다 —
  그 설정이 대시보드에 적용돼 있지 않은 것으로 보입니다
  (추정 — 대시보드는 git이 추적하지 않으므로 눈으로 확인해야 합니다).
  체크가 붙는 것이 곧 빌드는 아닙니다.
  [apps/frontend/vercel.json](../../apps/frontend/vercel.json)의
  `ignoreCommand`(`git diff --quiet HEAD^ HEAD -- .`)가 Root Directory인 `apps/frontend`를
  **마지막 커밋 한 개**에서만 보고, 변경이 없으면 빌드를 건너뛰기 때문입니다.
  #227의 `Vercel` 체크 설명이 실제로 `Canceled by Ignored Build Step`입니다.
  판정은 양쪽으로 어긋납니다 — #217이 `Deployment has completed`로 끝난 것은
  head가 `main`을 들여온 머지 커밋이라 `apps/frontend` 변경이 딸려 들어왔기 때문이지
  문서 PR이어서가 아니고, 반대로 #226은 `apps/frontend` 6개 파일을 바꾼 PR인데
  head가 프론트를 건드리지 않은 `main` 머지 커밋이라 건너뛰어졌습니다.
  즉 문서만 바꾼 push는 프리뷰가 빌드되지 않습니다.
  건너뛴 배포가 Hobby 하루 100건 한도를 먹는지는 확인되지 않았습니다(불확실).
  한도를 소진하면 **프로덕션 재배포까지 함께 막히므로**
  ([배포_절차.md](배포_절차.md) 0-2절 「프리뷰 배포를 끄는 이유」 —
  8/28 실측 하루 커밋 104건 중 `apps/frontend`를 건드린 것은 12건),
  **프리즈 태그를 찍기 전에 대시보드에서 Deployment Branches를 확인하십시오.**
- ⚠️ **태그를 배포하려면 클론에 `--branch`가 필요합니다.**
  [배포_절차.md](배포_절차.md) 1-3의 `git clone <url>`은 기본 브랜치를 받으므로 태그가 아닙니다.
  `git clone --branch <프리즈 태그> <url>`로 받아야
  「프리즈 태그가 배포되고」([역할_일정/01-기획총괄.md](../역할_일정/01-기획총괄.md) 8/29 행)가 성립합니다.
  태그로 클론하면 detached HEAD가 되는데, 배포 서버에서는 정상입니다.
- 태그로 트리거되는 워크플로는 없습니다. 태그를 밀어도 CI는 돌지 않습니다.
  다만 검사 여부를 사람이 기억해 되짚을 필요는 없습니다 — 태그는 `main` 커밋에만 찍고,
  위와 같은 이유로 `main`에는 required check 5종을 통과한 커밋만 들어옵니다.
  태그가 가리키는 트리는 그래서 이미 검사를 통과한 것입니다.

## 7. 상류 템플릿 역반영

이 저장소는 [Yopkigom/ai-project-template](https://github.com/Yopkigom/ai-project-template)에서 파생됐습니다.
여기서 발견한 개선점(새 함정, 더 나은 CI 구성, 관례)은 템플릿 쪽에 되돌려 두세요 — 템플릿은
"가장 최근 프로젝트의 교훈이 쌓인 곳"일 때만 가치가 있습니다.
이미 생성된 파생 저장소로는 자동 전파되지 않으므로, 반대 방향은 `git remote add template ...` 후
선별 cherry-pick으로 가져옵니다.
