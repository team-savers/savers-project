# AWS 계정 발급 가이드 (PM용)

한 줄 요약: 팀원이 AWS 서버를 만들고 접속할 수 있도록
**출입증(IAM 사용자 계정)을 발급하는 절차**입니다.

이 문서는 **계정 관리자(은남님)만 할 수 있는 작업**을 다룹니다.
서버에 들어간 뒤의 운영 작업은 [서버_운영.md](서버_운영.md)에 있으니 그쪽을 보시면 됩니다.
접속 방식의 근거는 [ADR-0009](../adr/0009-ssm-session-manager.md)입니다.

목표는 완벽한 권한 설계가 아니라 **오늘 30분 안에 안전하게 끝내는 것**입니다.
예선 마감이 2026-08-10 13:00입니다.

---

## 1. 왜 이 문서가 은남님 몫인가

[ADR-0009](../adr/0009-ssm-session-manager.md)의 후속 조치표에는
IAM 역할 생성과 정책 부여가 Backend/Infra(도혁님) 소관으로 적혀 있습니다.
그런데 **도혁님 계정 권한으로는 그 작업을 할 수 없습니다.**

개발자에게 주는 권한(PowerUserAccess)은 의도적으로 IAM 조작을 막습니다.
자기 권한을 스스로 올릴 수 없게 하려는 것이라 이 제한 자체는 옳습니다.
대신 **IAM 역할 만들기와 정책 붙이기는 계정 관리자가 해 주어야 합니다.**

은남님이 해야 하는 것은 다섯 가지입니다.

| 순서 | 작업 | 이걸 안 하면 |
|---|---|---|
| 1 | 예산 알림 설정 | 비용이 소리 없이 불어납니다 |
| 2 | 정책 3개 만들기 | 아래 작업들의 재료가 없습니다 |
| 3 | 서버용 역할 `savers-ec2-ssm` 만들기 | 도혁님이 서버에 역할을 못 붙입니다 |
| 4 | 도혁님 계정 발급 (인프라 작업용) | 서버를 만들 수 없습니다 |
| 5 | 두 사람 모두 `Developers` 그룹에 넣기 | 권한이 좁아 EC2 화면에서 아무것도 조회되지 않습니다 |

3번은 **4번보다 먼저** 해야 합니다. 그 외에는 순서 의존성이 없습니다.
4절에 표로 정리했습니다.

---

## 2. 먼저 이것만 알면 절반입니다

### (1) AWS에는 "월 10만원까지만" 같은 지출 상한이 없습니다

확실한 사실입니다. AWS가 제공하는 것은 **알림**뿐이고,
한도를 넘겨도 서비스가 자동으로 멈추지 않습니다.
그래서 예산 알림을 권한 설정보다 먼저 합니다.

팀 예산 상한은 45만원입니다([비용_산정.md](비용_산정.md) 기준).
서버 한 대가 월 6만~11만원이라 정상 운영이면 여유가 있습니다.
위험한 것은 정상 운영이 아니라 **오조작과 키 유출**입니다.

### (2) 액세스 키(Access Key)는 기본적으로 발급하지 않습니다

액세스 키는 비밀번호와 MFA를 건너뛰고 AWS를 조작할 수 있는 문자열입니다.
우리 저장소는 **공개**라서, 실수로 한 번 올라가면 되돌릴 수 없습니다.
지우고 커밋을 되돌려도 이미 공개된 것으로 보고 폐기해야 합니다.

두 사람 모두 브라우저로 작업할 수 있으므로 액세스 키는 필요 없습니다.
요청이 오면 그때 발급하고, 쓴 뒤 삭제합니다.

### (3) 루트 계정은 은남님만 씁니다

가입할 때 만든 이메일 계정이 루트 계정입니다.
누구에게도 공유하지 않고, MFA(휴대폰 인증)를 반드시 켜 둡니다.

### (4) 서버 안에는 비공개 키가 평문으로 있습니다

`infra/.env`에 HyperCLOVA X(NCP) 키가 들어 있습니다.
**셸에 들어갈 수 있는 사람은 그것을 전부 읽을 수 있습니다.**
[ADR-0009](../adr/0009-ssm-session-manager.md)가 셸 권한을 2인으로 좁힌 이유가 이것입니다.
"접속자를 늘려 달라"는 요청은 편의 문제가 아니라 **키 유출 경로를 늘리는 결정**입니다.

## 3. 계정은 두 개, 권한은 서로 다릅니다

[ADR-0009](../adr/0009-ssm-session-manager.md)가 셸 접근자를 김도혁, 신호정 2인으로 정했습니다.
**두 사람 모두 인프라 작업을 겸하므로 같은 권한을 받습니다.**

| 사람 | 하는 일 | 주는 권한 |
|---|---|---|
| **김도혁** (Backend/Infra) | 서버를 만들고 고칩니다 | `Developers` 그룹 |
| **신호정** (Tech Lead) | 서버를 만들고 고칩니다 | `Developers` 그룹 |
| 그 외 4명 | 공개 HTTPS로 상태만 확인 | **계정 발급 안 함** |

```
김도혁 · 신호정 IAM 사용자
 └── Developers 그룹
      ├── PowerUserAccess          (AWS 기본 제공, 넓은 개발 권한)
      ├── SaversRegionLock         (직접 만듦, 서울 리전 밖 차단)
      └── SaversPassEc2Role        (직접 만듦, 서버에 역할 연결 허용)
```

⚠️ **`PowerUserAccess`에는 SSM 접속 권한이 이미 들어 있습니다.**
그래서 이 구성에서는 별도의 셸 접근 정책(`SaversSsmShell`)이 필요 없습니다.
그 정책은 **인프라 권한 없이 셸만 필요한 사람이 생길 때**(예: QA) 쓰려고 남겨 둔 것이고,
지금은 만들지 않으셔도 됩니다. 이유는 8절에 있습니다.

### 왜 도혁님에게는 PowerUserAccess인가

원칙적으로는 "필요한 권한만 골라 주기"(최소 권한)가 맞습니다.
다만 무엇을 빠뜨렸는지는 **도혁님이 새벽에 막힐 때** 알게 됩니다.
마감 3일 전에 그 리스크를 지기보다, 넓게 주고 **울타리 세 개**를 치는 쪽이 현실적입니다.

| 울타리 | 막는 것 |
|---|---|
| 서울 리전 제한 | 다른 지역에 실수로 또는 몰래 자원이 생기는 것 |
| 예산 알림 | 비용이 소리 없이 불어나는 것 |
| 액세스 키 미발급 | 저장소 유출로 계정이 통째로 털리는 것 |

PowerUserAccess는 IAM 사용자 생성, 정책 수정, 권한 부여를 막습니다.
즉 도혁님이 자기 권한을 스스로 올릴 수는 없습니다.

## 4. 작업 순서

순서가 중요한 곳은 한 군데뿐입니다.
**Step 3(역할 생성)이 Step 4보다 먼저**여야 합니다. 나머지는 위에서부터 그대로 따라가시면 됩니다.

| 순서 | 작업 | 선행 조건 |
|---|---|---|
| Step 1 | 예산 알림 | 없음 |
| Step 2 | 정책 2개 생성 (`SaversRegionLock`, `SaversPassEc2Role`) | 계정 번호 확인 |
| Step 3 | 역할 `savers-ec2-ssm` 생성 | 없음 |
| Step 4 | `Developers` 그룹 생성 + 두 사람 계정 발급 | Step 2, 3 |
| Step 5 | 서버 생성 + 역할 부착 (은남님 작업 아님) | Step 4 |
| Step 6 | SSM 접속 확인 후 22번 폐쇄 (은남님 작업 아님) | Step 5 |
| Step 7 | 두 사람 MFA 등록 확인 | Step 4 |

Step 6은 개발자 작업이지만, 순서를 어기면 **아무도 서버에 못 들어갑니다.**
"SSM으로 실제 들어가 본 다음에 22번을 닫는다"는 순서를 꼭 확인해 주십시오
([서버_운영.md](서버_운영.md) 2-5).

### Step 1. 예산 알림 (5분)

1. 콘솔 우측 상단 계정 메뉴 -> **Billing and Cost Management**
2. 좌측 **Budgets** -> **Create budget** -> **Cost budget**
3. 예산 금액: 월 150,000원에 해당하는 USD (환율 1,400원 기준 약 **110 USD**)
4. 알림 임계값: **50% / 80% / 100%** 세 개를 각각 추가
5. 받는 사람: 은남님 이메일. 도혁님 이메일도 함께 넣으시면 좋습니다

주의: 알림은 하루 한 번 정도 갱신되므로 실시간이 아닙니다.
큰 사고를 막는 장치가 아니라 **주 단위 이상 징후를 잡는 장치**입니다.

### Step 2. 정책 2개 만들기

IAM -> **Policies** -> **Create policy** -> **JSON** 탭에 7절 내용을 붙여넣습니다.
이름은 `SaversRegionLock`, `SaversPassEc2Role`로 지어 주십시오.

`SaversPassEc2Role`에는 **12자리 AWS 계정 번호**를 직접 넣어야 합니다.
계정 번호는 콘솔 우측 상단 계정 메뉴에서 확인하실 수 있습니다.

### Step 3. 서버용 역할 만들기

**이 단계를 건너뛰면 도혁님이 막힙니다.**

IAM -> **Roles** -> **Create role**

1. 신뢰할 수 있는 엔터티: **AWS service** -> **EC2**
2. 권한 정책: `AmazonSSMManagedInstanceCore` 하나만 선택
3. 역할 이름: **`savers-ec2-ssm`**

이름을 정확히 맞춰 주십시오.
[서버_운영.md](서버_운영.md) 2-1과 7절의 PassRole 정책이 이 이름을 전제로 합니다.

참고: 이 정책은 **서버가 쓰는 것**입니다. 사람 계정에 붙이면 아무 효과가 없습니다.

### Step 4. 그룹 만들고 두 사람 계정 발급

먼저 IAM -> **User groups** -> **Create group**

- 그룹 이름: `Developers`
- 연결할 정책 3개: `PowerUserAccess`(AWS 제공), `SaversRegionLock`, `SaversPassEc2Role`

그다음 IAM -> **Users** -> **Create user**를 **두 번** 반복합니다.

| 항목 | 설정 |
|---|---|
| 사용자 이름 | `dohyeok` / `hojeong` |
| 콘솔 접근 | 활성화 |
| 비밀번호 | 자동 생성 |
| 다음 로그인 시 변경 | 체크 |
| 그룹 | **둘 다 `Developers`** |
| 액세스 키 | **만들지 않음** |

> **이미 계정이 있는 사람은 그룹에만 넣으면 됩니다.**
> IAM -> Users -> 해당 사용자 -> **그룹** 탭 -> **그룹에 사용자 추가** -> `Developers`.
> 이 단계를 빠뜨리면 EC2 화면에서 역할 목록이 비어 보이고
> `iam:GetInstanceProfile을(를) 사용할 권한이 없습니다` 경고가 뜹니다.

만든 직후 화면의 **로그인 URL, 사용자 이름, 임시 비밀번호**를 받아 둡니다.
이 화면을 벗어나면 비밀번호는 다시 볼 수 없습니다.

### Step 5. 서버를 만듭니다 (은남님 작업 아님)

절차는 [배포_절차.md](배포_절차.md)와 [서버_운영.md](서버_운영.md) 2-1에 있습니다.
이때 한 가지 부탁해 주십시오.
인스턴스에 **태그 `Project = savers`** 를 달아 달라는 것입니다.
비용을 자원별로 쪼개 볼 때 쓰고, 7절의 선택안을 쓸 때도 필요합니다.

키페어(`.pem`)는 만들되 **팀에 공유하지 않습니다.**
SSM이 고장 났을 때의 최후 경로로 서버를 만든 사람만 보관합니다([ADR-0009](../adr/0009-ssm-session-manager.md) 완화책).

### Step 6. 서버 접속 확인과 22번 폐쇄 (은남님 작업 아님)

개발자가 SSM으로 실제 접속에 성공한 뒤 보안그룹의 22번 규칙을 지웁니다.
**순서를 어기면 아무도 못 들어갑니다**([서버_운영.md](서버_운영.md) 2-5).

> **셸 접근 정책(`SaversSsmShell`)은 지금 만들지 않으셔도 됩니다.**
> 두 사람 모두 `Developers` 그룹에 있고, `PowerUserAccess`에 SSM 접속 권한이
> 이미 포함되어 있기 때문입니다.
> 그 정책은 **인프라 권한 없이 셸만 필요한 사람이 생길 때**(예: QA) 쓰려고 남겨 둔 것이고,
> JSON은 [서버_운영.md](서버_운영.md) 2-3에 있습니다. 이유는 8절에 적었습니다.

### Step 7. MFA 등록 확인

두 분이 처음 로그인해 비밀번호를 바꾸고 나면,
IAM -> Users -> 해당 사용자 -> **Security credentials** -> **Assign MFA device**에서
휴대폰 인증 앱을 등록하도록 안내해 주십시오.

주의: MFA를 정책으로 **강제**하는 방법도 있지만,
설정을 잘못하면 로그인 자체가 막혀 마감 직전에 시간을 잃습니다.
지금은 강제하지 말고 등록 여부를 눈으로 확인하시는 편을 권합니다. (추정 기반 판단)

## 5. 우리가 실제로 쓰는 AWS 자원

[ADR-0003](../adr/0003-single-vm-seoul.md), [ADR-0009](../adr/0009-ssm-session-manager.md) 기준입니다.

| 자원 | 개수 | 설명 |
|---|---|---|
| EC2 인스턴스 | 1대 | 서버 본체입니다. t3.medium 또는 t3.large |
| EBS 디스크 | 30GB | 서버에 붙는 저장 공간입니다 |
| 탄력적 IP | 1개 | 바뀌지 않는 서버 주소입니다 |
| 보안 그룹 | 1개 | 방화벽입니다. 최종적으로 80과 443만 열립니다 |
| IAM 역할 | 1개 | `savers-ec2-ssm`. 서버가 SSM에 등록되기 위한 것입니다 |

S3, RDS, Lambda, ECR은 **현재 계획에 없습니다.**
도커 이미지는 서버 안에서 직접 빌드하고, 로그도 서버 안에서 봅니다.

세션 명령 이력을 S3에 남기는 기능은 [ADR-0009](../adr/0009-ssm-session-manager.md)에서 예선 범위 밖으로 유보했습니다.
본선에서 감사 요구가 생기면 그때 켭니다.

## 6. 서버 접속 방식

[ADR-0009](../adr/0009-ssm-session-manager.md)에 따라 **SSM Session Manager**로 접속합니다.
브라우저에서 AWS 콘솔에 로그인해 바로 셸을 여는 방식입니다.

은남님 입장에서 중요한 것은 두 가지입니다.

**회수가 간단합니다.** 누군가 팀을 떠나거나 역할이 바뀌면
IAM에서 `SaversSsmShell` 정책을 떼면 끝입니다. 서버에는 손대지 않습니다.
`.pem` 파일을 나눠 갖는 방식이었다면 전원의 키를 바꿔야 했습니다.

**기록이 남습니다.** 누가 언제 셸을 열었는지가 사람 단위로 CloudTrail에 남습니다.
다만 **안에서 무슨 명령을 쳤는지는 남지 않습니다.**
세션 시작 사실만 기록된다는 점을 알고 계시면 됩니다.

접속 절차와 문제 해결은 [서버_운영.md](서버_운영.md) 2절에 있습니다.

## 7. 붙여넣을 정책 JSON

`SaversSsmShell`은 [서버_운영.md](서버_운영.md) 2-3에 있으니 여기서는 나머지 둘만 싣습니다.

### 7.1 `SaversRegionLock` (서울 리전 밖 차단)

도혁님 계정에만 붙입니다.
목록에 적힌 서비스들은 지역 개념이 없어 예외로 둡니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideSeoul",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "sts:*",
        "organizations:*",
        "account:*",
        "support:*",
        "budgets:*",
        "ce:*",
        "cur:*",
        "health:*",
        "trustedadvisor:*",
        "route53:*",
        "cloudfront:*",
        "s3:List*",
        "s3:GetBucketLocation"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": "ap-northeast-2"
        }
      }
    }
  ]
}
```

### 7.2 `SaversPassEc2Role` (서버에 역할 연결 허용)

도혁님 계정에만 붙입니다.
`111122223333`을 실제 12자리 계정 번호로 바꿔 주십시오.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PassSaversEc2RoleOnly",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::111122223333:role/savers-ec2-*",
      "Condition": {
        "StringEquals": {
          "iam:PassedToService": "ec2.amazonaws.com"
        }
      }
    },
    {
      "Sid": "ReadRolesForConsole",
      "Effect": "Allow",
      "Action": [
        "iam:GetRole",
        "iam:ListRoles",
        "iam:GetInstanceProfile",
        "iam:ListInstanceProfiles",
        "iam:ListInstanceProfilesForRole"
      ],
      "Resource": "*"
    }
  ]
}
```

두 번째 블록은 읽기 전용입니다.
이게 없으면 EC2 화면에서 역할 선택 목록이 비어 보입니다.

### 7.3 선택안: 인스턴스 ID 대신 태그로 지정하기

[서버_운영.md](서버_운영.md) 2-3의 정책은 인스턴스 ID를 직접 적습니다.
서버를 다시 만들면 ID가 바뀌어 정책을 매번 고쳐야 합니다.

Step 5에서 인스턴스에 태그 `Project = savers`를 달았다면,
첫 번째 블록을 아래로 바꿔 그 손질을 없앨 수 있습니다.

```json
{
  "Effect": "Allow",
  "Action": "ssm:StartSession",
  "Resource": [
    "arn:aws:ec2:ap-northeast-2:111122223333:instance/*",
    "arn:aws:ssm:ap-northeast-2::document/SSM-SessionManagerRunShell"
  ],
  "Condition": {
    "StringEquals": {
      "ssm:resourceTag/Project": "savers"
    }
  }
}
```

높은 신뢰 수준의 표준 패턴입니다.
다만 **태그가 붙지 않은 서버에는 접속이 안 되므로**,
새 서버를 만들 때 태그를 빠뜨리면 원인을 찾기 어려운 접속 실패가 납니다.
어느 쪽이 나은지는 도혁님과 정하시면 됩니다.
예선까지는 서버를 다시 만들 일이 드무니 기존 방식(ID 직접 지정)도 무방합니다.

## 8. 알아 두셔야 할 충돌 하나

[ADR-0009](../adr/0009-ssm-session-manager.md)는 "계정 전체 `ssm:StartSession`을 주지 않고
이 인스턴스 하나로 좁힌다"고 정했습니다.
그런데 **PowerUserAccess에는 이미 계정 전체 SSM 권한이 들어 있습니다.**

IAM에서 권한은 **더해지는** 방식입니다.
넓은 허용과 좁은 허용을 같이 붙이면 넓은 쪽이 이깁니다.
좁은 정책은 넓은 정책을 깎지 못합니다.
그래서 도혁님에게는 범위 제한이 **실질적으로 적용되지 않습니다.** (확실한 사실)

이것을 억지로 막을 수는 있지만, 그러지 않기를 권합니다.
서버를 만들고 지울 수 있는 사람은 언제든 새 서버를 띄워 들어갈 수 있어서,
막아도 실효가 없고 정책만 복잡해집니다.
게다가 인스턴스를 다시 만들 때마다 정책을 고쳐야 해서 마감 직전에 사고가 납니다.

**두 사람 모두 인프라 작업을 겸하므로, 현재 구성에는 이 범위 제한이 적용되는 사람이 없습니다.**

그래서 실제로 통제 역할을 하는 것은 아래 넷입니다. 3절의 울타리와 같은 것들입니다.

| 통제 | 막는 것 |
|---|---|
| 셸 접근자 2인 제한 | 서버 안 키를 읽을 수 있는 사람 수 |
| 서울 리전 잠금 | 다른 지역에 자원이 생기는 것 |
| 액세스 키 미발급 | 저장소 유출로 계정이 통째로 넘어가는 것 |
| 예산 알림 | 비용이 소리 없이 불어나는 것 |

⚠️ **"범위를 좁혔으니 안전하다"고 이해하시면 안 됩니다.**
지금은 **인프라 권한을 가진 두 사람이 서버 셸에 자유롭게 접근할 수 있는 상태**이고,
그것을 감수하는 근거가 위 표입니다.
문서와 실제가 어긋난 채로 통제가 있다고 믿는 것이 통제가 없는 것보다 나쁩니다.

`SaversSsmShell` 정책은 폐기하지 않고 남겨 둡니다.
**인프라 권한 없이 셸만 필요한 사람이 생길 때**(예: QA) 그 사람에게 붙일 정책이고,
그때는 실효가 있습니다.

ADR-0009 문안도 이 내용으로 정정되었습니다.

## 10. 로그인이나 접속이 안 될 때

### 로그인이 안 되는 경우

1. **주소가 맞는지.** AWS 첫 화면이 아니라
   `https://<계정번호>.signin.aws.amazon.com/console` 로 들어가야 합니다.
2. **콘솔 접근이 켜져 있는지.** IAM -> Users -> 해당 사용자 -> Security credentials
3. **비밀번호가 만료되지 않았는지.** 임시 비밀번호에는 유효기간이 있습니다.
4. **화면은 뜨는데 아무것도 안 보이는 경우.** 우측 상단 리전이
   **서울(ap-northeast-2)** 인지 확인합니다. 리전 제한 정책 때문입니다.

### 셸 접속이 안 되는 경우

1. **서버가 Systems Manager에 등록되어 있는지.**
   콘솔 -> Systems Manager -> Fleet Manager에 인스턴스가 보여야 합니다.
   안 보이면 역할이 안 붙었거나 에이전트가 멈춘 것입니다([서버_운영.md](서버_운영.md) 2-2).
2. **두 사람이 `Developers` 그룹에 들어가 있는지.**
   IAM -> Users -> 해당 사용자 -> 그룹 탭.
   빠져 있으면 EC2 화면에서 역할 목록이 비어 보이고
   `iam:GetInstanceProfile` 권한 경고가 뜹니다.
3. **`SaversSsmShell`을 쓰는 사용자라면** 정책의 인스턴스 ID가 현재 서버와 같은지
   (서버를 다시 만들었다면 ID가 바뀌었습니다 — 7.3 참고).

주의: 22번 포트가 이미 닫힌 상태에서 SSM까지 안 되면 **아무도 서버에 못 들어갑니다.**
도혁님이 보관 중인 `.pem`이 최후 경로이니, 이 상황에서는 먼저 도혁님께 연락해 주십시오.

## 11. 해커톤이 끝나면

잊기 쉬운데, 안 하면 비용과 위험이 계속 남습니다.

- [ ] EC2 인스턴스 종료(Terminate). 정지(Stop)만 하면 디스크 비용이 계속 나갑니다
- [ ] 탄력적 IP 해제. 서버에 안 붙어 있는 IP는 오히려 요금이 붙습니다
- [ ] IAM 사용자 `dohyeok`, `hojeong` 삭제 또는 비활성화
- [ ] 역할 `savers-ec2-ssm` 삭제
- [ ] 액세스 키를 발급했다면 삭제
- [ ] `infra/.env`에 있던 외부 API 키 폐기 또는 재발급
- [ ] 예산 알림은 그대로 두기 (남아 있는 자원을 잡아 줍니다)

## 12. 용어 사전

| 용어 | 쉬운 설명 |
|---|---|
| IAM | AWS의 출입증 관리 시스템입니다 |
| IAM 사용자 | 사람 한 명에게 주는 출입증입니다 |
| 그룹 | 출입증에 붙일 권한 묶음입니다. 사람이 늘어도 그룹만 넣으면 됩니다 |
| 정책(Policy) | "무엇을 해도 되는가"를 적은 규칙 문서입니다 |
| 역할(Role) | 사람이 아니라 **서버나 서비스**가 쓰는 출입증입니다 |
| PassRole | 서버를 만들 때 그 서버에 역할을 붙여 주는 권한입니다 |
| 리전(Region) | AWS 데이터센터가 있는 지역입니다. 우리는 서울 고정입니다 |
| MFA | 비밀번호 외에 휴대폰 인증을 한 번 더 하는 것입니다 |
| 액세스 키 | 프로그램이 AWS를 조작할 때 쓰는 문자열 비밀번호입니다 |
| EC2 | 클라우드에 빌리는 서버 컴퓨터 한 대입니다 |
| 인스턴스 ID | 서버 한 대의 고유 번호입니다. `i-`로 시작합니다 |
| 보안 그룹 | 서버의 방화벽입니다. 어떤 포트를 열지 정합니다 |
| SSM Session Manager | 포트를 열지 않고 브라우저로 서버 셸에 들어가는 AWS 기능입니다 |
| CloudTrail | 누가 언제 무엇을 했는지 기록하는 AWS 장부입니다 |
