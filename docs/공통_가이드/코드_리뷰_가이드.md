# 코드 리뷰 가이드

리뷰 **코멘트를 어떻게 쓰는가**에 대한 규약입니다.
리뷰어로 지정된 사람 전원이 대상입니다.

| 목적 | 문서 |
|---|---|
| 브랜치에서 PR 을 거쳐 머지까지의 **절차** | [pr-checklist.md](../pr-checklist.md) |
| 아키텍처 규칙과 경계 (지적의 **근거**) | [AGENTS.md](../../AGENTS.md) |
| **리뷰 코멘트 작성법** | 이 문서 |
| 문체 규칙 (리뷰 코멘트도 대상) | [문서_작성_규약.md](문서_작성_규약.md) |
| 리뷰 결과를 팀 메신저로 공유 | [메신저_규약.md](메신저_규약.md) + 이 문서 6절 |

> 이 문서는 무엇을 지적할지(1절), 어떻게 쓸지(2 ~ 4절), 어디에 남길지(6절)만 다룹니다.
> 규약 자체의 정본은 `AGENTS.md` 이며, 여기에 복제하지 않습니다.

## 1. 무엇을 보는가 (체크리스트)

리뷰어가 볼 것과 **기계가 이미 보는 것**을 분리합니다.
기계가 판정하는 항목을 사람이 다시 지적하면 조언이 충돌하고,
그 순간 팀은 리뷰 코멘트 전체를 신뢰하지 않기 시작합니다.

### 1-a. 반드시 볼 것

| # | 항목 | 왜 |
|---|---|---|
| 1 | **앱 간 경계 위반** - `apps/ai-engine` 이 `apps/backend` 를 import(역도 동일), `backend_core` 가 `api` 를 import, `e2e/` 가 앱 패키지를 import | import 한 줄이 "독립 배포 가능한 AI 모듈"이라는 성질을 조용히 없앱니다. `e2e/` 는 HTTP 로만 닿습니다 |
| 2 | **계약 누락** - 요청과 응답 스키마를 바꾸면서 `packages/contracts` 를 함께 고치지 않음 | 구두 합의는 계약이 아닙니다. Tech Lead 초반 집중형 모델의 핸즈오프 보험입니다 ([ADR-0002](../adr/0002-frontloaded-tech-lead.md)) |
| 3 | **하드코딩된 키, 토큰, 자격증명** (테스트 픽스처 포함) | public 레포입니다. 푸시되는 순간 공개이며 해결은 revert 가 아니라 폐기와 재발급입니다. GitHub Push protection 은 파트너 발급 패턴만 잡아 이 프로젝트가 쓰는 카카오, HyperCLOVA X, 솔라피 키는 걸리지 않습니다 |
| 4 | **예외 처리 없는 외부 호출** (재난 Open API, 카카오맵, HyperCLOVA X, FCM, 파일 IO) | 의도적 생략이면 주석에 이유가 있어야 합니다 |
| 5 | **폴백 경로 누락** - 공개 API 장애나 지연에서 사전 캐시 모드로 떨어지지 않고 실패하거나, 떨어진 사실을 `messageMode` 에 드러내지 않음 | 열화 폴백은 이 프로젝트에서 **선택이 아니라 하드 제약**입니다 ([AGENTS.md](../../AGENTS.md) `Non-negotiable design constraints`). 조용히 실패하는 재난 알림은 없는 것보다 나쁩니다 |
| 6 | **가드레일 우회** - 테스트를 통과시키려고 가드레일을 목으로 대체 | 테스트를 고치는 것이 아니라 on/off 델타 지표를 무효로 만듭니다. 제출 KPI 입니다 |
| 7 | **위치 정보 취급** - 좌표를 로그, DB, 파일에 남기거나, 세션 밖에서 다시 읽거나, 배경 추적을 도입 | 알림 열람 시점 1회 조회, 세션 스코프, 비영속이 하드 제약입니다. 민감 필드 최소 수집과 암호화도 같은 축입니다 |
| 8 | **논리 오류, 경계 조건 누락, 되돌릴 수 없는 부작용** | |
| 9 | **테스트 가능성** - 도메인 로직이 FastAPI 없이 실행되는가, 지표 함수가 순수 함수 `(prediction, truth) -> score` 로 남는가 | |
| 10 | **CI 계약 드리프트** - required 매트릭스 잡의 `name` 을 바꾸면서 `scripts/setup-github.sh` 의 `contexts` 를 함께 고치지 않음, 또는 required 워크플로에 `paths:` 필터를 추가 | 모든 PR 이 영원히 생성되지 않는 체크를 기다립니다 |
| 11 | **`src.` 접두어 import** | 런타임에 깨지는데 린트가 잡지 못합니다. 기계가 보지 않으므로 사람이 봅니다 |
| 12 | **확정 표기에 ADR 번호가 없음** - 다른 가이드 문서를 근거로 단 경우 포함 | 가이드가 가이드를 근거로 삼는 순환입니다. 확정의 출처는 `docs/adr/` 뿐입니다 |

### 1-b. 지적하지 않을 것

- **스타일, 포맷, import 정렬, 타입** - ruff 와 mypy 소관입니다. 결정론적으로 이미 판정됩니다.
- **줄바꿈** - 이미 다른 이유로 편집 중인 문단이 아니면 넘어갑니다.
  재정렬만 하는 변경은 `AGENTS.md` 가 금지합니다.
- **문서의 표현이나 오타** - 의미가 바뀌는 경우가 아니면 넘어갑니다.
- **취향에 속하는 설계 선택** - 규약 위반이 아니라면 지적이 아니라 질문으로 남기세요.

## 2. 대원칙: 결론부터 씁니다

리뷰는 두 종류의 독자를 동시에 상대합니다.
**코드를 열지 않는 PM 과 QA**, 그리고 **정확히 무엇을 고칠지 알아야 하는 작성자**입니다.
아래 세 원칙은 그 둘을 층으로 분리해 양쪽이 다 살아남게 합니다.

### 2-a. 모든 제목이 판정을 담아야 합니다

질문형 제목은 정보를 담지 못합니다.

- 나쁨: `### 그래서 실제로 무슨 일이 벌어지나`
- 좋음: `### 재난 API 가 느려지면 알림이 아예 나가지 않습니다`

### 2-b. 제목 옆에 처리 등급을 붙입니다

아래 네 라벨을 **글자 그대로** 씁니다.

| 라벨 | 뜻 |
|---|---|
| `머지 전 필수` | 이 PR 을 머지하기 전에 고쳐야 합니다 |
| `이 PR에서 권장` | 지금 고치는 편이 낫지만 머지를 막지는 않습니다 |
| `후속 과제` | 별도 이슈로 넘깁니다. 이 PR 에서 처리하지 않습니다 |
| `참고, 조치 불필요` | 맥락 공유입니다. 작성자가 할 일은 없습니다 |

등급을 맨 아래 요약에 몰아 두지 마세요.
위에서 아래로 읽는 사람은 각 항목이 자기를 막는지를 **그 자리에서** 알아야 합니다.
(Conventional Comments 와 같은 발상입니다.)

## 3. 첫 문단은 코드를 한 줄도 열지 않고 읽혀야 합니다

- **첫 문단만으로 누가, 언제, 어떻게 피해를 보는지**가 답해져야 합니다.
  "비전공자도 이해할 수 있게"는 자기 판단에 따라 흔들리지만,
  "코드를 열지 않고 읽히는가"는 실제로 검사할 수 있습니다.
- 기술적으로 무엇이 틀렸는지가 아니라 **실무에서 무엇이 잘못되는지**로 시작합니다.
  이 프로젝트에서는 재난 상황의 사용자가 그 실무입니다.
- **언제 깨지는지**와 **왜 지금은 멀쩡해 보이는지**를 함께 적습니다.
  후자는 오늘 무증상인 결함일수록 중요하고,
  이 저장소는 외부 의존이 전부 스텁이라 특히 그렇습니다.
- **근거와 수정 문단은 정확성을 우선합니다.**
  파일과 줄 번호를 정확히 인용하되, 처음 나오는 용어는 그 자리에서 한 문장으로 풀어 씁니다.
  읽기 쉽게 하려고 위치를 흐리면 리뷰가 수필이 되고 작성자에게는 조치할 것이 남지 않습니다.
- 코드 인용은 근거로 유지하되 앞뒤를 평문으로 감쌉니다.

## 4. 수정이 작을 때만 고친 코드를 줍니다

- 완성된 수정본은 **한 파일, 몇 줄, 판단이 개입하지 않을 때만** 제시합니다.
- **판단이 개입하면(설계나 규약 선택) 코드가 아니라 선택지를 제시합니다.**
  남의 설계 결정을 패치로 건네는 것은 리뷰가 아니라 인수입니다.
- **검증 여부를 몇 마디로 표기합니다.** 아래 라벨을 글자 그대로 씁니다.
  - `로컬에서 확인함`
  - `미검증, 눈으로만 확인`

  코드로 제시된 수정은 검증된 것처럼 읽히므로,
  확인한 주장과 확인하지 않은 주장에 같은 확신을 주어서는 안 됩니다.

### 4-a. 신뢰도를 라벨로 밝힙니다

검증 라벨이 **수정안**에 붙는 표기라면, 신뢰도는 **주장**에 붙는 표기입니다.
아래 네 라벨을 글자 그대로 씁니다.

| 라벨 | 언제 | 예 |
|---|---|---|
| `확실한 사실` | 문서, 코드, 실행 결과로 그 자리에서 확인됨 | 계약 파일에 해당 필드가 없습니다 |
| `높은 신뢰` | 직접 확인하진 않았지만 근거가 여러 개이고 반례를 못 찾음 | 이 설정이면 CI 에서도 같은 결과일 것입니다 |
| `추정` | 정황 근거만 있음. 확인하면 뒤집힐 수 있음 | 타임아웃 원인은 카카오맵 쪽으로 보입니다 |
| `불확실` | 근거 없이 제기하는 가능성. 작성자에게 확인을 요청하는 것 | 행정동 코드 갱신 때 매칭이 깨질 수 있습니다 |

라벨이 없는 문장은 `확실한 사실` 로 읽힙니다.
그래서 **모르는 것에 라벨을 붙이지 않는 쪽이 틀린 라벨보다 나쁩니다.**
리뷰어의 추측이 사실로 읽히면 작성자가 멀쩡한 코드를 고칩니다.

`추정` 과 `불확실` 항목에는 처리 등급을 `머지 전 필수` 로 달지 않습니다.
확인이 먼저입니다.

## 5. 작성 예시

아래는 서식 예시이며 실제 결함 보고가 아닙니다.

> ### 사용자 좌표가 애플리케이션 로그에 남습니다 - `머지 전 필수`
>
> 알림을 연 사용자의 정확한 좌표가 서버 로그에 평문으로 쌓입니다.
> 로그는 VM 디스크에 남고 백업에도 함께 들어가므로,
> "위치는 세션 안에서만 쓰고 저장하지 않는다"는 약속이 사실이 아니게 됩니다.
> 지금 드러나지 않는 이유는 스텁이 늘 같은 좌표를 돌려주기 때문이고,
> 실제 브라우저 좌표가 들어오는 날부터 개인정보가 쌓이기 시작합니다.
>
> `apps/backend/src/backend_core/matching.py:112` 에서 매칭 결과를 통째로 로깅하는데,
> 그 payload 에 `lat` 과 `lon` 이 들어 있습니다.
> 이 저장소에서 위치는 **알림 열람 시점 1회 조회, 세션 스코프, 비영속**이 하드 제약입니다
> ([AGENTS.md](../../AGENTS.md) `Non-negotiable design constraints`).
>
> 수정은 한 곳입니다. `미검증, 눈으로만 확인`:
>
> ```python
> # log the matched district and shelter count, never raw coordinates
> logger.info("matched: dong=%s shelters=%d", result.dong_code, len(result.shelters))
> ```
>
> **좌표가 필요한 디버깅은 로그가 아니라 테스트에서 하세요.**
> 로그 레벨을 낮추는 것으로는 해결되지 않습니다. 운영에서 한 번 켜지면 그대로 쌓입니다.

## 6. 팀 메신저로 공유할 때

**리뷰 본문은 PR 에 남기고, 메시지에는 판정과 링크만 보냅니다.**
서식(2 ~ 4절)은 PR 코멘트에 적용되는 것이고,
메신저에서는 [메신저_규약.md](메신저_규약.md) 가 우선합니다.

- 첫 줄: 어느 PR 인가, 가장 높은 처리 등급이 무엇인가, 몇 건인가.
- 둘째 줄: 링크. 근거와 `file:line` 은 링크 뒤에 둡니다.
- 5줄을 넘겼다면 메시지가 아니라 PR 코멘트에 들어갈 내용입니다.

```
#71 리뷰 남겼습니다. 머지 전 필수 1건(좌표가 로그에 남습니다), 나머지 2건은 후속 과제입니다.
https://github.com/team-savers/savers-project/pull/71#pullrequestreview-...
```

리뷰 내용을 메신저에 옮겨 적으면 PR 과 메신저가 각각 다른 버전의 리뷰를 갖게 되고,
작성자가 어느 쪽에 답해야 하는지 모르게 됩니다.
`Resolve conversation` 이력도 남지 않습니다.
