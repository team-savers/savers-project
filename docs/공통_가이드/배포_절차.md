# 배포 절차 — 단일 VM에 백엔드·AI 엔진 올리기

이 문서는 **AWS 서울 리전 단일 VM**에 `apps/backend`와 `apps/ai-engine`을 올리는 절차입니다
([ADR-0003](../adr/0003-single-vm-seoul.md)).
프론트엔드는 여기 없습니다 — 정적 산출물이라 VM 밖 정적 호스팅으로 나갑니다
([ADR-0008](../adr/0008-frontend-static-hosting.md)).
**기동 절차가 둘이라는 뜻**이고, 그 사실이 이 문서 전체의 전제입니다.

담당은 백엔드/인프라입니다.
로컬 개발 절차는 [환경_세팅_가이드.md](환경_세팅_가이드.md), 컨테이너 구성은
[infra/README.md](../../infra/README.md)를 보세요.

## 왜 리허설부터 하는가

**본 VM을 만들기 전에 최소 사양 VM으로 절차를 한 번 관통합니다.**

배포 절차의 오류는 대부분 코드가 아니라 절차 자체에 있습니다.
보안그룹 포트, 키페어, 인증서 발급 조건, CORS 값 —
전부 "해 보기 전에는 맞는지 알 수 없는" 항목이고,
본 VM에서 처음 부딪히면 그 VM의 상태가 실패 시도로 더럽혀집니다.
특히 인증서는 **Let's Encrypt가 같은 도메인 조합에 주당 5회 실패 한도**를 걸어 두어,
시행착오를 본 VM에서 하면 정작 시연 직전에 발급이 막힐 수 있습니다.

리허설 VM은 `t3.micro`면 충분합니다.
**서비스를 상시 구동하기에는 메모리가 모자라지만**(1GB), 확인하려는 것은
"절차가 맞는가"이지 "서비스가 잘 도는가"가 아닙니다.
1~2시간 쓰고 삭제하면 실비는 100원 미만이라
[비용_산정.md](비용_산정.md)의 단일 VM 예산을 건드리지 않습니다.

> ⚠️ 리허설 VM은 **반드시 삭제(terminate)** 합니다.
> 남겨서 스테이징으로 쓰기로 한다면 그건 별개 결정이고,
> 인스턴스 비용이 이중으로 발생하므로 `비용_산정.md` D-1을 함께 고쳐야 합니다.

## 0. 준비물

### 0-1. 계정과 키

| 항목 | 확인 |
|---|---|
| AWS 계정 + 결제수단 | [외부_승인.md](외부_승인.md) D절 |
| 리전 | **ap-northeast-2 (서울)** 고정 — 국내 외부 API 왕복 지연 때문입니다(ADR-0003) |
| 키페어 | 미리 생성해 `.pem`을 안전한 곳에 둘 것. ⚠️ 저장소에 두지 마세요(`.gitignore`가 `*.pem`을 막지만 믿지 말 것) |
| `infra/.env` 값 | 아래 3절에서 채웁니다 |

### 0-2. 프론트엔드를 먼저 배포해 오리진을 확정한다

**VM보다 이게 먼저입니다.**
백엔드의 `SAVERS_CORS_ALLOW_ORIGINS`에 넣을 값이 프론트의 배포 오리진이라,
프론트가 한 번도 배포된 적 없으면 1-3에서 채울 값이 없습니다.

반대 방향 의존(`VITE_API_BASE_URL`은 VM 호스트명이 필요)은 2-3에서 풀립니다.
Vercel은 첫 배포 시점에 고정 프로덕션 도메인을 확정하므로,
프론트를 먼저 올려도 백엔드 주소를 몰라 곤란해지지 않습니다.
이 단계에서는 환경변수를 하나도 넣지 않습니다 —
프론트 기본값이 목 데이터라 백엔드 없이도 화면이 뜹니다.

배포는 Vercel 대시보드에서 합니다. 설정할 항목은 넷뿐입니다.

| 항목 | 값 | 틀리면 |
|---|---|---|
| GitHub 연동 | `team-savers/savers-project` | 조직 레포라 Vercel GitHub App에 **조직 관리자(owner) 승인**이 필요합니다. 승인 전에는 프로젝트 목록에 레포가 아예 안 보입니다 |
| Root Directory | `apps/frontend` | 모노레포라 비워 두면 최상위에서 빌드를 시도하다 실패합니다 |
| Framework·Build Command·Output Directory | **비워 둘 것** | [apps/frontend/vercel.json](../../apps/frontend/vercel.json)에 이미 있습니다. 대시보드에도 채우면 같은 설정이 두 곳이 됩니다 |
| Production Branch | `main` | |

⚠️ **Vercel 무료(Hobby) 플랜은 멤버 초대가 없습니다.**
프로젝트를 만든 계정 소유자만 대시보드를 조작할 수 있고,
2-3의 환경변수 주입도 같은 사람이 해야 합니다.
계정을 누가 갖고 있는지가 곧 일정이므로 이 단계 전에 정해 두세요.

배포가 끝나면 **프로덕션 URL**을 받습니다. 현재 값은 이렇습니다.

```
https://savers-project.vercel.app
```

> ⚠️ **끝의 슬래시를 빼고 적으세요.**
> 브라우저가 보내는 `Origin` 헤더에는 경로가 붙지 않아
> `https://...app/`과 `https://...app`은 다른 출처로 취급됩니다.
> 그리고 이 실패는 **서버 로그에 아무것도 남기지 않습니다** — 브라우저만 조용히 응답을 버립니다.
>
> ⚠️ **프리뷰 도메인(`savers-project-git-<브랜치>.vercel.app`)은 쓰지 마세요.**
> 커밋마다 바뀌므로 허용 목록에 넣어도 다음 커밋에서 무의미해집니다(ADR-0008).

배포 직후 라우팅이 살아 있는지만 확인합니다.
첫 화면만 뜨고 나머지가 404면 Root Directory가 잘못 잡힌 것입니다 —
`vercel.json`을 못 읽어 rewrite 규칙이 적용되지 않은 상태입니다.

```bash
for p in / /ops /join; do
  curl -s -o /dev/null -w "$p %{http_code}\n" https://savers-project.vercel.app$p
done
#   셋 다 200
```

> 이 단계에서 **지도와 웹푸시는 꺼진 채로 보이는 것이 정상입니다.**
> 카카오맵 키와 FCM 설정을 아직 넣지 않았기 때문이고,
> 키가 없으면 해당 기능만 비활성화되고 나머지 화면은 그대로 렌더됩니다.
> 카카오맵은 등록된 도메인에서만 동작하므로,
> 이 URL을 카카오 디벨로퍼스 콘솔의 허용 도메인에 추가해야 지도가 뜹니다.

## 1. 리허설 (t3.micro, 1회용)

목적은 **절차 검증**입니다. 아래 8개가 전부 통과하면 삭제합니다.

### 1-1. 인스턴스 생성

- AMI: Ubuntu 24.04 LTS (x86_64)
- 타입: `t3.micro`
- 스토리지: gp3 20GB
- 보안그룹 인바운드:

| 포트 | 소스 | 이유 |
|---|---|---|
| 22 | **내 IP만** | SSH. 0.0.0.0/0으로 열지 마세요 |
| 80 | 0.0.0.0/0 | Let's Encrypt HTTP-01 검증에 필요 |
| 443 | 0.0.0.0/0 | 실제 서비스 트래픽 |

⚠️ **8000·8100은 열지 않습니다.** 백엔드는 `127.0.0.1`에만 바인딩되고
Caddy가 compose 네트워크로 직접 닿습니다.
ai-engine은 인증이 없고 취약계층 프로필을 받으므로 외부 노출 자체가 사고입니다
([ADR-0006](../adr/0006-generation-contract.md), 이슈 #25).

### 1-2. Docker 설치

```bash
ssh -i <키페어>.pem ubuntu@<공인IP>

sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2 git
sudo usermod -aG docker ubuntu
exit                     # 그룹 반영을 위해 재접속
```

### 1-3. 저장소 클론 + 환경파일

```bash
git clone https://github.com/team-savers/savers-project.git
cd savers-project
cp infra/.env.example infra/.env
```

`infra/.env`에서 채울 값은 세 개입니다.
`SAVERS_CORS_ALLOW_ORIGINS`와 `SAVERS_PUBLIC_BASE_URL`은 0-2에서 확정한 오리진이라 이미 정해져 있고,
새로 정하는 것은 `SAVERS_PUBLIC_HOST` 하나뿐입니다.
이 값은 **이 VM의 공인 IP에서 만들어야 하므로 손으로 적지 말고 조회해서 씁니다.**

아래를 VM 안에서 그대로 실행하면 세 값 모두 조회부터 파일 반영까지 끝납니다.

```bash
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
IP=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4)
ORIGIN=https://savers-project.vercel.app     # 0-2에서 확정한 프론트 오리진

sed -i "s|^SAVERS_PUBLIC_HOST=.*|SAVERS_PUBLIC_HOST=${IP//./-}.sslip.io|" infra/.env
sed -i "s|^SAVERS_CORS_ALLOW_ORIGINS=.*|SAVERS_CORS_ALLOW_ORIGINS=$ORIGIN|" infra/.env
sed -i "s|^SAVERS_PUBLIC_BASE_URL=.*|SAVERS_PUBLIC_BASE_URL=$ORIGIN|" infra/.env

grep -E '^SAVERS_(PUBLIC_HOST|CORS_ALLOW_ORIGINS|PUBLIC_BASE_URL)=' infra/.env
#   SAVERS_PUBLIC_BASE_URL=https://savers-project.vercel.app
#   SAVERS_CORS_ALLOW_ORIGINS=https://savers-project.vercel.app
#   SAVERS_PUBLIC_HOST=<이 VM의 공인 IP>.sslip.io
```

> ⚠️ **세 값을 셸에 그대로 입력하는 것으로는 안 됩니다.**
> `SAVERS_CORS_ALLOW_ORIGINS=...`를 터미널에 치면 셸 변수만 잠깐 생기고
> `infra/.env`는 비어 있는 채로 남는데, compose가 읽는 것은 파일입니다.
> 편집기로 직접 채워도 되지만, 그 경우에도 위 `grep`으로 파일에 들어갔는지 확인하세요.

> ⚠️ **예시 호스트명을 그대로 복사하지 마세요.**
> sslip.io는 호스트명에 적힌 IP로 그대로 응답하므로,
> 남의 IP가 박힌 호스트명은 **남의 서버로 연결을 시도합니다.**
> 증상은 CORS 실패가 아니라 `curl`이 응답 없이 멈추는 것이고,
> 그동안 Caddy는 받을 수 없는 인증서를 계속 재시도합니다.
> 이 절차에서 실제로 한 번 겪은 실수입니다.

**파일을 고쳤으면 셸에도 반영해야 합니다.**
`infra/.env`는 docker compose가 읽는 파일이지 셸이 읽는 파일이 아닙니다.
1-5의 검증 명령들이 `$SAVERS_PUBLIC_HOST`를 쓰므로 이 단계를 빠뜨리면 검증이 전부 헛돕니다.

```bash
set -a; . infra/.env; set +a
echo "[$SAVERS_PUBLIC_HOST]"     # 대괄호 안이 비어 있으면 안 됩니다
```

> **sslip.io가 무엇인가.** 어떤 호스트명이든 그 안에 들어 있는 IP로 응답하는 공개 DNS입니다.
> 도메인을 사지 않고도 **공인 호스트명**이 생기므로 Let's Encrypt 인증서를 받을 수 있습니다.
> 대가는 URL이 예쁘지 않다는 것과, **공인 IP가 바뀌면 호스트명도 바뀐다**는 것입니다.
> 그래서 아래 2-1에서 본 VM에는 탄력적 IP를 붙입니다.

### 1-4. 기동

```bash
docker compose -f infra/docker-compose.yml --profile tls up -d --build
docker compose -f infra/docker-compose.yml --profile tls ps
```

⚠️ `t3.micro`에서는 빌드가 메모리 부족으로 실패할 수 있습니다.
**그것도 리허설의 정상적인 결과입니다** — 확인하려는 것은 그 앞 단계(네트워크·권한·환경변수)입니다.
빌드가 막히면 이미지 빌드는 본 VM에서 하고, 아래 검증 중 가능한 것까지만 확인합니다.

### 1-5. 검증 8개

**한눈에 보는 판정표.** 여덟 개가 모두 통과해야 리허설이 끝납니다.

| # | 무엇을 증명하는가 | 통과 |
|---|---|---|
| ① | 세 컨테이너가 떠 있다 | `Up` 3줄, backend·ai-engine은 `(healthy)` |
| ② | 백엔드·ai-engine이 외부에 안 열려 있다 | 8000·8100 **모두** 연결 실패 (`timed out`) |
| ③ | TLS 인증서가 발급됐다 | `certificate obtained successfully` + `HTTP/2 405` |
| ④ | 허용 출처에 CORS 헤더가 붙는다 | `access-control-allow-origin: <프론트 URL>` |
| ⑤ | 모르는 출처에는 안 붙는다 | `정상: 허용되지 않음` |
| ⑥ | DELETE 프리플라이트가 통과한다 | `access-control-allow-methods`에 `DELETE` |
| ⑦ | 압축이 걸린다 | `content-encoding: gzip` |
| ⑧ | `/internal/*`이 외부에 안 열려 있다 | `404` |

⚠️ **②와 ⑤는 "출력이 없는 것"이 통과 조건입니다.**
그래서 명령이 엉뚱한 곳을 때려도 똑같이 통과한 것처럼 보입니다.
⓪을 건너뛰면 이 둘은 아무것도 검사하지 않은 채 초록으로 보입니다.

#### ⓪ 준비 — 건너뛰면 아래가 전부 무의미해집니다

`infra/.env`는 **docker compose가 읽는 파일이지 셸이 읽는 파일이 아닙니다.**
아래 검증은 전부 셸 변수를 쓰므로 먼저 읽어 들여야 합니다.

```bash
set -a; . infra/.env; set +a
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
IP=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4)

echo "호스트명 [$SAVERS_PUBLIC_HOST]"
echo "공인IP   [$IP]"
```

> **통과:** 대괄호 안이 **둘 다 비어 있지 않아야** 합니다.
> ```
> 호스트명 [3-35-233-232.sslip.io]
> 공인IP   [3.35.233.232]
> ```
> 하나라도 비어 있으면 여기서 멈추고 1-3을 다시 하세요.
> 빈 채로 진행하면 URL이 `https:///...`로 펼쳐지는데,
> `curl -s`가 오류 메시지까지 숨겨서 **"CORS 실패"와 똑같은 빈 화면**이 됩니다.

#### ① 컨테이너가 살아 있는가

```bash
docker compose -f infra/docker-compose.yml --profile tls ps
```

> **통과:** `backend` · `ai-engine` · `caddy` 세 줄이 모두 `Up`.
> 앞의 둘은 `(healthy)`까지 붙어야 합니다.

#### ② 백엔드·ai-engine이 외부에 직접 노출되지 않았는가

```bash
curl --max-time 5 "http://$IP:8000/health" || echo "정상: 8000 안 열림"
curl --max-time 5 "http://$IP:8100/health" || echo "정상: 8100 안 열림"
```

> **통과:** 두 줄 모두 연결이 **실패해야** 정상입니다.
> ```
> curl: (28) Connection timed out after 5002 milliseconds
> 정상: 8000 안 열림
> curl: (28) Connection timed out after 5002 milliseconds
> 정상: 8100 안 열림
> ```
> JSON이 돌아오면 그 포트가 열려 있다는 뜻이라 **즉시 멈추고 보안그룹을 고쳐야 합니다.**
> ai-engine은 인증 없이 취약계층 프로필을 받으므로(ADR-0006) 노출 자체가 사고입니다.
>
> ⚠️ 8100을 8000과 같이 찔러 보는 이유: 이 항목이 위험 근거로 드는 것은 ai-engine인데
> 정작 확인하는 포트는 백엔드였습니다([이슈 #25](https://github.com/team-savers/savers-project/issues/25)
> DoD 1). 두 포트는 `docker-compose.yml`의 서로 다른 서비스 블록에 있어
> 한쪽 바인딩이 바뀌어도 다른 쪽 검증은 그대로 통과합니다.

#### ③ TLS 인증서가 발급됐는가

```bash
docker compose -f infra/docker-compose.yml --profile tls logs caddy \
  | grep -i "certificate obtained"
curl -sI "https://$SAVERS_PUBLIC_HOST/health" | head -1
```

> **통과:**
> ```
> caddy-1  | {"level":"info", ... "msg":"certificate obtained successfully", ...}
> HTTP/2 405
> ```
> **405가 맞습니다.** `curl -I`는 HEAD를 보내는데 `/health`는 GET 전용이라 405를 돌려줍니다.
> Starlette의 `Route`는 GET 라우트에 HEAD를 자동으로 얹지만
> FastAPI의 `APIRoute`는 그러지 않아서(`self.methods = {m.upper() for m in methods}`),
> `@app.get`으로 선언한 경로는 HEAD를 받지 않습니다.
> 여기서 확인하는 것은 상태 코드가 아니라 **HTTPS 응답이 왔다는 사실**입니다.
>
> 첫 줄이 비어 있으면 아직 발급 중일 수 있습니다. 수십 초까지 걸리므로 붙어서 기다리세요.
> ```bash
> docker compose -f infra/docker-compose.yml --profile tls logs -f caddy
> ```

#### ④ 허용 출처에 CORS 헤더가 돌아오는가

```bash
curl -sI -H "Origin: https://savers-project.vercel.app" \
  "https://$SAVERS_PUBLIC_HOST/health" | grep -i access-control-allow-origin
```

> **통과:**
> ```
> access-control-allow-origin: https://savers-project.vercel.app
> ```
> 비어 있으면 허용 목록과 실제 출처가 다른 것입니다.
> **끝의 슬래시, `www.` 유무, `http`/`https`가 하나라도 다르면 다른 출처입니다.**

#### ⑤ 모르는 출처에는 헤더가 없는가

```bash
curl -sI -H "Origin: https://evil.example.com" \
  "https://$SAVERS_PUBLIC_HOST/health" | grep -i access-control-allow-origin \
  || echo "정상: 허용되지 않음"
```

> **통과:**
> ```
> 정상: 허용되지 않음
> ```
> 헤더가 찍히면 허용 목록이 너무 넓습니다(와일드카드가 들어갔을 가능성).

#### ⑥ DELETE 프리플라이트가 통과하는가

```bash
curl -si -X OPTIONS "https://$SAVERS_PUBLIC_HOST/v1/devices" \
  -H "Origin: https://savers-project.vercel.app" \
  -H "Access-Control-Request-Method: DELETE" \
  -H "Access-Control-Request-Headers: Content-Type" \
  | grep -i access-control-allow-methods
```

> **통과:** 목록에 `DELETE`가 있어야 합니다.
> ```
> access-control-allow-methods: GET, POST, DELETE, OPTIONS
> ```

**①~⑤가 전부 단순 GET이라 프리플라이트를 한 번도 발생시키지 않기 때문에** 이 항목이 따로 있습니다.
`DELETE /v1/devices`(분실 단말·복지관 공용 단말·동의 철회 시 기기 등록 해제)는
CORS "simple method"가 아니라 브라우저가 항상 `OPTIONS`를 먼저 보내는데,
허용 메서드 목록에 DELETE가 없으면 브라우저가 실제 요청을 아예 보내지 않습니다.
로컬은 동일 출처라 CORS가 개입하지 않고 `curl`은 프리플라이트를 보내지 않으므로,
이 결함은 **배포된 프론트에서만** 드러납니다(#49에서 실제로 한 번 났습니다).

#### ⑦ 압축이 실제로 걸리는가

```bash
curl -s -o /dev/null -D - -H "Accept-Encoding: gzip" \
  "https://$SAVERS_PUBLIC_HOST/openapi.json" | grep -i content-encoding
```

> **통과:**
> ```
> content-encoding: gzip
> ```

⚠️ **`/health`로 검사하면 반드시 실패합니다.** 두 가지 이유가 겹칩니다.
`/health` 응답은 15바이트뿐이라 Caddy `encode`의 압축 하한(기본 512바이트)에 못 미치고,
`-I`는 HEAD라 압축할 본문 자체가 없습니다.
그래서 본문이 큰 `/openapi.json`(약 17KB)에 GET으로 물어봅니다.

이 항목이 있는 이유는 [infra/Caddyfile](../../infra/Caddyfile)의 `encode zstd gzip`이
실제로 동작하는지 확인하기 위해서입니다.
응답 크기는 알림 도달 시간에 그대로 들어가고,
대상 사용자의 기본 조건이 구형 단말과 혼잡 회선이라 압축이 빠지면 KPI에 직접 영향을 줍니다.

#### ⑧ `/internal/*`이 외부에서 닫혀 있는가

```bash
curl -s -o /dev/null -w "internal %{http_code}\n" \
  -X POST "https://$SAVERS_PUBLIC_HOST/internal/alerts/dispatch"
curl -s -o /dev/null -w "health   %{http_code}\n" \
  "https://$SAVERS_PUBLIC_HOST/health"
```

> **통과:**
> ```
> internal 404
> health   200
> ```

⚠️ **②를 통과했다고 이 항목이 자동으로 통과하지는 않습니다.**
②는 8000·8100이 `127.0.0.1` 바인딩이라 **그 포트로는** 안 열린다는 것만 보는데,
같은 엔드포인트가 Caddy를 거쳐 **443으로는 그대로 열릴 수 있습니다.**
실제로 리허설에서 `POST https://<호스트명>/internal/alerts/dispatch`가 200을 돌려줬고,
그것이 [infra/Caddyfile](../../infra/Caddyfile)에 `handle /internal/*` 차단을 넣은 계기입니다(#25).

**`health`를 같이 보는 것이 이 항목의 절반입니다.**
차단이 과하게 걸려 일반 경로까지 막히면 `internal 404`만으로는 구분이 안 됩니다.
둘을 한 번에 봐야 "`/internal`만 끊겼다"가 증명됩니다.

이 엔드포인트에는 인증이 없어, 열려 있으면 **외부 누구나 재난 알림 발송을 트리거**할 수 있습니다.
지금은 발송기가 기록만 하는 스텁이라 피해가 없지만,
FCM 자격증명이 VM에 들어오는 순간 같은 경로가 실제 푸시 발송기가 됩니다.
→ [ADR-0007](../adr/0007-walking-skeleton.md) "부정 / 완화" 표의 각주

### 1-6. 삭제

```bash
docker compose -f infra/docker-compose.yml --profile tls down
```

콘솔에서 인스턴스를 **종료(terminate)** 하고, 붙여 둔 EBS·탄력적 IP가 남지 않았는지 확인합니다.
**탄력적 IP는 인스턴스가 없어도 요금이 붙습니다.**

## 2. 본 VM

리허설에서 걸린 것을 절차에 반영한 뒤 진행합니다.

### 2-1. 인스턴스

- 타입: **`t3.medium`(2vCPU/4GB)** 기준.
  임베딩을 로컬 모델로 돌리기로 하면 `t3.large`가 필요합니다 —
  근거와 비용 비교는 [비용_산정.md](비용_산정.md) D-1에 있습니다.
- 스토리지: gp3 30GB
- **탄력적 IP를 할당해 붙입니다.** 인스턴스를 재시작해도 IP가 유지돼야
  sslip.io 호스트명과 FCM·카카오 허용 도메인 등록이 살아 있습니다.
- 보안그룹은 1-1과 동일

> ⚠️ **탄력적 IP는 2-2 기동 *전에* 붙이세요.**
> 인스턴스를 만들면 임시 공인 IP가 자동으로 붙는데,
> **탄력적 IP를 나중에 붙이면 그 임시 IP가 교체됩니다.**
> 이미 기동한 뒤라면 Caddy는 임시 IP로 만든 sslip.io 호스트명으로 인증서를 받아 둔 상태이고,
> 그 호스트명은 교체와 동시에 이 서버를 가리키지 않게 됩니다.
> TLS 설정이 잘못된 것이 아니라 **인증서에 적힌 이름과 서버 주소가 어긋난 상태**입니다.
>
> 순서를 놓쳤다면 1-3의 조회·반영 명령을 다시 돌려 호스트명을 갱신하고
> `up -d`로 재생성하면 새 인증서가 발급됩니다.
> 새 호스트명이라 Let's Encrypt 한도는 새로 시작하고,
> 기존 인증서는 `caddy_data`에 남지만 무해하므로 **볼륨을 지우지 마세요.**
> 본 VM 구축에서 실제로 겪은 순서 실수입니다.

### 2-2. 기동

1-2 ~ 1-4와 같습니다. `infra/.env`의 `SAVERS_PUBLIC_HOST`만 **본 VM의 탄력적 IP** 기준으로 바꿉니다.

### 2-3. 프론트 쪽 설정

백엔드 주소가 정해졌으므로 정적 호스팅의 환경변수를 맞춥니다.

```
VITE_API_BASE_URL=https://<SAVERS_PUBLIC_HOST>
```

기본값이 빈 문자열(= 동일 출처)이라 **설정하지 않으면 프론트가 자기 자신을 호출합니다**
(ADR-0008). 배포에서는 반드시 절대 URL이어야 합니다.

### 2-4. 검증

1-5의 8개를 그대로 반복하고, 여기에 관통 1회를 더합니다.

```bash
# VM 안에서 (외부에 열려 있지 않으므로 SSH 안에서 호출합니다)
curl -X POST localhost:8000/internal/alerts/dispatch
```

`messageMode`가 `grounded`면 ai-engine까지 살아 있는 것이고,
`official_fallback`이면 엔진에 닿지 못한 것입니다 —
200이 떨어져도 그건 **저하 경로**이지 성공이 아닙니다
([워킹_스켈레톤_점검.md](워킹_스켈레톤_점검.md) §14).

그다음 실기기에서 프론트 배포 URL을 열어 웹푸시 수신까지 확인합니다.
이것이 [ADR-0005](../adr/0005-webpush-primary-channel.md)가 대기 중이던 실기기 검증입니다.

## 4. 자주 걸리는 것

| 증상 | 원인 |
|---|---|
| Caddy가 `unrecognized global option: encode`로 죽음 | `SAVERS_PUBLIC_HOST`가 비어 있음. 사이트 주소가 없어 Caddyfile 전체가 전역 옵션 블록으로 해석됩니다 |
| 인증서 발급 실패 | 80 포트가 막혀 있거나(보안그룹), 호스트명이 이 VM의 IP를 가리키지 않음 |
| 발급은 됐는데 HTTPS가 안 붙음 | 인증서 로그의 `identifier`와 현재 공인 IP를 대조하세요. 다르면 기동 후에 탄력적 IP를 붙여 임시 IP가 교체된 것입니다(2-1 경고). 호스트명을 갱신하고 `up -d` |
| 인증서 재발급이 계속 실패 | Let's Encrypt 주당 실패 한도 소진. 며칠 기다리거나 호스트명을 바꿔야 합니다 — `caddy_data` 볼륨을 지우지 마세요 |
| 검증 명령이 아무 출력도 없이 끝남 | `$SAVERS_PUBLIC_HOST`가 셸에 없어 URL이 `https:///...`로 펼쳐진 것. `curl -s`가 오류까지 숨겨 CORS 실패와 구분되지 않습니다. `echo "[$SAVERS_PUBLIC_HOST]"`로 먼저 확인 |
| `curl`이 응답 없이 멈춤 | 호스트명이 이 VM이 아닌 IP를 가리킴(예시 값을 그대로 복사). 1-3의 조회 명령으로 다시 만드세요 |
| `.env`를 고쳤는데 반영 안 됨 | `docker compose restart`는 환경변수를 다시 읽지 않습니다. `up -d`로 컨테이너를 재생성하세요 — 출력이 `Running`이면 안 바뀐 것이고 `Recreated`여야 합니다 |
| 브라우저 콘솔에 CORS 오류 | 허용 목록과 실제 출처 불일치(슬래시·`www.`·스킴). `curl -I -H "Origin: ..."`로 먼저 확인 |
| 프론트가 API를 안 부르고 자기 자신을 부름 | `VITE_API_BASE_URL` 미설정 |
| `docker compose down -v` 이후 HTTPS가 안 됨 | `-v`가 `caddy_data`(인증서)를 지웠습니다. 위 재발급 한도 항목 참고 |

## 5. 아직 없는 것

- **관리형 이중화** — ALB·ASG·RDS Multi-AZ는 예선 범위에서 유보했습니다(ADR-0003).
  전환 경로만 문서로 남긴 상태입니다.
- **프로비저닝 자동화(IaC)** — 지금은 콘솔 수작업입니다.
  리허설로 절차가 굳으면 스크립트화 대상입니다.
- **세션 영속화** — 세션은 프로세스 메모리에 있어 **재시작하면 살아 있던 알림 링크가 전부 무효**입니다.
  시연 중 `docker compose restart`를 하지 마세요.
- **FCM 실발송** — 현재 발송기는 기록만 합니다(`RecordingDispatcher`).
  Admin SDK 자격증명이 VM에 들어오는 시점에 교체됩니다.
