# 서버 운영 — 팀원 접속과 관리

[배포_절차.md](배포_절차.md)가 VM을 **세우는** 절차라면, 이 문서는 세워진 뒤
**누가 어떻게 들어가고 무엇을 해도 되는지**를 정합니다.

담당은 백엔드/인프라(김도혁)이고, Tech Lead(신호정)가 백업입니다.

> 접속 방식(SSM)과 권한 등급은 [ADR-0009](../adr/0009-ssm-session-manager.md)에 기록돼 있습니다.
> 이 ADR은 아직 **제안(Proposed)** 상태이므로, 승인 전까지 1·2절 내용은 **검토 중**입니다.
> 절차 자체는 그대로 실행 가능하지만, 등급 구성에 이견이 있으면 ADR에 달아 주세요.

## 지금 떠 있는 것

| 항목 | 값 |
|---|---|
| 리전·타입 | ap-northeast-2 (서울), `t3.medium` |
| 공개 주소 | `https://54-116-13-82.sslip.io` |
| 탄력적 IP | `54.116.13.82` (고정 — 재시작해도 유지됩니다) |
| 컨테이너 | `backend` · `ai-engine` · `caddy` |
| 프론트엔드 | Vercel(`https://savers-project.vercel.app`) — **이 VM에 없습니다**(ADR-0008) |

프론트가 VM 밖에 있다는 것이 이 문서 전체의 전제입니다.
화면이 안 뜨는 문제와 API가 안 되는 문제는 **서로 다른 곳을 봐야 합니다.**

## 1. 권한 등급 — 대부분은 셸이 필요 없습니다

근거: [ADR-0009](../adr/0009-ssm-session-manager.md) (제안 상태 — 위 안내 참고).

| 등급 | 대상 | 할 수 있는 것 | 필요한 것 |
|---|---|---|---|
| 상태 확인 | **팀 전원** | 서버가 살아 있는지, API가 응답하는지 | 없음 (공개 URL) |
| 셸 접속 | **김도혁 · 신호정** | 로그 열람, 컨테이너 재기동, 설정 변경 | AWS IAM 사용자 + SSM 권한 |

**셸 접근자를 둘로 좁힌 이유는 VM 안에 비공개 키가 있기 때문입니다.**
`infra/.env`에는 CLOVA API 키를 비롯한 값이 평문으로 들어 있고,
셸에 들어갈 수 있는 사람은 그것을 모두 볼 수 있습니다.
접근자 수가 곧 유출 경로의 수입니다.

로그가 필요한 팀원은 담당자에게 요청하세요.
이 프로젝트 규모에서는 요청-전달이 별도 권한 체계를 만드는 것보다 빠릅니다.

### 전원이 쓰는 상태 확인

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://54-116-13-82.sslip.io/health
#   200 이면 정상
```

브라우저에서 열어도 됩니다. 자격증명이 필요 없습니다.
`200`이 아니면 담당자에게 알리고, 그 숫자를 함께 전달하세요 —
아래 5절이 숫자별로 원인을 나눠 둡니다.

## 2. 접속은 SSM Session Manager로 합니다

근거: [ADR-0009](../adr/0009-ssm-session-manager.md) (제안 상태 — 위 안내 참고).
세 방식의 비교표와 탈락 이유가 그 문서에 있습니다.

**SSH 포트(22번)를 열지 않습니다.** 대신 AWS Systems Manager로 셸을 엽니다.

키페어 `.pem`을 나눠 갖는 방식과 비교하면 차이가 분명합니다.
`.pem`은 **한 사람에게만 회수하는 것이 불가능**해서, 한 명이 팀을 떠나면
전원의 키를 교체해야 합니다. 접속 기록도 사람 단위로 남지 않습니다.

각자 공개키를 등록하는 SSH 방식은 회수는 되지만,
보안그룹 22번에 각자의 IP를 등록해야 하고 **집·카페·학교에서 IP가 바뀔 때마다 다시 열어야 합니다.**

SSM은 셋 다 해결합니다. 포트를 닫고, IP와 무관하며, 사람별로 즉시 회수됩니다.

### 2-1. 인스턴스에 IAM 역할 붙이기 (최초 1회)

1. IAM > 역할 > 역할 생성 > 신뢰할 엔터티 **AWS 서비스 > EC2**
2. 권한 정책에 **`AmazonSSMManagedInstanceCore`** 하나만 선택
3. 역할 이름 `savers-ec2-ssm`으로 생성
4. EC2 > 해당 인스턴스 > 작업 > 보안 > **IAM 역할 수정** > 위 역할 선택

⚠️ **1~3은 계정 관리자(PM)만 할 수 있습니다.** `PowerUserAccess`는 `iam:CreateRole`을 막습니다.
4만 Backend/Infra 소관이고, 그것도 `iam:PassRole` 권한이 별도로 필요합니다.
발급 절차는 [AWS_계정_발급_가이드.md](AWS_계정_발급_가이드.md)에 있습니다.

재부팅은 필요 없습니다. 다만 **이미 떠 있는 인스턴스에 역할을 나중에 붙였다면
에이전트를 재시작해야 합니다.**

```bash
sudo systemctl restart snap.amazon-ssm-agent.amazon-ssm-agent.service
```

에이전트는 **기동 시점에 인스턴스 자격증명을 잡습니다**(높은 신뢰).
역할이 없던 상태로 떠 있었다면 붙었다는 사실을 모른 채 계속 돌고 있어서,
재시작 전까지 Fleet Manager에 나타나지 않습니다.
4번 직후에 목록을 보고 "역시 안 되네"라고 판단하기 쉬운 자리입니다.

역할이 실제로 붙었는지는 VM 안에서 한 번에 갈립니다.

```bash
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -w "\n[%{http_code}]\n" -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

역할 이름이 찍히면 붙은 것이고, **`[404]`면 안 붙은 것**입니다.

### 2-2. 에이전트 동작 확인

Ubuntu 24.04 공식 AMI에는 `amazon-ssm-agent`가 미리 설치돼 있습니다.
아직 SSH가 열려 있는 동안 확인하세요.

```bash
sudo snap list amazon-ssm-agent
sudo systemctl status snap.amazon-ssm-agent.amazon-ssm-agent.service
```

없으면 `sudo snap install amazon-ssm-agent --classic`으로 설치합니다.

콘솔에서 **Systems Manager > Fleet Manager**에 인스턴스가 나타나면 등록된 것입니다.

### 2-3. 팀원 IAM 사용자에 권한 부여

셸이 필요한 사람(김도혁·신호정)의 IAM 사용자에 아래 정책을 붙입니다.
계정 전체가 아니라 **이 인스턴스 하나로 범위를 좁힌 정책**입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ssm:StartSession"],
      "Resource": [
        "arn:aws:ec2:ap-northeast-2:<계정ID>:instance/<인스턴스ID>",
        "arn:aws:ssm:ap-northeast-2::document/SSM-SessionManagerRunShell"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["ssm:TerminateSession", "ssm:ResumeSession"],
      "Resource": "arn:aws:ssm:*:*:session/${aws:username}-*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "ssm:DescribeSessions",
        "ssm:DescribeInstanceInformation",
        "ec2:DescribeInstances"
      ],
      "Resource": "*"
    }
  ]
}
```

> ⚠️ **위 JSON에는 성격이 다른 자리표시자가 두 종류 섞여 있습니다.**
>
> | 자리표시자 | 어떻게 하나 |
> |---|---|
> | `<계정ID>` · `<인스턴스ID>` | **사람이 실제 값으로 바꿉니다** |
> | `${aws:username}` | **손대지 않고 그대로 둡니다** |
>
> `${aws:username}`은 빈칸이 아니라 **AWS가 실행 시점에 접속한 사람의 이름으로 치환하는 변수**입니다.
> 달러 기호와 중괄호까지 통째로 두어야 하고, 실제 이름으로 바꾸면 오히려 동작하지 않습니다.
> 실제로 이 구분이 없어 계정 발급이 한 번 멈춘 적이 있습니다.

`${aws:username}`은 **IAM 사용자로 로그인할 때만 값이 채워집니다**(확실한 사실).
팀이 IAM Identity Center(SSO)로 옮기면 이 자리가 비어 해당 문장이 맞지 않게 되므로,
그때 다시 봐야 합니다.

두 번째 문장은 **자기가 연 세션을 자기가 닫는** 권한이라, 없어도 접속 자체는 됩니다
(세션이 시간이 지나 자동으로 끊길 뿐입니다).
콘솔에서 저장이 막히면 그 블록만 빼고 진행해도 나머지는 동작합니다.

**회수는 이 정책을 떼는 것으로 끝납니다.** VM에 손대지 않아도 됩니다.

### 2-4. 각자 로컬 준비

브라우저(AWS 콘솔 > EC2 > 연결 > 세션 관리자)로 접속하면 설치할 것이 없습니다.

> ⚠️ **같은 "연결" 창의 "EC2 인스턴스 연결" 탭을 누르면 실패합니다.**
> 이름이 비슷해 나란히 놓여 있지만 **SSM이 아니라 22번 포트를 쓰는 별개 기능**이고,
> 접속이 사용자 PC가 아니라 AWS가 관리하는 별도 IP 대역에서 들어옵니다.
> 22번을 닫았거나 특정 IP만 허용해 두었다면 막힙니다.
>
> 실패 메시지가 `Error establishing SSH connection to your instance`로 나와
> **SSM 설정이 잘못된 것처럼 읽히지만 무관합니다.** 반드시 **세션 관리자** 탭을 쓰세요.
터미널에서 붙으려면 AWS CLI에 더해 Session Manager 플러그인이 필요합니다.
플러그인이 없으면 `SessionManagerPlugin is not found` 오류가 납니다.

```bash
# Ubuntu·WSL
curl -o session-manager-plugin.deb \
  "https://s3.amazonaws.com/session-manager-downloads/plugin/latest/ubuntu_64bit/session-manager-plugin.deb"
sudo dpkg -i session-manager-plugin.deb

# macOS
brew install --cask session-manager-plugin

# 설치 확인 — 버전이 찍히면 됩니다
session-manager-plugin --version
```

Windows는 설치 관리자(`.exe`)를 받아 실행합니다.
운영체제별 최신 링크는 [AWS 공식 설치 문서](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html)에 있습니다.

```bash
aws ssm start-session --target <인스턴스ID> --region ap-northeast-2
```

접속하면 `ssm-user`로 들어가므로, 작업 전에 배포 사용자로 전환합니다.

```bash
sudo su - ubuntu
cd ~/savers-project
```

### 2-5. 22번 포트 닫기

> ⚠️ **반드시 마지막에, SSM 접속을 실제로 성공한 뒤에 하세요.**
> 순서를 바꾸면 SSM이 아직 안 되는 상태에서 SSH까지 막혀 **아무도 못 들어갑니다.**
> 잠기면 인스턴스를 다시 만드는 것 외에 방법이 마땅치 않습니다.

SSM으로 한 번 들어가 본 뒤 보안그룹 인바운드에서 22번 규칙을 삭제합니다.
남는 것은 80과 443뿐입니다.

## 3. 일상 운영 명령

셸에 들어간 뒤 `~/savers-project`에서 실행합니다.

```bash
# 컨테이너 상태
docker compose -f infra/docker-compose.yml --profile tls ps

# 로그 (최근 100줄)
docker compose -f infra/docker-compose.yml --profile tls logs --tail 100 backend
docker compose -f infra/docker-compose.yml --profile tls logs --tail 100 caddy

# 로그 실시간
docker compose -f infra/docker-compose.yml --profile tls logs -f backend

# 코드 갱신 후 재배포
git pull
docker compose -f infra/docker-compose.yml --profile tls up -d --build
```

`.env`를 고쳤을 때는 `restart`가 아니라 **`up -d`** 를 써야 합니다.
환경변수는 컨테이너를 만들 때 박히므로 재시작만으로는 바뀌지 않습니다.
출력이 `Running`이면 반영되지 않은 것이고 `Recreated`여야 합니다.

인증서는 Caddy가 자동으로 갱신합니다. 사람이 할 일이 없습니다.

## 4. 하지 말아야 할 것

> ⚠️ **시연 중 `restart`·`up -d` 금지.**
> 세션이 프로세스 메모리에 있어서 **재시작하면 발급된 알림 링크가 전부 무효**가 됩니다.
> 시연 직전에 배포하지 말고, 문제가 생겨도 시연이 끝난 뒤에 손대세요.

> ⚠️ **`docker compose down -v` 금지.**
> `-v`가 `caddy_data` 볼륨을 지우는데 거기에 TLS 인증서가 들어 있습니다.
> 재발급은 Let's Encrypt 한도에 걸릴 수 있어, 최악의 경우 HTTPS 없이 발표하게 됩니다.

> ⚠️ **`infra/.env` 내용을 저장소·이슈·채팅에 붙여넣지 마세요.**
> 이 저장소는 공개입니다. 커밋된 키는 되돌려도 공개된 것이라 재발급이 유일한 대응입니다.
> 값을 공유해야 하면 팀 보관소를 쓰세요.

> ⚠️ **8000·8100 포트를 보안그룹에서 열지 마세요.**
> 두 포트는 `127.0.0.1`에만 바인딩돼 있고 Caddy가 내부 네트워크로 닿습니다.
> 열면 평문 경로가 같이 열려 HTTPS 대책이 통째로 우회되고,
> ai-engine은 인증 없이 취약계층 프로필을 받으므로 노출 자체가 사고입니다(이슈 #25).

## 5. 장애 대응

`/health` 응답 코드로 먼저 나눕니다.

| 증상 | 어디를 보는가 |
|---|---|
| 응답 없음 / 연결 실패 | 인스턴스가 꺼졌거나 caddy가 죽음. 콘솔에서 인스턴스 상태 → `ps` |
| `502` | caddy는 살아 있고 backend가 죽음. `logs backend` |
| `404` (`/health`인데) | 요청이 엉뚱한 서버로 감. 인증서 `identifier`와 현재 공인 IP 대조 |
| `200`인데 프론트가 안 됨 | 서버 문제가 아닙니다. Vercel 배포와 `VITE_API_BASE_URL` 확인 |
| 브라우저 콘솔에 CORS 오류 | `SAVERS_CORS_ALLOW_ORIGINS`와 실제 프론트 오리진 대조(슬래시·스킴까지) |

배포 검증 8개를 다시 돌리는 것이 가장 빠른 진단입니다 —
[배포_절차.md](배포_절차.md) 1-5를 그대로 쓰면 어디가 깨졌는지 항목 단위로 나옵니다.

## 6. 아직 없는 것

- **모니터링·알림** — 서버가 죽어도 아무도 자동으로 알지 못합니다.
  시연 전에는 사람이 `/health`를 확인하는 것이 유일한 감시입니다.
- **백업** — 세션은 메모리, 그 외 영속 데이터는 인증서 볼륨뿐입니다.
  백업 대상이 생기는 시점에 이 절을 고쳐야 합니다.
- **이중화** — 단일 VM입니다(ADR-0003). 이 VM이 죽으면 서비스가 죽습니다.
- **프로비저닝 자동화** — 콘솔 수작업입니다. 인스턴스를 잃으면 절차를 다시 밟아야 합니다.
