# 후속 과제

프론트엔드 PWA(#32) 머지 시점 기준으로 남아 있는 과제 목록입니다.
담당은 사람 이름이 아니라 **역할**로 적습니다.
일정과 인원 배치는 [docs/역할_일정/00-overall.md](../역할_일정/00-overall.md)가 단일 출처이고,
이 문서는 "무엇이 왜 남았는가"만 다룹니다.

각 항목에 **왜**를 함께 적은 이유는 이 저장소의 다른 문서와 같습니다.
이유 없는 항목은 나중에 읽는 사람이 건너뜁니다.

우선순위 기준:

- **P0** — 사용자 안전에 직접 닿음. 다른 것보다 먼저.
- **P1** — 제출 지표나 모듈 간 계약에 영향.
- **P2** — 품질·성능. 시연 인상과 지표에 간접 영향.
- **P3** — 정리. 지금 아프지는 않지만 방치하면 사고를 냄.

## P0

### 1. 오프라인 폴백이 "회선 단절"만 잡는다

| | |
|---|---|
| 위치 | `apps/frontend/src/sw.ts` — `NavigationRoute` 핸들러 |
| 역할 | 프론트엔드 |

**현상.**
내비게이션 핸들러는 `fetch()`가 **거부(reject)될 때만** 프리캐시 셸로 넘어갑니다.
비행기모드는 즉시 거부되므로 정상 동작합니다.

**왜 문제인가.**
재난 상황의 실제 회선은 끊기기보다 **혼잡해서 응답만 안 옵니다.**
`fetch`에는 기본 타임아웃이 없어 이 경우 수십 초를 매달리고, 그동안 화면은 비어 있습니다.
캐시에 멀쩡한 앱 셸이 있는데도 쓰이지 않습니다.
`AGENTS.md`의 오프라인 폴백 하드 제약이 **가장 필요한 순간에 발동하지 않는 모양**입니다.

**해결 방향.**
`AbortController` 기반 짧은 타임아웃(3초 안팎)을 `fetch`와 경주시켜,
거부뿐 아니라 "제때 안 옴"도 같은 폴백 사다리로 흘려보냅니다.
폴백 사다리(프리캐시 → 캐시 직조회 → 503) 자체는 이미 구현돼 있어
진입 조건만 넓히면 됩니다.

**검증.**
비행기모드가 아니라 **네트워크 스로틀링(오프라인이 아닌 극저속)** 으로
`/a?t=…` 진입을 확인해야 합니다.
비행기모드 확인만으로는 이 경로가 검증되지 않습니다.

## P1

### 2. 계약 미러 드리프트를 잡을 장치가 없다

| | |
|---|---|
| 위치 | `apps/frontend/src/api/types.ts` ↔ `packages/contracts/openapi.yaml` |
| 역할 | 프론트엔드 + 계약 소유자 |

**현상.**
`types.ts`는 손으로 옮긴 미러이고, 머지 시점 기준으로는 정확합니다(`1e2cbd0` 기준 대조 완료).

**왜 문제인가.**
`contracts-check.yml`은 스펙이 **문법적으로 유효한지**만 검사합니다.
스펙에서 필드 하나가 nullable로 바뀌어도 이 파일은 조용히 낡고,
낡았다는 사실은 런타임에 화면이 깨질 때 알게 됩니다.
"구두 합의 금지"가 규약인데 미러는 사람 눈이 유일한 강제 수단입니다.

**해결 방향.**
openapi.yaml에서 TS 타입을 생성해 커밋본과 diff하는 스텝을 `frontend-ci.yml`에 추가합니다.
생성물로 대체하자는 게 아니라 — 지금 파일의 주석은 그 자체로 가치가 있습니다 —
**어긋남만 알려주는** 용도입니다.

> ⚠️ `frontend-ci.yml`은 `paths:` 필터가 걸린 워크플로이므로
> **required check로 지정하지 마세요.** ([저장소_운영.md](저장소_운영.md) §4)

### 3. 등록 생성 API가 계약에 없다

| | |
|---|---|
| 위치 | `packages/contracts/openapi.yaml` |
| 역할 | 계약 소유자 + 백엔드 |

**현상.**
계약에는 조회(`GET /v1/registration/{token}`)와 기기 연결(`POST /v1/devices`)만 있고
**등록을 만드는 경로가 없습니다.**
그래서 `/ops` 화면과 `src/api/firestore.ts` 임시 어댑터가 현재 유일한 등록 경로입니다.

**왜 문제인가.**
임시 어댑터를 없앨 착지점이 계약에 없으면 그 어댑터가 기본값으로 굳습니다.
`firestore.ts` 헤더에도 "not a new contract surface"라고 적혀 있는데,
대체할 계약이 없으면 그 선언이 지켜지지 않습니다.

**해결 방향.**
`POST /v1/registrations` 초안을 계약에 올립니다.
요청 본문에 동의 상태(현재 `types.ts` 하단에 프론트 전용으로 격리된 `ConsentFlags`)를
포함할지가 함께 정해져야 합니다.
착지하면 `client.ts` 호출부만 교체되고 화면은 그대로입니다.

### 4. 임시 저장소 접근 통제 확정

| | |
|---|---|
| 위치 | `apps/frontend/src/api/firestore.ts` (경계), 보안 규칙 |
| 역할 | QA/보안 + 인프라 |

**현상.**
두 기기(운영자 태블릿 ↔ 당사자 폰)를 잇는 임시 저장소에 접근 인증이 없고,
보안 규칙이 콘솔에만 있어 이 저장소에서 독립 검증이 불가합니다.

**왜 문제인가.**
저장되는 항목이 이름·행정동·연락처·기기 토큰이며,
이는 **그 자체로 취약계층 명단**입니다.
현재 합성 데이터만 넣는다는 것은 운영 원칙이지 통제 장치가 아닙니다.

**해결 방향과 진행 상황은 팀 내부 채널에서 다룹니다.**
실데이터 투입 차단과 규칙 확정이 끝나기 전까지 실데이터를 다루지 않는 것이 선행 조건입니다.
개인정보 체크리스트(#27)의 S1·S3 판정도 이 항목과 함께 QA/보안 확인을 받습니다.

### 13. 평가 하네스에 채점 대상이 아직 없다

| | |
|---|---|
| 위치 | `apps/ai-engine/eval/` |
| 역할 | AI/RAG + QA/보안 |

**현상.**
지표 함수·골든셋·채점 스크립트는 들어왔습니다(#48).
하네스는 돌아가고 수치도 나오지만, **재는 대상이 전부 스텁**입니다.

**왜 문제인가.**
지금 나오는 근거 일치율 100%는 원문을 그대로 인용하는 스텁 생성기를
그 원문과 대조한 값이고, 환각 억제율은 `측정 불가`로 나옵니다.
스텁은 환각을 만들 수 없어 가드레일 on/off 문안이 같기 때문입니다.
코퍼스도 `[더미]` 표시가 붙은 자리표시자입니다.
**제출 지표 4종 중 실측이라 부를 수 있는 것이 아직 하나도 없습니다.**

**해결 방향.**
세 가지가 채워져야 수치가 의미를 갖고, 서로 독립입니다.

1. **실제 코퍼스** — `[더미]` 픽스처를 국민행동요령 원문으로 교체 (AI/RAG)
2. **실제 생성기** — `Generator` 이음매에 HyperCLOVA X 클라이언트 (AI/RAG).
   붙는 순간 환각 억제율이 처음으로 값을 냅니다
3. **골든셋 확장** — 현재 6건, 목표는 30~50건 (QA/보안).
   케이스 형식과 검증은 이미 잡혀 있어 데이터만 추가하면 됩니다

**하네스가 이미 잡아낸 것.**
`확정 사실 그대로 반복` 50% — 문안이 대피소 **이름은 넣지만 거리(320m)는 넣지 않습니다.**
계약상 금지는 아니지만, 얼마나 먼지 모르면 갈지 말지 판단할 수 없습니다.
문안 프레임에 거리를 넣을지가 결정 사항입니다.

[ADR-0005](../adr/0005-webpush-primary-channel.md)의 실기기 웹푸시 검증이 착수됩니다.
예선 제출보다 앞선 기한입니다.

## P2

### 6. 라우트 코드 분할이 없다

| | |
|---|---|
| 위치 | `apps/frontend/src/App.tsx` |
| 역할 | 프론트엔드 |

**현상.**
라우트 6개가 전부 정적 import입니다(동적 `import()`·`React.lazy` 0건).

**왜 문제인가.**
재난 알림을 탭해 `/a?t=`로 들어온 사용자가
`Ops.tsx`(2,428줄)·`Register.tsx`(1,699줄)·`qrcode`·Firestore SDK까지
**전부 내려받은 뒤에야** 첫 화면을 봅니다.
그 사용자에게는 하나도 필요 없는 코드입니다.
이건 성능 취향 문제가 아니라 **알림 도달 ≤30초 지표에 그대로 들어가는 시간**입니다.
구형 단말 + 혼잡 회선이 우리 대상 사용자의 기본 조건입니다.

**해결 방향.**
라우트 단위 `React.lazy` 분리 + 빌드 산출 번들 크기를 CI 로그에 남깁니다.
동작 변경이 없는 순수 분리라 화면 리뷰 부담 없이 들어갑니다.

### 7. 자동 테스트 0건

| | |
|---|---|
| 위치 | `apps/frontend/` |
| 역할 | 프론트엔드 + QA |

**현상.**
현재 품질 게이트는 `oxlint`와 `tsc`(tsconfig 3종)뿐입니다.

**왜 문제인가.**
타입 검사는 "형태가 맞는가"만 봅니다.
폴백 사다리·토큰 충돌 처리·저장 필드 허용 목록처럼
**분기가 맞는가**는 아무도 안 봅니다.
그리고 위 P0·P2 항목을 고칠 때 회귀를 잡아줄 그물이 없습니다.

**해결 방향.**
mock 어댑터가 사실상 계약 fixture 역할을 하므로 **어댑터 계층부터** 붙이는 것이 순서입니다
(#32 본문의 판단에 동의).
vitest 셋업 + 어댑터 계약 테스트 한 묶음으로 형식을 세운 뒤 화면 테스트로 확장합니다.

3. **남은 것 (b) — 더 큽니다.** [ADR-0005](../adr/0005-webpush-primary-channel.md)가
   1차 채널을 알림톡에서 웹푸시로 바꿨는데, **그 전환이 문서 대부분에 반영되지 않았습니다.**
   ADR-0005 자신이 §"영향받는 문서"에 대상 표를 갖고 있고, 그중 상당수가 아직 미처리입니다.
   특히 `역할_가이드/04-프론트엔드-UX.md`는 여전히 "알림톡을 1차 푸시 채널, 웹푸시를 보조"로
   서술하고 **폐기된 렌더링 어댑터**(ADR-0005가 재도입 금지한 바로 그것)를 산출물로 지정합니다.
   `역할_일정/00-overall.md`의 간트와 8/6 수직 관통 게이트 정의도 알림톡 통합 기준입니다.

   **Tech Lead 소관분은 #47로 처리했습니다.** 머지되지 않고 남아 있던 로컬 초안
   (`docs/webpush-sync`)을 현재 main 위로 옮긴 것으로, `외부_승인.md` C절·
   `역할_가이드/02`·README·ADR-0005 후속 조치 표가 여기 들어갔습니다.
   초안에 있던 Firebase 프로젝트 ID는 적지 않았습니다 — 저장소가 public이고,
   개인 계정 프로젝트라 팀 계정으로 옮기면 틀린 값이 됩니다.

   **남은 것은 PM·QA 소관입니다.** `역할_가이드/04-프론트엔드-UX.md`는 여전히
   "알림톡을 1차 푸시 채널, 웹푸시를 보조"로 서술하고 **폐기된 렌더링 어댑터**
   (ADR-0005가 재도입 금지한 바로 그것)를 산출물로 지정합니다.
   `역할_일정/00-overall.md`·`리스크.md`·`비용_산정.md`·`구현_범위.md`도 미처리이며,
   대상과 소관은 ADR-0005 후속 조치 표에 ⬜로 남아 있습니다.
4. **남은 것 (c)** — `AGENTS.md`의 역할표 두 행이 ADR과 어긋납니다(#34 리뷰, 김도혁).
   Backend/Infra 행의 `infra redundancy`는
   [ADR-0003](../adr/0003-single-vm-seoul.md)의 "관리형 이중화는 유보"와 반대이고,
   QA/Security 행의 `web-push fallback path`는
   웹푸시를 1차로 올린 [ADR-0005](../adr/0005-webpush-primary-channel.md)와 어긋납니다
   (알림톡이 1차이던 시절 웹푸시가 "보조 경로"였던 서술이 그대로 남은 것입니다).
   두 문구 모두 `2f7db4b`(#1) 이후 수정된 적이 없어, 두 ADR보다 앞선 서술입니다.

   같은 파일 기술스택 표에는 이미 "managed redundancy deferred"라고 정정돼 있어
   **한 파일 안에서 두 줄이 서로 모순**입니다.
   `AGENTS.md`는 모든 에이전트가 읽는 단일 진실 문서라 역할 가이드보다 파급이 큽니다.
   QA/Security 쪽은 명칭만 고칠 것이 아니라,
   ADR-0005가 "⚠️ 미해결"로 남긴 **알림 권한 거부 시 대체 도달 경로**가
   그 자리에 들어가야 하는지 함께 정해야 합니다.
   두 행 모두 당사자 소유라 오너 리뷰가 필요합니다.

**왜 문제인가.**
이 저장소는 공개이고 심사위원이 직접 봅니다.
문서와 코드가 어긋나면 어느 쪽이 진실인지 판단할 근거가 없습니다.

**해결 방향.**
정리 범위를 먼저 공유하고 각 문서 소유자 리뷰를 받습니다.
구분할 것 — **수직 대피 지시·주변 위험 경고**는 "뺀 것"이 아니라
계약에 필드가 없어 데이터를 받을 수 없는 상태입니다.
이 둘은 계약에 필드가 추가되면 화면을 붙이는 항목이지 삭제 대상이 아닙니다.

## 이미 확인된 것 (다시 파지 않아도 되는 것)

같은 검증을 반복하지 않도록 기록해 둡니다.
기준은 #32 머지 커밋입니다.

- **계약 미러 정확성** — `types.ts`를 `1e2cbd0` 기준 스펙과 대조.
  `Profile`·`AlertMessage`·`ShelterList`·`ChatResponse`·
  `DeviceRegisterRequest`·`RegistrationTarget`의 필수/nullable 여부 일치.
  해당 커밋 이후 `packages/contracts/`에 변경 없음.
- **위치 미저장** — `apps/frontend/src` 전체에서
  `localStorage`·`sessionStorage`·`indexedDB`·`document.cookie` **쓰기 0건.**
  하드 제약이 약속이 아니라 구조로 성립합니다.
- **환경변수 표면** — 코드가 읽는 `VITE_*` 16개가 `.env.example`과 정확히 일치.
  미문서화 읽기 없음.
  `VITE_TMAP_APP_KEY`는 예시 파일에만 있고 소비하는 코드 없음(자리표시자).
- **의존성 출처** — `package-lock.json`의 `resolved`가 전부 공식 npm 레지스트리.
  설치 스크립트를 가진 패키지는 `@firebase/util`·`fsevents`·`protobufjs` 3개로 모두 표준.
- **서비스워커 1개 원칙** — 루트 `firebase-messaging-sw.js` 없음.
  `injectManifest` + 커스텀 `sw.ts` 단일 등록.
