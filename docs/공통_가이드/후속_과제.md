# 후속 과제

프론트엔드 PWA(#32) 머지 시점 기준으로 남아 있는 과제 목록입니다.
담당은 사람 이름이 아니라 **역할**로 적습니다.
일정과 인원 배치는 [docs/역할_일정/00-overall.md](../역할_일정/00-overall.md)가 단일 출처이고,
이 문서는 "무엇이 왜 남았는가"만 다룹니다.

각 항목에 **왜**를 함께 적은 이유는 이 저장소의 다른 문서와 같습니다.
이유 없는 항목은 나중에 읽는 사람이 건너뜁니다.

우선순위 기준:

- **P0** — 사용자 안전에 직접 닿음. 다른 것보다 먼저.
- **P1** — 제출 지표나 모듈 간 계약에 영향.
- **P2** — 품질·성능. 시연 인상과 지표에 간접 영향.
- **P3** — 정리. 지금 아프지는 않지만 방치하면 사고를 냄.

## P0

### 1. 오프라인 폴백이 "회선 단절"만 잡는다

| | |
|---|---|
| 위치 | `apps/frontend/src/sw.ts` — `NavigationRoute` 핸들러 |
| 역할 | 프론트엔드 |

**현상.**
내비게이션 핸들러는 `fetch()`가 **거부(reject)될 때만** 프리캐시 셸로 넘어갑니다.
비행기모드는 즉시 거부되므로 정상 동작합니다.

**왜 문제인가.**
재난 상황의 실제 회선은 끊기기보다 **혼잡해서 응답만 안 옵니다.**
`fetch`에는 기본 타임아웃이 없어 이 경우 수십 초를 매달리고, 그동안 화면은 비어 있습니다.
캐시에 멀쩡한 앱 셸이 있는데도 쓰이지 않습니다.
`AGENTS.md`의 오프라인 폴백 하드 제약이 **가장 필요한 순간에 발동하지 않는 모양**입니다.

**해결 방향.**
`AbortController` 기반 짧은 타임아웃(3초 안팎)을 `fetch`와 경주시켜,
거부뿐 아니라 "제때 안 옴"도 같은 폴백 사다리로 흘려보냅니다.
폴백 사다리(프리캐시 → 캐시 직조회 → 503) 자체는 이미 구현돼 있어
진입 조건만 넓히면 됩니다.

**검증.**
비행기모드가 아니라 **네트워크 스로틀링(오프라인이 아닌 극저속)** 으로
`/a?t=…` 진입을 확인해야 합니다.
비행기모드 확인만으로는 이 경로가 검증되지 않습니다.

### 18. 침수 회피 경로 엔진이 코드에 없다 — 「경로 없음→대피소 재선정」 실패 모드를 시연할 수 없음

| | |
|---|---|
| 위치 | `apps/backend/src/backend_core/shelters.py` (직선거리 `haversine_m()`만 존재) |
| 역할 | 백엔드 |

**현상.**
[실패_모드_시연_대본.md](실패_모드_시연_대본.md) 작성 중(2026-08-28) 확인.
`origin/main` 전체를 검색해도 `osmnx`·`networkx` 관련 코드가 `apps/` 어디에도 없고,
링크 등급(R0~R3) 필터링·그래프 구축·"경로 없음" 응답 형태 모두
코드·계약(`packages/contracts/openapi.yaml`) 어디에도 없다.
[ADR-0017](../adr/0017-route-engine-osmnx-networkx.md)은 엔진 선택(OSRM 대신 OSMnx+networkx)에
대한 제안일 뿐, 구현 여부와는 별개다.
[역할_일정/04-백엔드.md](../역할_일정/04-백엔드.md)의 계획(경로 A안 완료 8/26,
「경로 없음」 폴백 8/27)과 어긋난다.

**왜 문제인가.**
"최단이 아니라 지나갈 수 있는 길"은 [구현_범위.md](구현_범위.md)가 명시한 서비스 고유 안전
기능이자, 5대 실패 모드 시연 케이스 중 하나([아키텍처.md](아키텍처.md) 5절)다. 지금 상태로는
침수 등급이 높은 링크를 걸러내지 않고 직선거리로만 대피소를 고르므로, 실제 침수 구간을
통과하는 경로를 안내할 수 있다 — 리스크.md ①이 경고하는 "잘못된 대피 지침"의 구체 사례다.

**해결 방향.**
Backend에 미병합 로컬 브랜치 존재 여부를 우선 확인한다. 없다면 8/28~29 구간에서
최소 버전(경로 없음 판정 + 재선정 API 응답 하나만이라도)을 붙이거나, 시연 대본에서
코드 시연을 화이트보드 설명으로 대체하기로 결정한다 — 세 선택지 모두
[실패_모드_시연_대본.md](실패_모드_시연_대본.md) 케이스 4 절에 이미 정리돼 있다.

**8/29 갱신.** 원격 브랜치 60여 개를 전부 확인했으나 route/osmnx 관련 브랜치는
없었다 — 미병합 구현 없음으로 결론. 별도로 도혁 님이 이 케이스의 구현으로 제시한
[PR #118](https://github.com/team-savers/savers-project/pull/118)도 검증했는데,
경로 엔진과 무관한 별개의 안전 필터 기능(대피소 후보 전부 지하라 `all_excluded`)이었다
— 실재현 가능하고 단위 테스트로 고정돼 있어 [실패_모드_시연_대본.md](실패_모드_시연_대본.md)
케이스 6(보너스)으로 별도 기록했지만, 이 항목(경로 엔진)을 채우지는 못한다. 오늘이
코드 프리즈일이라 위 해결 방향 중 "화이트보드 대체"만 남았다.

## P1

### 2. 계약 미러 드리프트를 잡을 장치가 없다

| | |
|---|---|
| 위치 | `apps/frontend/src/api/types.ts` ↔ `packages/contracts/openapi.yaml` |
| 역할 | 프론트엔드 + 계약 소유자 |

**현상.**
`types.ts`는 손으로 옮긴 미러이고, 머지 시점 기준으로는 정확합니다(`1e2cbd0` 기준 대조 완료).

**왜 문제인가.**
`contracts-check.yml`은 스펙이 **문법적으로 유효한지**만 검사합니다.
스펙에서 필드 하나가 nullable로 바뀌어도 이 파일은 조용히 낡고,
낡았다는 사실은 런타임에 화면이 깨질 때 알게 됩니다.
"구두 합의 금지"가 규약인데 미러는 사람 눈이 유일한 강제 수단입니다.

**해결 방향.**
openapi.yaml에서 TS 타입을 생성해 커밋본과 diff하는 스텝을 `frontend-ci.yml`에 추가합니다.
생성물로 대체하자는 게 아니라 — 지금 파일의 주석은 그 자체로 가치가 있습니다 —
**어긋남만 알려주는** 용도입니다.

> ⚠️ `frontend-ci.yml`은 `paths:` 필터가 걸린 워크플로이므로
> **required check로 지정하지 마세요.** ([저장소_운영.md](저장소_운영.md) §4)

### 3. 등록 생성 API가 계약에 없다

| | |
|---|---|
| 위치 | `packages/contracts/openapi.yaml` |
| 역할 | 계약 소유자 + 백엔드 |

**현상.**
계약에는 조회(`GET /v1/registration/{token}`)와 기기 연결(`POST /v1/devices`)만 있고
**등록을 만드는 경로가 없습니다.**
그래서 `/ops` 화면과 `src/api/firestore.ts` 임시 어댑터가 현재 유일한 등록 경로입니다.

**왜 문제인가.**
임시 어댑터를 없앨 착지점이 계약에 없으면 그 어댑터가 기본값으로 굳습니다.
`firestore.ts` 헤더에도 "not a new contract surface"라고 적혀 있는데,
대체할 계약이 없으면 그 선언이 지켜지지 않습니다.

**해결 방향.**
`POST /v1/registrations` 초안을 계약에 올립니다.
요청 본문에 동의 상태(현재 `types.ts` 하단에 프론트 전용으로 격리된 `ConsentFlags`)를
포함할지가 함께 정해져야 합니다.
착지하면 `client.ts` 호출부만 교체되고 화면은 그대로입니다.

### 4. 임시 저장소 접근 통제 확정

| | |
|---|---|
| 위치 | `apps/frontend/src/api/firestore.ts` (경계), 보안 규칙 |
| 역할 | QA/보안 + 인프라 |

**현상.**
두 기기(운영자 태블릿 ↔ 당사자 폰)를 잇는 임시 저장소에 접근 인증이 없고,
보안 규칙이 콘솔에만 있어 이 저장소에서 독립 검증이 불가합니다.

**왜 문제인가.**
저장되는 항목이 이름·행정동·연락처·기기 토큰이며,
이는 **그 자체로 취약계층 명단**입니다.
현재 합성 데이터만 넣는다는 것은 운영 원칙이지 통제 장치가 아닙니다.

**해결 방향과 진행 상황은 팀 내부 채널에서 다룹니다.**
실데이터 투입 차단과 규칙 확정이 끝나기 전까지 실데이터를 다루지 않는 것이 선행 조건입니다.
개인정보 체크리스트(#27)의 S1·S3 판정도 이 항목과 함께 QA/보안 확인을 받습니다.

### 13. 평가 하네스에 채점 대상이 아직 없다

| | |
|---|---|
| 위치 | `apps/ai-engine/eval/` |
| 역할 | AI/RAG + QA/보안 |

**현상.**
지표 함수·골든셋·채점 스크립트는 들어왔습니다(#48).
하네스는 돌아가고 수치도 나오지만, **재는 대상이 전부 스텁**입니다.

**왜 문제인가.**
지금 나오는 근거 일치율 100%는 원문을 그대로 인용하는 스텁 생성기를
그 원문과 대조한 값이고, 환각 억제율은 `측정 불가`로 나옵니다.
스텁은 환각을 만들 수 없어 가드레일 on/off 문안이 같기 때문입니다.
코퍼스도 `[더미]` 표시가 붙은 자리표시자입니다.
**제출 지표 4종 중 실측이라 부를 수 있는 것이 아직 하나도 없습니다.**

**해결 방향.**
세 가지가 채워져야 수치가 의미를 갖고, 서로 독립입니다.

1. **실제 코퍼스** — `[더미]` 픽스처를 국민행동요령 원문으로 교체 (AI/RAG)
2. **실제 생성기** — `Generator` 이음매에 HyperCLOVA X 클라이언트 (AI/RAG).
   붙는 순간 환각 억제율이 처음으로 값을 냅니다
3. **골든셋 확장** — 현재 6건, 목표는 30~50건 (QA/보안).
   케이스 형식과 검증은 이미 잡혀 있어 데이터만 추가하면 됩니다

**하네스가 이미 잡아낸 것.**
`확정 사실 그대로 반복` 50% — 문안이 대피소 **이름은 넣지만 거리(320m)는 넣지 않습니다.**
계약상 금지는 아니지만, 얼마나 먼지 모르면 갈지 말지 판단할 수 없습니다.
문안 프레임에 거리를 넣을지가 결정 사항입니다.

### 15. 보호자 기기 **최초** 구독 화면이 없다

| | |
|---|---|
| 위치 | `apps/frontend/` `/register` 완료 화면(신설 대상), 계약은 `POST /v1/devices` |
| 역할 | AI/RAG/프론트엔드 |

**현상.**
보호자 기기 구독 경로는 계약에 둘입니다 —
최초는 사전등록 시점의 `POST /v1/devices`(`role: guardian`),
갱신은 `/g/` 진입 시의 `POST /v1/guardian/{token}/device`입니다([ADR-0015](../adr/0015-guardian-device-registration.md)).
이 중 **갱신 화면만 본선 범위에 있습니다**(8/28 보호자 화면 칸).
`/register` 완료 화면의 최초 구독은 슬롯이 없어 본선 후로 내렸습니다
(Tech Lead 판단, 2026-08-25 — [ADR-0015](../adr/0015-guardian-device-registration.md)의 결과 절과 후속 조치 표).

**왜 문제인가.**
2차 발송 채널이 웹푸시 하나뿐이라([ADR-0014](../adr/0014-closed-loop-second-dispatch-channel.md))
보호자에게 닿으려면 먼저 구독이 있어야 하는데, `/g/` 링크 자체가 그 2차 발송으로 갑니다.
최초 구독이 없으면 **첫 재난에서 그 순환이 닫히지 않습니다.**
복지관·지자체가 대리등록한 경우에는 보호자가 등록 토큰을 갖지 못해 순환을 깰 방법이 아예 없습니다.

**본선에서는 어떻게 넘기는가.**
리허설에서 보호자 폰으로 `/g/` 링크에 한 번 들어가 갱신 경로로 구독해 둡니다.
등록은 세션이 아니라 **보호자 레코드에 붙으므로** 본 시연의 첫 재난에서 그대로 쓰입니다.
그래서 시연 전제가 넷입니다 — 8/28 구독 UI, 리허설 구독, 그 폰을 본선까지 고정,
본선 당일 아침 갱신(FCM 토큰 로테이션 대비).

⚠️ **셋째가 가장 약합니다.** 앞뒤 셋은 "언제 누가 무엇을 누른다"라 체크리스트로 관리되지만,
폰 고정은 리허설(8/31)부터 본선(9/2)까지 사흘짜리 **지속 조건**이고
깨져도 그 순간에는 아무 신호가 없습니다. 다음 알림에서 2차 발송 화면이 안 나올 때 처음 드러납니다.

**화면의 알림 상태를 보는 것으로는 이것을 잡지 못합니다.**
`GuardianStatus.pushEnabled`는 **피보호자 한 명 단위**로 "보호자 기기가 하나 이상 있는지"를 말합니다.
갱신은 성공해야 교체가 일어나므로, 아침 갱신이 실패하면 리허설에 쓴 토큰이 그대로 남고
본선 폰이 재구독에 실패해도 그 값은 참으로 내려옵니다.
가장 걱정하는 실패를 정확히 놓치는 확인 방법이므로 쓰지 않습니다.

**확인은 실제 발송으로 합니다.** 본선 당일 아침에 데모 발송을 한 번 돌려
**그 폰에 알림이 실제로 뜨는지** 봅니다. 시연용 30분 -> 30초 단축 플래그가 있어
2차 발송까지 그 자리에서 확인됩니다.
**잔여 등록을 따로 지우는 단계는 없습니다** — 그 아침 갱신이 보호자 기기 목록을
새 토큰 하나로 교체하므로 남은 토큰이 함께 사라집니다.
절차의 정본은 [ADR-0015](../adr/0015-guardian-device-registration.md) 결과 절이고
여기서 되풀이하지 않습니다([이슈 151](https://github.com/team-savers/savers-project/issues/151) 판정).
⚠️ **이 교체는 아직 계약과 ADR 에만 있습니다.** `registry.py` 는 여전히 덧붙이므로,
8/28 전에 그 수정(ADR-0015 후속 조치 표, Backend)이 들어가야 위 문장이 참이 됩니다.
⚠️ 시드의 FCM 토큰은 가공값이라 실발송에서 거부됩니다.
1차도 같으므로 **실기기 등록이 시연 전제**입니다.

**해결 방향.**
`/register` 완료 화면에 `/g/` 랜딩과 같은 구독 컴포넌트를 두고 `role: guardian`으로 호출합니다.
계약은 이미 그 경로를 갖고 있어 프론트 작업만 남습니다.

⚠️ **그때 보호자 기기 2대 문제가 같이 올라옵니다** — 갱신이 교체라
폰과 태블릿 둘로 구독하면 하나만 남습니다.
서술은 [ADR-0015](../adr/0015-guardian-device-registration.md) 후속 조치 표가 정본이고
여기서 되풀이하지 않습니다. **구독 화면을 여는 PR 이 그 행을 함께 처리합니다.**

⚠️ **같은 구조가 피보호자(`ward`) 기기 쪽에도 남아 있습니다.**
교체는 보호자 갱신 경로 하나에만 적용했으므로,
`POST /v1/devices`의 `ward` 등록은 그대로 덧붙고 지울 값을 아는 쪽도 그 브라우저뿐입니다.
1차 발송이 죽은 토큰으로 나가는 형태로 나타납니다.
본선 시연이 피보호자 기기 1대로 서므로 본선 범위 밖이며,
[ADR-0015](../adr/0015-guardian-device-registration.md) 후속 조치 표에 함께 올렸습니다.

### 16. 검증 실패(422) 응답이 계약의 오류 모양과 다르다

| | |
|---|---|
| 위치 | [`apps/backend/src/api/main.py`](../../apps/backend/src/api/main.py) — 예외 핸들러 등록 |
| 역할 | 백엔드 |

**현상.**
계약은 모든 오류를 `Error`(`{code, message}`) 모양으로 약속합니다.
그런데 등록된 핸들러는 `HTTPException` 하나뿐이라,
FastAPI가 본문 검증에서 스스로 올리는 422(`RequestValidationError`)는 그 핸들러를 타지 않고
프레임워크 기본 모양(`{"detail": [...]}`)으로 나갑니다.

**왜 문제인가.**
계약에 적힌 모양을 믿고 짠 프론트나 테스트가 실제 응답과 어긋납니다.
[`tests/api/test_main.py`](../../apps/backend/tests/api/test_main.py)의 422 검사가
상태 코드만 보고 본문 모양을 보지 않는 것이 그 회피 흔적입니다.
422를 쓰는 계약 지점이 늘고 있어(보호자 Q&A의 목록 밖 질문 등) 어긋남도 같이 늡니다.

**해결 방향.**
`RequestValidationError`에도 같은 핸들러를 등록해 `Error` 모양으로 변환하고,
기존 422 테스트가 상태 코드와 함께 본문 키까지 보게 합니다.

> 안은남 님이 [PR 104](https://github.com/team-savers/savers-project/pull/104) 리뷰에서 찾았습니다.
> 계약 PR에서 머지를 막을 문제는 아니라고 판정됐고, 구현 쪽 과제로 여기 옮깁니다.

### 14. `scripts/`의 점검 스크립트가 품질 게이트 밖에 있다

| | |
|---|---|
| 위치 | `scripts/check_privacy.py` (952줄), `scripts/check_push_ready.py` (353줄) |
| 역할 | Tech Lead + QA |

**현상.**
CI의 `Lint & Type Check`는 `apps/<app>`만 돌고,
`scripts/run-tests.sh`도 `APPS=(backend ai-engine)`만 순회합니다.
pre-commit의 ruff 훅은 `scripts/`를 포함하지만 mypy 훅은 없고, 이 파일의 단위 테스트는 0건입니다.
즉 훅을 걸지 않은 기여자의 변경은 아무 검사도 거치지 않습니다.

**왜 문제인가.**
이 스크립트는 S1-E6 증빙을 만드는 파일이고,
고장 방향이 **조용한 미탐**입니다 — 검사가 아무것도 못 잡아도 초록으로 보입니다.
특히 `_blank_comments_and_strings`는 자기 docstring에 실제 미탐 사례를 기록해 두고 있습니다
(정규식 리터럴 `/[&<>"']/g` 뒤 구간이 통째로 검사에서 사라졌던 건).
그 사례들이 그대로 회귀 테스트 픽스처인데, 픽스처가 없습니다.

`check_push_ready.py`도 같은 자리에 같은 고장 방향으로 놓여 있습니다.
PR [#81](https://github.com/team-savers/savers-project/pull/81) 리뷰에서
`vapid` 검사가 **배포본 상태와 무관하게 항상 PASS** 했던 것이 실제로 그 사례입니다 —
Firebase SDK가 번들에 항상 넣는 `DEFAULT_VAPID_KEY`를 잡고 있었고,
키를 한 번도 주입하지 않은 배포본까지 초록으로 나왔습니다.
정규식 판정이라 회귀가 눈에 보이지 않으므로,
이 파일도 픽스처로 고정할 사례가 이미 셋 있습니다 —
SDK 기본키 제외, base64url `-`로 끝나는 키 매칭, config 4종 중 일부만 있는 half-config.

**해결 방향.**
관리 요소를 새로 만들지 말고 기존 잡의 경로만 넓히는 쪽이 먼저입니다 —
`run-tests.sh`와 CI lint 잡에 `scripts/`를 추가하고, pre-commit에 mypy 훅을 붙입니다.
테스트는 docstring이 이미 지목한 네 가지(인라인 주석, `*` 없는 블록 연속행, 정규식 리터럴,
닫히지 않은 백틱)와 위 `check_push_ready.py` 세 가지부터 픽스처로 고정합니다.
두 파일을 한 항목으로 묶어 두는 이유는 해결 수단이 같기 때문입니다 —
경로를 넓히는 한 번의 변경이 둘을 동시에 덮습니다.
배치 근거는 [ADR-0010](../adr/0010-privacy-harness-placement.md)이고,
이 항목이 그 ADR의 부정 항목에 걸린 유일한 미완입니다.

   `역할_가이드/03-AI-RAG-프론트엔드.md`는 PR #95에서 웹푸시 1차 채널로 정정됐고
   (렌더링 어댑터 재도입 금지 문구까지 명시), `역할_일정/00-overall.md`의 간트와
   8/6 수직 관통 게이트 정의도 같은 PR의 8/21 개정으로 구간별 매트릭스·새 기준 날짜 표로
   교체되면서 알림톡 통합 서술이 함께 사라졌습니다.

   **Tech Lead 소관분은 #47로 처리했습니다.** 머지되지 않고 남아 있던 로컬 초안
   (`docs/webpush-sync`)을 현재 main 위로 옮긴 것으로, `외부_승인.md` C절·
   `역할_가이드/02`·README·ADR-0005 후속 조치 표가 여기 들어갔습니다.
   초안에 있던 Firebase 프로젝트 ID는 적지 않았습니다 — 저장소가 public이고,
   개인 계정 프로젝트라 팀 계정으로 옮기면 틀린 값이 됩니다.

   **남은 것은 PM 소관입니다.** `역할_가이드/03-AI-RAG-프론트엔드.md`와
   `역할_일정/00-overall.md`는 PR #95에서 이미 정정됐습니다. `리스크.md`·
   `비용_산정.md`·`구현_범위.md`는 아직 미처리이며,
   대상과 소관은 ADR-0005 후속 조치 표에 ⬜로 남아 있습니다.
4. **남은 것 (c)** — `AGENTS.md`의 역할표 두 행이 ADR과 어긋납니다(#34 리뷰, 김도혁).
   Backend/Infra 행의 `infra redundancy`는
   [ADR-0003](../adr/0003-single-vm-seoul.md)의 "관리형 이중화는 유보"와 반대이고,
   QA/Security 행의 `web-push fallback path`는
   웹푸시를 1차로 올린 [ADR-0005](../adr/0005-webpush-primary-channel.md)와 어긋납니다
   (알림톡이 1차이던 시절 웹푸시가 "보조 경로"였던 서술이 그대로 남은 것입니다).
   두 문구 모두 `2f7db4b`(#1) 이후 수정된 적이 없어, 두 ADR보다 앞선 서술입니다.

   같은 파일 기술스택 표에는 이미 "managed redundancy deferred"라고 정정돼 있어
   **한 파일 안에서 두 줄이 서로 모순**입니다.
   `AGENTS.md`는 모든 에이전트가 읽는 단일 진실 문서라 역할 가이드보다 파급이 큽니다.
   QA/Security 쪽은 명칭만 고칠 것이 아니라,
   ADR-0005가 "⚠️ 미해결"로 남긴 **알림 권한 거부 시 대체 도달 경로**가
   그 자리에 들어가야 하는지 함께 정해야 합니다.
   두 행 모두 당사자 소유라 오너 리뷰가 필요합니다.

**왜 문제인가.**
이 저장소는 공개이고 심사위원이 직접 봅니다.
문서와 코드가 어긋나면 어느 쪽이 진실인지 판단할 근거가 없습니다.

**해결 방향.**
정리 범위를 먼저 공유하고 각 문서 소유자 리뷰를 받습니다.
구분할 것 — **수직 대피 지시·주변 위험 경고**는 "뺀 것"이 아니라
계약에 필드가 없어 데이터를 받을 수 없는 상태입니다.
이 둘은 계약에 필드가 추가되면 화면을 붙이는 항목이지 삭제 대상이 아닙니다.

## 팀 결정 대기 (코드로 정할 수 없는 것)

아래는 구현 문제가 아니라 **결정이 없어서 남은** 항목입니다.
결정이 나야 위 과제의 방향이 정해집니다.

| 항목 | 무엇을 정해야 하나 | 결정 전까지의 상태 |
|---|---|---|
| `stage` 화면 분기 | 계약은 `SessionResponse.stage`를 "화면 분기의 단일 권위"로 규정하는데, 현재 화면은 `stage`를 읽지 않아 1단계(예비특보)와 2단계(경보)가 같은 화면입니다. 예선 범위 결정인지, 미구현인지 | 결정에 따라 계약 문서를 구현에 맞추거나, 화면 분기를 구현 |
| iOS 지원 범위 | 현재 검증 환경은 안드로이드/데스크톱 크롬입니다. 대상 사용자(고령층)에 아이폰 비중이 작지 않습니다 | 예선 제출 범위에서 "iOS 미지원" 명시 또는 본선 전 검증 항목으로 편입 |
| `/`·`/register` 유지 여부 | 역할 문서에 없는 화면이며 시연 동선을 위해 추가됐습니다. 제거 시 라우트 2줄 + 화면 파일 2개 | 유지 |
| 실기기 확인 증거 | 2기기 웹푸시 흐름은 자가 확인 완료, 스크린샷·녹화는 미첨부입니다 | 심사 제출물로 필요한지 판단 필요 |
| 등록 토큰의 수명 | 계약이 TTL·1인당 발급 매수·분실 시 재발급을 **"미정이며 팀 결정이 필요하다"**로 남겨 두었습니다(`openapi.yaml`의 `registrationToken`). 보호자 기기가 이 토큰에 매이므로([ADR-0015](../adr/0015-guardian-device-registration.md)) 만료 정책이 곧 2차 발송 도달에 걸립니다 | 만료 없이 운용. 갱신 경로(`/g/`)가 있어 완전 차단은 아니지만, **최초 구독은 이 토큰뿐**입니다 |

## 이미 확인된 것 (다시 파지 않아도 되는 것)

같은 검증을 반복하지 않도록 기록해 둡니다.
기준은 #32 머지 커밋입니다.

- **계약 미러 정확성** — `types.ts`를 `1e2cbd0` 기준 스펙과 대조.
  `Profile`·`AlertMessage`·`ShelterList`·`ChatResponse`·
  `DeviceRegisterRequest`·`RegistrationTarget`의 필수/nullable 여부 일치.
  해당 커밋 이후 `packages/contracts/`에 변경 없음.
- **위치 미저장** — `apps/frontend/src` 전체에서
  `localStorage`·`sessionStorage`·`indexedDB`·`document.cookie` **쓰기 0건.**
  하드 제약이 약속이 아니라 구조로 성립합니다.
- **환경변수 표면** — 코드가 읽는 `VITE_*` 16개가 `.env.example`과 정확히 일치.
  미문서화 읽기 없음.
  `VITE_TMAP_APP_KEY`는 예시 파일에만 있고 소비하는 코드 없음(자리표시자).
- **의존성 출처** — `package-lock.json`의 `resolved`가 전부 공식 npm 레지스트리.
  설치 스크립트를 가진 패키지는 `@firebase/util`·`fsevents`·`protobufjs` 3개로 모두 표준.
- **서비스워커 1개 원칙** — 루트 `firebase-messaging-sw.js` 없음.
  `injectManifest` + 커스텀 `sw.ts` 단일 등록.
