# 세이버스(SAVERS) 프로젝트 리스크 분석

문서 3종(참가신청서, 아이디어 개발 기획서, 수상작 GitHub 레포 전수조사)을 근거로 파악한 리스크를 심각도 순으로 정리한 문서입니다.

## 1. 시연/사업화를 통째로 막을 수 있는 리스크 (최우선)

### ① 카카오 알림톡 템플릿 사전승인 제약

- **원칙**: 카카오 알림톡은 발신 전 카카오·대행사 심사를 거친 **고정 템플릿 + 변수 치환** 방식이 원칙이며, LLM이 매번 자유롭게 생성한 전체 문장을 실시간 발송하는 방식과 정책적으로 충돌할 가능성이 있습니다.
- **실무 예시**: "지금 계신 곳은 ○○동 저지대입니다..." 같은 예시 메시지는 문장 구조가 매번 달라지는데, 실제 알림톡은 이런 자유생성 텍스트를 그대로 승인해주지 않는 경우가 많아 변수 슬롯 설계(`#{장소}`, `#{행동}` 등)로 우회해야 할 수 있습니다.
- 기획서도 "사전 발신 승인 제약"을 리스크로 인지하고 웹푸시 대체 경로를 언급했지만, **동적 생성 자유도 자체가 얼마나 제약되는지**는 다뤄지지 않았습니다. 서비스의 핵심 가치제안("개인화 생성")과 직결되는 부분이라 예선 초반에 실제 카카오 정책을 확인하지 않으면 데모 막판에 막힐 수 있습니다.
- 신뢰도: 높은 신뢰 (알림톡 일반 정책 기준. 세이버스가 실제 신청한 발신프로필 유형은 문서에 없어 확정은 아님)

### ② 안전 관련 오작동의 실제 위해 가능성

- **원칙**: 이 서비스는 데모용 챗봇이 아니라 "대피 행동을 대신 판단"하는 서비스입니다. 위치 매칭 오류, 가드레일 실패, API 장애가 겹치면 잘못된 대피 지침(반대 방향 안내, 지연 도달 등)이 실제 피해로 이어질 수 있는 구조입니다.
- **실무 예시**: 가드레일이 100% 환각을 막지 못한 상태에서 "계단이 아니라 큰길로 가세요" 같은 지침이 틀리게 생성되면, 정보 미제공보다 더 나쁜 결과(잘못된 확신을 주는 행동 유도)를 낳을 수 있습니다.
- 이 리스크는 심사 관점에서는 "안전장치 설계 깊이"를 어필할 기회이기도 하지만, 데모에서 성공 사례만 보여주고 실패 모드·안전장치를 설명하지 않으면 신뢰성 문제로 역풀이될 수 있습니다.
- 신뢰도: 확실한 사실 (서비스 성격 자체에서 발생하는 구조적 리스크)

## 2. 기술적 실현 가능성 리스크

### ③ 30초 지연시간 목표의 타이트함

알림톡 지연 3~5초 + LLM 생성 5~10초 + 매칭 여유분으로 30초를 산정했는데, API 폴링 주기·위치 확인 왕복시간·Chroma 검색 시간을 보수적으로 반영하지 않은 낙관적 추정으로 보입니다. HyperCLOVA X 실시간 생성이 네트워크 상황에 따라 10초를 넘기는 경우가 흔합니다.

- 신뢰도: 추정

### ④ 실시간 공공 API 의존성

기상청·소방청·행정안전부 Open API는 공공기관 API 특유의 불안정성(레이트리밋, 스키마 변경, 승인 대기)이 있고, 신청부터 승인까지 5주 일정에 큰 변수가 될 수 있습니다. 오프라인 예비모드를 설계했다는 점은 좋은 완화책이지만, 예선 5주 안에 "정상 경로"조차 완성하기 빠듯한 일정입니다.

- 신뢰도: 높은 신뢰

### ⑤ 위치 정밀도와 행정동 경계 불일치

브라우저 Geolocation은 실내·도심 고층 환경에서 오차가 크고, 위험구역 판정이 행정동 단위 폴리곤과 GPS 좌표 매칭에 의존하는데 경계 지점 근처 사용자는 오분류 가능성이 있습니다. "위험구역 여부"라는 이진 판단에 이 오차가 직접 영향을 줍니다.

- 신뢰도: 높은 신뢰

## 3. 평가지표 신뢰성 리스크

### ⑥ 목표 수치의 근거 박약

근거 일치율 85%, 환각 억제율 50% 감소 등은 "공개 벤치마크 근거"라고만 되어 있고 세이버스 자체 파일럿 데이터는 없습니다. 문서에도 "가설 목표치"라고 스스로 명시했지만, 심사 과정에서 "왜 하필 85%인가"라는 질문에 답할 근거가 약할 수 있습니다. 평가셋 30~50건은 통계적으로 작아, 근거 일치율 차이가 우연에 의한 것인지 구분하기 어렵습니다.

- 신뢰도: 확실한 사실 (문서 자체가 인정한 한계)

### ⑦ 교차 채점 모델 선정 미정

"생성에 쓰지 않은 별도 모델"로 채점한다고 했는데 구체 모델·비용·API 한도 계획이 없습니다. 자기평가 편향을 막으려던 설계의 핵심인데, 실행 계획이 비어있으면 예선 제출 직전에 급조하게 될 위험이 있습니다.

- 신뢰도: 높은 신뢰

## 4. 일정/범위 리스크

### ⑧ 5주 일정에 4개 모듈 + 통합 + 평가 스크립트 + 보안·E2E 테스트가 모두 들어감

7/23 기준 코드가 한 줄도 없는 상태에서, 데이터 확보 → RAG 인덱싱 → 위치 매칭 → 가드레일 → 알림톡 통합 → 자동 평가 → 보안 테스트 → 시연까지가 사실상 순차 의존관계입니다. 한 단계가 밀리면 뒤 단계 전체가 밀리는 구조라 버퍼가 거의 없습니다.

6명이 서로 다른 전문영역(FE/BE/AI/Infra/QA)을 동시에 진행하지만, 인터페이스(예: 위치 매칭 엔진의 출력 스키마, RAG 검색 결과 포맷)를 언제 확정하는지 문서에 없어 통합 시점에 충돌 위험이 있습니다.

- 신뢰도: 높은 신뢰

## 5. 데이터/프라이버시 리스크

### ⑨ 장애 여부 등 민감정보 처리

장애 여부는 개인정보보호법상 민감정보로 분리 동의·암호화가 필요합니다. "최소 수집·암호화"라는 원칙은 세웠지만 구체적 동의 절차, 보관 기간, 파기 정책은 기획서에 없어 실제 구현 시 법적 요건을 놓칠 여지가 있습니다.

- 신뢰도: 높은 신뢰

## 6. 엔지니어링 관행 리스크 (자체 조사 문서 기준)

### ⑩ 구조 세팅을 미루면 나중에 리팩터링 비용 발생

저장소 구조는 **단일 모노레포**로 확정했고(근거: [개발자_가이드.md](개발자_가이드.md) 7절),
그 안에서 AI(`apps/ai-engine`)를 자체 Dockerfile·README를 가진 독립 배포 엔진으로 유지하기로 했습니다.
스캐폴딩은 끝났습니다 — 세 앱과 계약·CI·compose가 자리를 잡았고,
`apps/ai-engine`은 자체 Dockerfile로 독립 배포 가능함을 증명합니다.

남은 위험은 형태가 바뀌었습니다.
구조를 못 만드는 것이 아니라, **시간 압박 속에서 그 경계를 우회하는 것**입니다.
`apps/backend`가 HTTP 대신 `ai_engine`을 직접 import 하는 한 줄이면
"독립 배포 엔진"이라는 성질이 조용히 사라지고, 그 한 줄은 테스트를 통과합니다.
방어 장치는 셋입니다 — AGENTS.md의 아키텍처 규칙(교차 import 금지),
`CODEOWNERS`의 경로별 리뷰어, 그리고 계약이 `packages/contracts`에 먼저 존재해야 한다는 규약.
리뷰에서 이 셋을 실제로 확인하지 않으면 규칙만 남습니다.

- 신뢰도: 추정
