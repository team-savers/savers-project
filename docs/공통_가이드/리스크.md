# 세이버스(SAVERS) 프로젝트 리스크 분석

제출 기획서 v3(2026-08-10)와 본선 준비 계획(**8/22 ~ 9/2**)을 기준으로 리스크를 심각도 순으로 정리한 문서입니다.
번호(① ~ ⑩)는 역할 가이드·일정 문서가 그대로 참조하므로 **재번호를 붙이지 않고** 내용만 갱신합니다.

## 1. 시연/사업화를 통째로 막을 수 있는 리스크 (최우선)

### ① FCM 실발송이 아직 연결되지 않아 4대 지표 중 둘이 측정 불가

- **현황**: `dispatch.py`의 기본 `RecordingDispatcher`는 주석 그대로 **기록만 하고 실제로 보내지 않습니다.**
  Admin SDK 자격증명이 배포 VM에만 있기 때문입니다.
- **왜 최우선인가**: 「알림 도달 30초」와 「폐루프 2차 발송 성공률 100%」는
  실발송 없이는 **측정 자체가 성립하지 않습니다.** 값이 나쁜 것이 아니라 값이 없는 상태가 됩니다.
- **완화**: **8/22 오후에 실기기 도달 캡처 1장**까지 가고(3.5h), 2차 발송 경로는 8/25에 붙입니다
  (→ [역할_일정/04-백엔드.md](../역할_일정/04-백엔드.md)).
- 신뢰도: 확실한 사실 (코드와 주석으로 확인)

> **옛 ① 「카카오 알림톡 템플릿 사전승인 제약」은 해소됐습니다.**
> [ADR-0005](../adr/0005-webpush-primary-channel.md)로 1차 채널이 웹푸시(FCM)로 확정되면서
> 알림톡은 예선·본선 모두 채택하지 않습니다.
> 남은 채널 리스크는 iOS 웹푸시 제약(A2HS 필요)·알림 권한 거부이며,
> 1차 구현 범위를 **Android 무설치 웹푸시**로 좁혀 대응합니다.

### ② 안전 관련 오작동의 실제 위해 가능성

- **원칙**: 이 서비스는 데모용 챗봇이 아니라 "대피 행동을 대신 판단"하는 서비스입니다. 위치 매칭 오류, 가드레일 실패, API 장애가 겹치면 잘못된 대피 지침(반대 방향 안내, 지연 도달 등)이 실제 피해로 이어질 수 있는 구조입니다.
- **실무 예시**: 가드레일이 100% 환각을 막지 못한 상태에서 "계단이 아니라 큰길로 가세요" 같은 지침이 틀리게 생성되면, 정보 미제공보다 더 나쁜 결과(잘못된 확신을 주는 행동 유도)를 낳을 수 있습니다.
- 이 리스크는 심사 관점에서는 "안전장치 설계 깊이"를 어필할 기회이기도 하지만, 데모에서 성공 사례만 보여주고 실패 모드·안전장치를 설명하지 않으면 신뢰성 문제로 역풀이될 수 있습니다.
- 신뢰도: 확실한 사실 (서비스 성격 자체에서 발생하는 구조적 리스크)

## 2. 기술적 실현 가능성 리스크

### ③ 30초 지연시간 목표의 타이트함

웹푸시 발송 \~1초 + LLM 생성 5 ~ 10초 + 매칭·경로 산출 여유분으로 30초를 산정했는데,
API 폴링 주기·위치 확인 왕복시간·경로 계산 시간(networkx)을 보수적으로 반영하지 않은 낙관적 추정입니다.
HyperCLOVA X 실시간 생성이 네트워크 상황에 따라 10초를 넘기는 경우가 흔합니다.
**폐루프가 붙으면서 단계 수가 늘어난 점**도 함께 봐야 합니다 — 다만 30초 예산은 1차 발송 구간에만 적용됩니다.

- 신뢰도: 추정 (OTel p95 실측으로 교체 예정, PM 8/29)

### ④ 실시간 공공 API 의존성

정부 특보 Open API는 공공기관 API 특유의 불안정성(레이트리밋, 스키마 변경, 승인 대기)이 있습니다.
특보 API 중단 시 **Redis 캐시로 폴백**하고, 지오코딩·DEM 매칭 실패 시 **「판정 불가」로 표기**하는 것이 완화책이며,
"안내는 멈추지 않되 무엇이 대체된 값인지 화면에 드러낸다"는 원칙이 여기서 나옵니다
(→ [아키텍처.md](아키텍처.md) 5절).
본선 준비 구간에서는 실패 모드 시연 대본의 첫 번째 케이스이기도 합니다.

- 신뢰도: 높은 신뢰

### ⑤ 위치 정밀도와 행정동 경계 불일치

브라우저 Geolocation은 실내·도심 고층 환경에서 오차가 크고, 위험구역 판정이 행정동 단위 폴리곤과 GPS 좌표 매칭에 의존하는데 경계 지점 근처 사용자는 오분류 가능성이 있습니다. "위험구역 여부"라는 이진 판단에 이 오차가 직접 영향을 줍니다.

- 신뢰도: 높은 신뢰

## 3. 평가지표 신뢰성 리스크

### ⑥ 부합도 모델 3차 수치가 아직 실측 전

기획서 [표3]의 3차(모델) 칸에는 자체 실측값이 아니라 **유사 기법 선행연구의 보고치가 목표 구간으로** 들어가 있습니다
(spy 기법 PU 학습 F 43.9→76.6, 지형 인자 PU recall 38.9%→51.1%, 침수 PU AUC 0.897).
심사위원이 가장 먼저 대조할 칸이고, **본선까지 자체 실측으로 교체**해야 합니다.

완화책은 이미 계획에 들어 있습니다 — **3차가 2차(규칙 기반)를 넘지 못하면 그 사실을 실패 사례로 기재**합니다.
규칙으로 되는 일을 모델로 포장하지 않는 것이 이 팀이 지키는 선입니다.

- 신뢰도: 확실한 사실 (기획서 [표3] 주석이 스스로 명시한 한계)

### ⑦ 검증 겹 수를 4겹에서 3겹으로 줄임

공간블록 CV·비학교 recall@top-20%·lift는 유지하되,
**④ 문자열·표준필드·모델 3자 비교는 압축 일정에서 생략**했습니다.
[표3]에 3겹 기준임을 명시하지 않으면 기획서와 산출물이 어긋나 보입니다.
자기평가 편향 방지 장치가 한 겹 줄어든 것이기도 합니다.

- 신뢰도: 확실한 사실 (팀이 명시적으로 내린 축소 결정)

## 4. 일정/범위 리스크

### ⑧ 본선 구현 창구가 52시간(8/22 ~ 8/29)이고 버퍼가 0

이벤트 로그 스키마(**8/22 오후**) → 로그 API(8/24) → 세션 로그 답변(8/25 ~ 26) → 검증기(8/26 ~ 27) → 폐루프(8/28 ~ 29) → 지표 취합(8/31)이
**한 줄로 이어진 임계 사슬**입니다. 첫 칸이 반나절 늦으면 마지막 칸이 이틀 밀려 **코드 프리즈를 넘깁니다.**

4인 중 구현자는 둘(AI/RAG·Backend)뿐이고 **임계경로가 두 사람을 번갈아 지납니다** — 한쪽이 밀리면 반대쪽이 대기합니다.
그래서 Tech Lead의 스펙 3건(**8/22 스키마 리뷰 · 8/24 Q&A 계약·검증기 스펙**)이 먼저 내려와야 하고,
AI/RAG 쪽에는 **잘라낼 카드를 미리 정해 두었습니다**
(→ [역할_일정/03-AI-RAG-프론트엔드.md](../역할_일정/03-AI-RAG-프론트엔드.md) 압축 카드).

또 **8/29 하루에 세 가지가 겹칩니다** — 마지막 구현 · 시연 환경 배포(PM 단독) · 코드 프리즈. 8/30이 휴무라 넘길 수 없습니다.
**구현이 끝나는 날에 얼려서 배포까지 합니다.**

- 신뢰도: 확실한 사실 (계획 자체의 구조)

## 5. 데이터/프라이버시 리스크

### ⑨ 장애 여부 등 민감정보 처리

장애 여부는 개인정보보호법상 민감정보로 분리 동의·암호화가 필요합니다.
기획서 v3는 동의를 **최소/표준/확장 3단계**로 나누고 민감정보는 별도 동의로 두었으며,
파기·동의 이력을 **개인정보 없는 이벤트 저널**로 설계했습니다 — 다만 **예선 시점 미구현**입니다.
모델 학습에도 개인정보를 쓰지 않습니다.

위치정보는 **받되 저장하지 않는** 구조입니다.
`POST /v1/shelters/search`가 좌표를 받아 그 요청 처리에만 쓰고, 세션·이벤트 로그·DB·파일 어디에도 쓰지 않습니다.
「받지 않는다」가 아니라 「무저장·무로깅」이며 — 원 기획서 4장의 「받지 않는다」와 어긋나는 점은
[ADR-0010](../adr/0010-m3-no-storage-not-no-receipt.md)(제안 상태, 검토 중)에 기록했습니다.
검증은 "지우는지"가 아니라 "저장·로깅 지점이 있는지"를 스캔으로 확인합니다
(→ [개인정보_체크리스트.md](개인정보_체크리스트.md)).

- 신뢰도: 높은 신뢰 (미구현 항목은 확실한 사실)

## 6. 엔지니어링 관행 리스크 (자체 조사 문서 기준)

### ⑩ 구조 세팅을 미루면 나중에 리팩터링 비용 발생

저장소 구조는 **단일 모노레포**로 확정했고(근거: [개발자_가이드.md](개발자_가이드.md) 7절),
그 안에서 AI(`apps/ai-engine`)를 자체 Dockerfile·README를 가진 독립 배포 엔진으로 유지하기로 했습니다.
스캐폴딩은 끝났습니다 — 세 앱과 계약·CI·compose가 자리를 잡았고,
`apps/ai-engine`은 자체 Dockerfile로 독립 배포 가능함을 증명합니다.

남은 위험은 형태가 바뀌었습니다.
구조를 못 만드는 것이 아니라, **시간 압박 속에서 그 경계를 우회하는 것**입니다.
`apps/backend`가 HTTP 대신 `ai_engine`을 직접 import 하는 한 줄이면
"독립 배포 엔진"이라는 성질이 조용히 사라지고, 그 한 줄은 테스트를 통과합니다.
방어 장치는 셋입니다 — AGENTS.md의 아키텍처 규칙(교차 import 금지),
`CODEOWNERS`의 경로별 리뷰어, 그리고 계약이 `packages/contracts`에 먼저 존재해야 한다는 규약.
리뷰에서 이 셋을 실제로 확인하지 않으면 규칙만 남습니다.

- 신뢰도: 추정

## 종합 의견

재난·안전 도메인 해커톤 프로젝트는 심사에서 "정량 지표의 재현 가능성"만큼
"실패 시나리오를 얼마나 정직하게 설계했는가"를 높게 평가하는 경향이 있습니다.
본선 준비 구간에서 시연 실패 확률을 가장 크게 줄이는 지점은 ①③⑥⑧입니다 —
**FCM 실기기 도달(8/22 오후)**, **지연시간 p95 실측(8/29)**,
**부합도 3차 자체 실측치 확보(8/24)**, **8/22 오후 스키마 확정**.
넷 중 셋이 첫 사흘에 몰려 있는 것은 우연이 아니라, 그 뒤 전부가 여기에 매달려 있기 때문입니다.

한편 ②(실패 모드)는 리스크인 동시에 **이 팀의 차별점**입니다.
역대 수상작 대부분이 성공 경로만 시연하므로,
실패 모드 5케이스를 발표 중에 실연하는 것 자체가 신뢰도의 근거가 됩니다
(→ [역할_일정/01-기획총괄.md](../역할_일정/01-기획총괄.md) 8/28).
