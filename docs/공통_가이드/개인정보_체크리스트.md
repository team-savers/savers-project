일정: [역할_일정/06-QA-보안.md](../역할_일정/06-QA-보안.md) S1-1. 관련 승인 항목:
[외부_승인.md](외부_승인.md) E절. 관련 리스크: [리스크.md](리스크.md) ⑨.

가이드라인·고시**를 이 프로젝트의 구체적 데이터 필드(위치정보, 장애 여부)에 매핑한
점검표입니다([역할_가이드/06-QA-보안.md](../역할_가이드/06-QA-보안.md)의 "자체 법률 해석 대신
공개된 가이드라인/체크리스트 활용" 원칙). S1-2(8/3~8/6)에서 실제 점검 스크립트(로그·DB
스캔)로 각 항목을 자동 검증할 때 이 표를 기준 삼습니다.

> ⚠️ **신뢰도 표기**: 아래 근거 법령·고시명은 높은 신뢰(공개 검색으로 확인)이나, 조항 번호·시행일은
> 시간이 지나면 개정될 수 있습니다. 실제 적용 전 [국가법령정보센터](https://www.law.go.kr)와
> [개인정보보호위원회](https://www.pipc.go.kr) 최신본으로 재확인하세요 — 이 표 자체가 법률
> 자문을 대체하지 않습니다.

## 1. 위치정보 — 위치정보의 보호 및 이용 등에 관한 법률(위치정보법)

SAVERS의 비타협 제약("상시 위치 추적 없음", [AGENTS.md](../../AGENTS.md))이 실제로
위치정보법의 개인위치정보 보호 의무와 일치하는지 확인하는 항목입니다.

| # | 점검 항목 | 근거 | 검증 방법(S1-2 스크립트 대상) |
|---|---|---|---|
| P1 | 개인위치정보 수집 전 **동의**를 받았는가 (알림 링크 진입 = 위치 조회 발생 시점에 별도 고지) | 위치정보법 제15조·제18조 | 알림 진입 플로우에 동의 UI/문구가 위치 조회 API 호출보다 먼저 실행되는지 코드 경로 확인 |
| P2 | 수집 목적을 달성한 즉시 **파기**하는가 (요청-응답 세션 범위를 벗어나 저장하지 않음) | 위치정보법 제16조 | 로그·DB 스캔: 응답 후 원본 좌표(위경도)가 어떤 테이블/로그 파일에도 남아있지 않은지 자동 확인 |
| P3 | 동의 철회 시 **지체 없이 파기**하는가 | 위치정보법 제18조 | 세션 스코프 설계상 "저장 자체가 없음"이 철회 파기 요건을 자동 충족하는지 논리 검증 (저장이 없으면 파기할 대상도 없음 — 설계로 요건을 무력화하는 방식) |
| P4 | 위치정보 수집·이용·제공 **사실 확인자료**를 법정 기간 보관하는가 (원본 좌표와는 별개로, "언제 누구 위치를 조회했는지"의 메타 로그) | 위치정보법 제16조제2항 | 원본 좌표 없이 조회 시각·사용자 ID만 남기는 감사 로그가 있는지 확인 — 이 메타 로그 자체는 "개인위치정보"가 아니므로 즉시 파기 대상 아님 |

## 2. 장애 여부 등 민감정보 — 개인정보 보호법 제23조

| # | 점검 항목 | 근거 | 검증 방법(S1-2 스크립트 대상) |
|---|---|---|---|
| S1 | 장애 여부를 **일반 개인정보 동의와 분리된 별도 동의**로 수집하는가 | 개인정보 보호법 제23조 | 등록(보호자/복지관/지자체 대행) 플로우에서 동의 항목이 "일반 동의"와 "민감정보 동의"로 UI/데이터 모델상 분리돼 있는지 확인 |
| S2 | 민감정보 수집·이용 목적이 구체적으로 명시돼 있는가 (예: "개인 맞춤 행동지침 생성"으로 한정, 포괄 동의 아님) | 개인정보 보호법 제15조·제23조 | 개인정보처리방침·동의 문구 텍스트 검토 (자동화 어려움 — 사람이 문구 존재 여부만 체크) |
| S3 | 민감정보를 **저장 시 암호화**하는가 | [개인정보의 안전성 확보조치 기준](https://www.law.go.kr) (PIPC 고시) | DB 스캔: 장애 여부 필드가 평문으로 저장돼 있지 않은지 자동 확인 (컬럼 값이 암호문 형태인지) |
| S4 | 지자체·복지관 대행 등록 시 **위탁 근거**가 명확한가 (위탁자-수탁자 관계, 위탁 계약서 필수 기재사항) | 개인정보 보호법 제26조 | 대행 등록 플로우에 위탁 근거를 남기는 필드/문서가 있는지 확인 (자동화 어려움 — 운영 문서 존재 여부 체크) |
| S5 | 민감정보를 주고받는 **인증 없는 내부 경로가 외부에 노출되지 않는가** | [개인정보의 안전성 확보조치 기준](https://www.law.go.kr) (PIPC 고시) — 접근 통제 | **배포 시점 확인** — [배포_절차.md](배포_절차.md) 검증 ⑧(`POST /internal/alerts/dispatch` → `404`). 점검 스크립트로는 자동화 불가(기동된 VM 필요) |

### S5를 항목으로 세운 이유 (실제로 열렸던 적이 있습니다)

이 항목은 가정이 아니라 **한 번 열렸던 경로**입니다. 리허설 VM에서
`POST https://<호스트명>/internal/alerts/dispatch`가 **200을 돌려줬습니다**
([이슈 #25](https://github.com/team-savers/savers-project/issues/25), 2026-08-07).
Caddy TLS 종단이 들어오면서([PR #49](https://github.com/team-savers/savers-project/pull/49))
프록시가 백엔드 전체를 경로 제한 없이 넘겼고, `/internal` 라우터는 같은 공개 앱에 인증 없이
붙어 있었기 때문입니다. 그 한 번의 호출이 **실제 웹푸시 발송을 트리거**합니다.

노출 시 새는 것이 민감정보라 이 절에 둡니다 — ai-engine의 `/v1/generate`·`/v1/answer`는
인증이 없고 거주형태(`housing`)·이동능력(`mobility`)·독거 여부(`livesAlone`)·돌봄
필요(`care`)를 요청 본문으로 받습니다([ADR-0006](../adr/0006-generation-contract.md),
[packages/contracts/openapi.yaml](../../packages/contracts/openapi.yaml)).

현재 상태(3중 방어, 전부 코드에 있음):

| 층 | 무엇 | 근거 |
|---|---|---|
| 프록시 | `handle /internal/*` → `404`, `reverse_proxy` **앞에** 위치 | [infra/Caddyfile](../../infra/Caddyfile) |
| 바인딩 | backend·ai-engine 모두 `127.0.0.1`에만 바인딩 | [infra/docker-compose.yml](../../infra/docker-compose.yml) |
| 라우팅 | Caddy는 backend만 프록시 — ai-engine은 라우팅 대상이 아님 | 같은 Caddyfile 헤더 주석 |

⚠️ **QA 점검 포인트는 "코드가 그렇게 돼 있다"가 아니라 "배포된 VM에서 실제로 닫혀 있다"입니다.**
세 층 중 하나만 바뀌어도(예: Caddyfile에 정적 파일이나 새 서비스를 얹으면서 `handle` 순서가
밀리면) 조용히 열립니다. 그래서 코드 리뷰가 아니라 **배포 절차의 검증 단계**에 걸어 둡니다.
[배포_절차.md](배포_절차.md) 검증 ⑧이 그 자리이고, 본 VM을 세울 때마다 통과해야 합니다.

## 3. 개인정보처리방침 — PIPC 처리방침 작성지침

| # | 점검 항목 | 근거 | 검증 방법 |
|---|---|---|---|
| N1 | 처리방침에 수집 항목(위치정보 세션 단위, 장애 여부 등 민감정보)이 실제 구현과 **1:1로 일치**하는가 | PIPC 개인정보 처리방침 작성 가이드라인 | 처리방침 문서 vs 실제 DB 스키마/수집 필드 diff 확인 — 문서에 없는 필드를 수집하고 있지 않은지 |
| N2 | 위탁 사실(지자체/복지관 대행 등록)을 처리방침에 명시했는가 | 개인정보 보호법 제26조·PIPC 가이드라인 | 처리방침 텍스트 검토 |

## 4. S1-2로 넘기는 것 (오늘 범위 아님)

이 문서는 S1-1 DoD("점검 계획")입니다. 아래는 이 표를 근거로 S1-2(8/3~8/6)에서 작성할
**미저장·암호화 점검 스크립트**의 구체적 대상이며, 지금은 스켈레톤만 준비합니다:

- P2/S3: 로그·DB 자동 스캔 스크립트 (Backend의 미저장 구현 완료 후 실행 가능 — 선행 대기)
- 테스트 하네스 위치: `apps/backend/tests/`(스캔 대상이 backend_core 도메인 로직이므로) 또는
  운영 스크립트라면 `scripts/`. 앱 경계(backend_core는 api를 모름) 규칙을 지키는 형태로
  S1-2 착수 시 Tech Lead와 배치 위치를 확정합니다.
