# 개인정보·위치정보 준수 체크리스트 (QA/Security 점검 계획)

담당: 최혜리(QA/Security). 역할 정의: [역할_가이드/06-QA-보안.md](../역할_가이드/06-QA-보안.md) ·
일정: [역할_일정/06-QA-보안.md](../역할_일정/06-QA-보안.md) S1-1. 관련 승인 항목:
[외부_승인.md](외부_승인.md) E절. 관련 리스크: [리스크.md](리스크.md) ⑨.

이 문서는 QA가 자체적으로 법을 해석한 결과가 아니라, **개인정보보호위원회(PIPC)가 공개한
가이드라인·고시**를 이 프로젝트의 구체적 데이터 필드(위치정보, 장애 여부)에 매핑한
점검표입니다([역할_가이드/06-QA-보안.md](../역할_가이드/06-QA-보안.md)의 "자체 법률 해석 대신
공개된 가이드라인/체크리스트 활용" 원칙). S1-2(8/3~8/6)에서 실제 점검 스크립트(로그·DB
스캔)로 각 항목을 자동 검증할 때 이 표를 기준 삼습니다.

> ⚠️ **신뢰도 표기**: 아래 근거 법령·고시명은 높은 신뢰(공개 검색으로 확인)이나, 조항 번호·시행일은
> 시간이 지나면 개정될 수 있습니다. 실제 적용 전 [국가법령정보센터](https://www.law.go.kr)와
> [개인정보보호위원회](https://www.pipc.go.kr) 최신본으로 재확인하세요 — 이 표 자체가 법률
> 자문을 대체하지 않습니다.

## 1. 위치정보 — 위치정보의 보호 및 이용 등에 관한 법률(위치정보법)

SAVERS의 비타협 제약("상시 위치 추적 없음", [AGENTS.md](../../AGENTS.md))이 실제로
위치정보법의 개인위치정보 보호 의무와 일치하는지 확인하는 항목입니다.

| # | 점검 항목 | 근거 | 검증 방법(S1-2 스크립트 대상) |
|---|---|---|---|
| P1 | 개인위치정보 수집 전 **동의**를 받았는가 (알림 링크 진입 = 위치 조회 발생 시점에 별도 고지) | 위치정보법 제15조·제18조 | 알림 진입 플로우에 동의 UI/문구가 위치 조회 API 호출보다 먼저 실행되는지 코드 경로 확인 |
| P2 | 수집 목적을 달성한 즉시 **파기**하는가 (요청-응답 세션 범위를 벗어나 저장하지 않음) | 위치정보법 제16조 | 로그·DB 스캔: 응답 후 원본 좌표(위경도)가 어떤 테이블/로그 파일에도 남아있지 않은지 자동 확인 |
| P3 | 동의 철회 시 **지체 없이 파기**하는가 | 위치정보법 제18조 | 세션 스코프 설계상 "저장 자체가 없음"이 철회 파기 요건을 자동 충족하는지 논리 검증 (저장이 없으면 파기할 대상도 없음 — 설계로 요건을 무력화하는 방식) |
| P4 | 위치정보 수집·이용·제공 **사실 확인자료**를 법정 기간 보관하는가 (원본 좌표와는 별개로, "언제 누구 위치를 조회했는지"의 메타 로그) | 위치정보법 제16조제2항 | 원본 좌표 없이 조회 시각·사용자 ID만 남기는 감사 로그가 있는지 확인 — 이 메타 로그 자체는 "개인위치정보"가 아니므로 즉시 파기 대상 아님 |

| # | 점검 항목 | 근거 | 검증 방법(S1-2 스크립트 대상) |
|---|---|---|---|
| S1 | 장애 여부를 **일반 개인정보 동의와 분리된 별도 동의**로 수집하는가 | 개인정보 보호법 제23조 | 등록(보호자/복지관/지자체 대행) 플로우에서 동의 항목이 "일반 동의"와 "민감정보 동의"로 UI/데이터 모델상 분리돼 있는지 확인 |
| S2 | 민감정보 수집·이용 목적이 구체적으로 명시돼 있는가 (예: "개인 맞춤 행동지침 생성"으로 한정, 포괄 동의 아님) | 개인정보 보호법 제15조·제23조 | 개인정보처리방침·동의 문구 텍스트 검토 (자동화 어려움 — 사람이 문구 존재 여부만 체크) |
| S3 | 민감정보를 **저장 시 암호화**하는가 | [개인정보의 안전성 확보조치 기준](https://www.law.go.kr) (PIPC 고시) | DB 스캔: 장애 여부 필드가 평문으로 저장돼 있지 않은지 자동 확인 (컬럼 값이 암호문 형태인지) |
| S4 | 지자체·복지관 대행 등록 시 **위탁 근거**가 명확한가 (위탁자-수탁자 관계, 위탁 계약서 필수 기재사항) | 개인정보 보호법 제26조 | 대행 등록 플로우에 위탁 근거를 남기는 필드/문서가 있는지 확인 (자동화 어려움 — 운영 문서 존재 여부 체크) |

## 4. 점검 스크립트 — `scripts/check_privacy.py`

위 표를 실행 가능한 검사로 옮긴 것이 [`scripts/check_privacy.py`](../../scripts/check_privacy.py)
입니다(S1-2 DoD, Stage 1 Exit Criteria S1-E6). 배치 위치는 `scripts/`입니다 —
라이브 검사가 기동된 서비스에 **HTTP로만** 접근하므로(앱 패키지를 import 하지 않음)
`apps/backend/tests/`에 두면 앱 경계 규칙을 어기고, required pytest 매트릭스가
스택 없이 이 검사를 수집하게 됩니다. 표준 라이브러리만 쓰므로 venv 없이 돕니다.

```bash
python3 scripts/check_privacy.py                                  # 정적 검사만
python3 scripts/check_privacy.py --base-url http://localhost:8000 \
    --log <서버로그> --out report.json                             # 정적 + 라이브
```

| 항목 | 검사 방식 | 현재 결과 |
|---|---|---|
| P1 | 정적 — `getCurrentPosition` 호출이 동의 분기를 소유한 두 파일 안에만 있는지 + `watchPosition` 0건 | PASS |
| P2 | 라이브 — 센티널 좌표로 검색 후 ①응답 반향 ②`Cache-Control: no-store` ③세션·보호자 재조회 ④서버 로그 네 곳 확인 | PASS |
| P3 | P2가 전부 통과일 때만 "저장이 없으니 파기 대상도 없음"을 유도 | PASS (유도) |
| P4 | 좌표 없는 접근 기록 존재 확인 | **WARN** — 법정 보관 기간을 갖춘 전용 감사 로그는 미구현 |
| S1 | 정적 — `ConsentFlags`가 개인정보/민감정보/위치정보 독립 필드인지 + `/ops` 분리동의 UI | PASS |
| S3 | — | **SKIP** — 등록 저장소(`backend_core/registry.py`의 `ResidentRegistry`)가 인메모리라 스캔할 DB가 없습니다. 근거는 [ADR-0007](../adr/0007-walking-skeleton.md) "해결되지 않은 문제" 표의 **인메모리 상태** 항목(⚠️ 미해결). 실저장소를 붙이는 PR이 이 SKIP을 검사로 바꿔야 합니다 — [후속_과제.md](후속_과제.md) 4번(Firestore 릴레이 접근 통제)과는 다른 저장소입니다 |
| S2·S4·N1·N2 | — | **SKIP** — 이 표가 사람 검토로 지정한 문구·문서 항목 |

**SKIP·WARN은 통과가 아니라 "검사되지 않음"입니다.** 스크립트가 출력에 그렇게 명시하고,
못 잰 항목을 PASS로 세지 않습니다(평가 하네스의 `null ≠ 0` 규약과 같은 축).

두 가지 설계 판단이 결과를 읽는 방식을 가릅니다:

- **로그 검사는 카나리아를 함께 요구합니다.** 같은 로그에서 검색 요청의 접근 기록이
  **보여야** 좌표 부재가 증거가 됩니다. 엉뚱한 로그를 긁고 "좌표 없음 = 통과"가 되는
  무음 실패를 막기 위해, 접근 기록이 없으면 PASS가 아니라 FAIL입니다.
- **센티널 좌표**는 이 스크립트만 아는 소수부 자릿수를 씁니다. 실좌표처럼 생겨 서버가
  다르게 처리하지 않으면서, 로그·응답 어디에 남아도 부분 문자열로 잡힙니다.

CI는 [`e2e.yml`](../../.github/workflows/e2e.yml)의 종단 관통 잡에 붙어 있습니다(비필수).
라이브 검사가 기동된 스택과 그 스택의 로그를 둘 다 요구하고, 그 둘이 그 잡에만 있기
때문입니다. 보고서는 `privacy-check-report` 아티팩트로 올라갑니다.
