# QA/Security 역할 매뉴얼

## 담당 범위

민감정보 최소수집·암호화, 가드레일 검증, 웹푸시 대체경로, E2E 통합 테스트, 시연 자료.  
다른 5개 역할의 산출물이 실제로 설계 원칙(특히 [CLAUDE.md](../../CLAUDE.md)의 비타협 제약)을 지키는지 검증하는 역할입니다.

## 직접 구현해야 하는 부분

- **민감정보 암호화·최소수집 정책의 실제 구현/검증** — 위치정보 미저장, 장애 여부 등 민감정보 분리 동의·암호화가  
    코드 수준에서 실제로 지켜지는지 확인하는 점검 로직(예: 로그·DB 스캔 스크립트로 위치 원본 좌표가 남아있지 않은지 자동 확인).
- **가드레일 검증 테스트 스위트** — 악의적 명령어 주입, 원문 외 내용 생성 유도 등 적대적 입력에 대해 가드레일이 실제로 막는지 확인하는 테스트 케이스 설계.
- **환각 억제율 on/off 비교 테스트 하네스** — 동일 평가셋을 가드레일 켠 상태/끈 상태로 실행해  
    결과를 비교하는 실험 관리(측정 로직 자체는 AI/RAG Engineer와 공유하되, 독립적 검증 관점에서 재실행).
- **E2E 통합 테스트 시나리오** — 사전 등록 → 재난 감지 → 매칭 → 위치 확인 → 생성 → 발송까지 전체 파이프라인을 관통하는 테스트,  
    특히 실패 모드(API 장애, 위치 실패, 가드레일 이탈) 케이스.
- **실패 시나리오 문서화(시연 자료)** — 데모에서 성공 사례만 보여주는 것이 아니라,  
    실패 시 안전장치가 작동함을 보여줄 수 있는 시연 대본.  
    [리스크.md](../공통_가이드/리스크.md) ②에서 지적한 "성공 사례만 보여줄 때의 신뢰성 문제"에 대한 직접 대응.

## 기능 통합이 필요한 부분

- **암호화 표준** — 자체 암호화 알고리즘을 만들지 않고 TLS, KMS 등 표준 암호화 도구·클라우드 서비스 통합.
- **웹푸시 대체 경로 테스트** — FCM 등 기존 푸시 인프라의 장애 시뮬레이션 도구 활용.
- **개인정보보호법 준수 체크리스트** — 자체 법률 해석 대신 공개된 개인정보보호위원회 가이드라인/체크리스트 활용.
- **E2E 테스트 프레임워크** — Playwright, pytest 등 기존 테스트 도구로 시나리오만 작성.

## 다른 역할과의 인터페이스

| 받는 것 | 역할 | 주는 것 |
|---|---|---|
| 가드레일 로직 구현체 | Tech Lead | 적대적 테스트 케이스, 검증 결과 |
| 위치 미저장 구현 | Backend/Infra | 검증 스크립트, 통과 여부 |
| 근거 일치율 측정 스크립트 | AI/RAG Engineer | 독립 재검증 결과 |
| 알림 발송 UI/발송 로직 | Frontend/UX | E2E 테스트 시나리오 |
| 테스트·보안 점검 결과 | PM | 시연 가능 여부 최종 신호 |

## 관련 리스크

- **② 안전 관련 오작동** — 가장 직접적인 소관. 실패 모드를 사전에 발견하고 시연에서 정직하게 다뤄야 함.
- **⑨ 민감정보 처리** — 암호화·최소수집 원칙의 실제 준수 여부를 검증하는 최종 관문.
- **⑥·⑦ 평가지표 신뢰성** — 독립적인 재검증(생성 모델과 다른 채점 방식 확인)으로 자기평가 편향을 막는 역할.
- **① 카카오 알림톡 템플릿 제약** — 웹푸시 대체 경로가 실제로 장애 상황에서 작동하는지 검증.

## 관련 외부 승인

- **E. 개인정보/법적 검토** — 위치정보(세션 단위)·장애 여부(민감정보) 수집·이용 동의 문구와 개인정보처리방침이 실제로 설계·구현됐는지 검증하는 최종 관문.  
    장애 여부는 개인정보보호법상 **분리 동의**가 원칙이며,  
    지자체·복지관 대리등록 시 위탁 근거가 명확한지 확인(신청·수립 주체는 PM과 공동, 준수 검증은 QA/Security).
- **C. 웹푸시(FCM)** — 알림톡 실패 시 보조 채널이 실제로 발신되는지 장애 시뮬레이션으로 검증(FCM 프로젝트·iOS 제약 확인은 Frontend와 공유).
