각 매뉴얼은 동일한 구조를 따릅니다.

1. **담당 범위** — 이 역할이 책임지는 영역
2. **직접 구현해야 하는 부분** — 외부 모듈로 대체할 수 없는, 이 역할 고유의 구현 작업
3. **기능 통합이 필요한 부분** — 외부 API/오픈소스/다른 역할의 산출물을 가져와 엮는 작업
4. **다른 역할과의 인터페이스** — 무엇을 주고, 무엇을 받는지
5. **관련 리스크** — [리스크.md](../공통_가이드/리스크.md) 중 이 역할이 직접 관리해야 할 항목
6. **관련 외부 승인** — [외부_승인.md](../공통_가이드/외부_승인.md) 중 이 역할이 신청·확인 주체가 되는 항목

| Backend | 김도혁 | [04-백엔드.md](04-백엔드.md) |

포지션 경계에서 가장 자주 헷갈리는 두 가지를 먼저 못박습니다.

- **인프라는 PM이 가집니다.** `infra/`·배포·서버 운영·계측이 PM 소관이고, Backend는 애플리케이션 코드만 씁니다.
  본선 당일 현장 인프라 **실행 대응은 Backend**입니다 — PM은 무대에 있어 서버를 볼 수 없기 때문입니다.
  **판단은 PM, 손은 Backend.** 셸 권한 3인(김도혁·신호정·안은남)이 이것을 전제로 합니다
  ([ADR-0009](../adr/0009-ssm-session-manager.md) 2026-08-26 개정).
  시연 환경 배포(8/29)는 **PM 단독**으로 합니다 — 인프라가 PM 소관이 되었고, 그 시각 Backend는 폐루프 마감과 겹칩니다.
  대신 PM이 **8/26에 혼자 한 바퀴 돌아 보는 것**이 선행 조건입니다.
- **Tech Lead는 코드를 쓰지 않습니다.** 설계·계약·스펙 정의와 판정만 합니다.
  구현자가 자기 설계를 스스로 승인하지 않게 만드는 것이 이 분리의 목적이고,
  코드 프리즈 판정을 이해관계 없이 내릴 수 있는 근거이기도 합니다.
- **조건부 항목의 컷오프 판정은 PM이 합니다.** 자를 때 달라지는 것(발표 대본·[표3] 문구·지표 취합)이
  전부 PM 소관이고, 예비 시간을 들고 있는 사람도 PM이라 **「자를까 / 받아줄까」를 같은 자리에서** 정할 수 있습니다.
  Tech Lead는 「남은 시간으로 끝나는 상태인가」에 대한 **기술 의견**을 댑니다.

## 전체 그림

이 매뉴얼이 "누가·무엇을"이라면, 각 역할이 그 작업을 **언제** 하는지(시간축·구간·마감)는 [역할_일정/](../역할_일정/README.md)에 정리돼 있으니 함께 보세요.
역할 간 데이터가 어떻게 넘어가는지는 [아키텍처.md](../공통_가이드/아키텍처.md)의 파이프라인·모듈 다이어그램을 참고하세요.
기획서 v3의 핵심 기술 셋과 역할의 대응 관계는 다음과 같습니다.

- 핵심기술① 대피소 부합도 모델(PU 학습·SHAP) → **AI 모델·RAG·프론트엔드**
- 핵심기술② 침수 회피 경로(**OSMnx+networkx** · 링크 R0 ~ R3) → **Backend** — 기획서는 OSRM으로 적었으나 본선 구현본은 A안입니다([정정 항목](../공유_문서/서비스_기획서.md))
- 핵심기술③ 보호자 상황 확인 RAG → **AI 모델·RAG·프론트엔드**(생성부·대조 검증기) + **Backend**(이벤트 로그·폐루프 오케스트레이션)
- 사용자 화면 5단계(특보 수신 → 정보 입력 → 상황 분기 → 행동 권고 → 경로 안내) → **AI 모델·RAG·프론트엔드**
- 인프라·배포·계측·품질 판정 → **PM · QA/보안 · 인프라**
- 모듈 간 계약·검증기 규칙·폐루프 상태 전이 스펙 → **Tech Lead**
