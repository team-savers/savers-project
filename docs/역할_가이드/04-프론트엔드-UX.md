# Frontend/UX 역할 매뉴얼

## 담당 범위

PWA·알림톡 연동, 대화형 챗봇 UI/UX, 접근성(다국어·쉬운 글·음성) 구현, 가독성 지표 계측.  
모듈 4(무설치 사용자 터미널)의 실무 구현을 책임집니다.

프론트엔드 배포 형태는 **PWA(웹)로 확정**되어 있으며 네이티브·하이브리드는 제외입니다(→ [ADR-0004](../adr/0004-pwa-over-native.md)).  
"무설치 사용자 터미널"·"당사자 설치 부담 없음" 원칙과 정합하고,  
알림톡 딥링크 → 브라우저 진입 → 위치 1회 확인 흐름이 웹 권한 모델과 일치하기 때문입니다.  
네이티브의 유일한 이점(백그라운드 위치)은 "상시 추적 금지" 원칙상 우리가 써서는 안 되는 기능이라 메리트가 없습니다.  
권장 스택은 **React + Vite + `vite-plugin-pwa`(Workbox 기반 SW/오프라인 캐싱)** 입니다.

## 직접 구현해야 하는 부분

- **Interactive Care 챗봇 대화 흐름/의도 분기 로직** — 사용자가 "도움"이라고 답장하는 등 추가 질의에 응답하는 시나리오는 세이버스 고유 설계이며,  
    오픈소스 챗봇 UI는 뼈대만 제공할 뿐 흐름 자체는 직접 만들어야 합니다.
- **접근성 통합 UX** — 쉬운 글 표시 + 음성 재생 버튼 + (필요시) 원문 대조 화면을 하나의 사용자 경험으로 엮는 작업.  
    개별 기능(TTS, 번역)은 외부 API지만, 조합 방식은 취약계층·외국인 근로자 각각의 사용성을 고려해 직접 설계해야 합니다.
- **가독성 지표 계측 훅** — 행정용어 치환율, "실행 가능한 단일 행동" 포함 여부를 프론트엔드 단에서 로깅하거나 검증할 수 있는 계측 지점.
- **알림톡/PWA 메시지 렌더링 어댑터** — [리스크.md](../공통_가이드/리스크.md) ①에서 지적한 대로,  
    알림톡이 변수 슬롯 기반 템플릿을 요구할 경우 자유생성 텍스트를  
    템플릿 변수(`#{장소}`, `#{행동}` 등)에 매핑하는 어댑터 로직이 필요할 수 있습니다.
- **알림톡 진입 랜딩(딥링크 → 개인화 페이지)** — 발송 자체는 백엔드가 대행사 API로 처리하므로,  
    프론트는 알림톡에 담긴 딥링크로 진입해 세션 토큰을 받고 개인화 페이지를 렌더하는 랜딩이 핵심입니다.  
    위치 권한 거부·실패 시 **등록 행정동 기반 매칭으로 degrade**(단일 실패점이 되지 않도록)하는 UX도 여기서 처리합니다.

## 기능 통합이 필요한 부분

- **PWA 서비스워커/오프라인 캐싱** — Workbox 등 기존 라이브러리로 상당 부분 대체 가능.
- **웹푸시 인프라** — Firebase Cloud Messaging(FCM) 등 외부 서비스 통합.  
    단, 알림톡을 1차 푸시 채널, 웹푸시를 보조 fallback으로 두는 구조라 iOS Safari 웹푸시 제약(A2HS PWA에서만 가능)은 우회됩니다.
- **카카오 알림톡 발송 대행사** — 발송은 백엔드가 담당하지만, 후보는 **솔라피(Solapi)/알리고(Aligo)** 이며 예선·데모(저볼륨)는 알리고,  
    대량 발송 전환 시 솔라피 할인구간을 재비교합니다(→ [구현_범위.md](../공통_가이드/구현_범위.md) 4절).  
    발신 프로필·템플릿 승인은 별도 행정 절차(PM/Backend와 조율).
- **TTS** — 클로바보이스, Google TTS 등 외부 API 통합.
- **번역** — 파파고 API, Google Cloud Translation 등 외부 API 통합.
- **채팅 UI 컴포넌트** — 오픈소스 채팅 UI 라이브러리로 뼈대 구성, 로직만 직접 연결.

## 다른 역할과의 인터페이스

| 받는 것 | 역할 | 주는 것 |
|---|---|---|
| 생성된 페르소나별 메시지 | Tech Lead | 렌더링/발송 결과, UX 피드백 |
| 위험구역·대피소 거리 정보(표시용) | Backend/Infra | 알림 화면 요구사항 |
| 가독성 지표 측정 결과 | PM / QA | UI 계측 데이터 |
| 알림톡 템플릿 승인 현황 | Backend/Infra | 프론트 렌더링 방식 조정 |

## 관련 리스크

- **① 카카오 알림톡 템플릿 사전승인 제약** — 가장 직접적인 소관. 예선 초반에 실제 승인 정책을 확인해야 함.
- **iOS PWA 웹푸시 제약** (기획서의 기술 리스크 선제 방어 항목, `리스크.md`에는 별도 번호 없음) —  
    iOS Safari의 백그라운드 위치·웹푸시 지원 제약을 실제 기기에서 검증 필요.
- **⑥ 목표 수치의 근거 박약** 중 메시지 명확성 지표 — 가독성 자동 채점 결과가 목표(치환율 90% 등)에 못 미칠 경우  
    UI 표시 로직으로 보완할 수 있는지 확인.

## 관련 외부 승인

- **C. 메시징/알림 채널 (리드타임 최장)** — 알림톡 발신 프로필·템플릿 사전 승인이 프론트 렌더링 방식을 좌우합니다.  
    LLM 자유생성 문장은 승인이 거부될 수 있어 변수 슬롯 설계가 강제될 수 있으므로,  
    **예선 초반에 실제 승인 정책을 확인**해야 렌더링 어댑터 설계를 확정할 수 있습니다(신청 주체는 Backend/PM, 프론트는 결과에 맞춰 렌더링 방식 조정).
- **C. 웹푸시(FCM) 발신 설정** — 보조 채널 검증을 위해 FCM 프로젝트 생성과 iOS 16.4+ Safari 웹푸시 제약 확인이 필요.
