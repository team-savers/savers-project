## 담당 범위

전체 마일스톤 관리, 파트 간 통합, 리스크 관리, 본선 발표·시연 총괄 **+ 품질/보안 심사 + 인프라 + 문턱값 실험**.  
코드를 직접 작성하는 역할이 아니라 **다른 3개 역할(Tech Lead·AI-RAG/프론트엔드·Backend)의 산출물이  
하나의 서비스로 맞물리도록 조율**하는 역할이며, 다른 5개 역할의 산출물이 실제로 설계 원칙  
(특히 [AGENTS.md](../../AGENTS.md)의 비타협 제약)을 지키는지 검증하는 역할도 겸합니다.

## 직접 구현해야 하는 부분

PM의 "구현"은 코드가 아니라 **의사결정 도구와 프로세스 산출물**입니다. 다음은 외부 툴로 대체하기보다 프로젝트 특성에 맞춰 직접 설계해야 합니다.

### 통합·일정

- **일정 의존관계 지도**: [아키텍처.md](../공통_가이드/아키텍처.md)의 6단계 파이프라인을 기준으로,  
    어떤 모듈이 먼저 끝나야 다음 모듈 개발이 가능한지 명시한 의존관계 표.  
    빠듯한 일정([리스크.md](../공통_가이드/리스크.md) ⑧)에서 병목을 조기에 발견하는 유일한 장치입니다.
- **모듈 간 인터페이스 확정 시점 관리**: 위치 매칭 엔진의 출력 스키마, RAG 검색 결과 포맷 등을  
    "언제까지 확정"할지 못박아야 통합 단계에서 충돌하지 않습니다.
- **리스크 트래킹**: [리스크.md](../공통_가이드/리스크.md)의 항목별로 담당자·완화 조치·확인 시점을 매핑한 리스크 대장.
- **시연 시나리오 및 예상 질의응답**: 킬러 데모(호우·도시침수 1종 × 페르소나 2 × 행정동 1곳)의 진행 스크립트와,  
    실패 모드가 발생했을 때 보여줄 대응(가드레일 오작동 시 폴백 등)을 사전에 문서화.
- **외부 승인 리드타임 추적**: [외부_승인.md](../공통_가이드/외부_승인.md)의 항목별 신청 주체·상태를 통합 추적.  
    개별 담당자에게 흩어진 신청 상태를 PM이 한 곳에서 봐야 병목을 조기 발견할 수 있습니다.

### QA/보안

- **민감정보 암호화·최소수집 정책의 실제 구현/검증** — 위치정보 미저장, 장애 여부 등 민감정보 분리 동의·암호화가  
    코드 수준에서 실제로 지켜지는지 확인하는 점검 로직(예: 로그·DB 스캔 스크립트로 위치 원본 좌표가 남아있지 않은지 자동 확인).
- **가드레일 검증 테스트 스위트** — 악의적 명령어 주입, 원문 외 내용 생성 유도 등 적대적 입력에 대해 가드레일이 실제로 막는지 확인하는 테스트 케이스 설계.
- **환각 억제율 on/off 비교 테스트 하네스** — 동일 평가셋을 가드레일 켠 상태/끈 상태로 실행해  
    결과를 비교하는 실험 관리(측정 로직 자체는 AI/RAG와 공유하되, 독립적 검증 관점에서 재실행).
- **E2E 통합 테스트 시나리오** — 사전 등록 → 재난 감지 → 매칭 → 위치 확인 → 생성 → 발송까지 전체 파이프라인을 관통하는 테스트,  
    특히 실패 모드(API 장애, 위치 실패, 가드레일 이탈) 케이스.
- **실패 시나리오 문서화(시연 자료)** — 데모에서 성공 사례만 보여주는 것이 아니라,  
    실패 시 안전장치가 작동함을 보여줄 수 있는 시연 대본.  
    [리스크.md](../공통_가이드/리스크.md) ②에서 지적한 "성공 사례만 보여줄 때의 신뢰성 문제"에 대한 직접 대응.

### 인프라

- **종단 지연시간 계측 인프라** — **OpenTelemetry 분산 트레이싱**으로 "API 수신 → 발송" 구간의 종단 지연·p95를 스팬 연결로 자동 측정하고,  
    집계·시각화는 OTel 백엔드(Grafana Tempo·Jaeger 등)를 활용합니다.  
    세이버스 고유 스팬·속성은 Backend가 파이프라인 단계에 얹습니다(→ [04-백엔드.md](04-백엔드.md), [구현_범위.md](../공통_가이드/구현_범위.md) 5절).
- **AWS 단일 VM(서울 리전) + docker-compose** — 예선/데모는 단일 VM에 전체 스택을 올려 운영하고,  
    배포·운영 절차를 README에 정리(심사 요건).  
    관리형 이중화(ALB·ASG·RDS Multi-AZ)는 확장 시로 유보하며  
    README에 전환 경로만 1줄 문서화(→ [ADR-0003](../adr/0003-single-vm-seoul.md)).
- **컴퓨트는 CPU 전용** — 생성(HyperCLOVA X)·임베딩이 외부 API 기반이라 GPU 인스턴스 불필요.  
    자체 서버는 CPU VM으로 구성하며, GPU는 오픈 LLM 자체 호스팅 전환 시에만 재검토.
- **본선 당일 실행은 Backend에 위임** — PM은 무대에 있어 발표 시간 동안 서버를 볼 수 없습니다.  
    인프라 **소유**는 PM이지만 그 시간의 **손은 Backend**입니다 — 판단은 PM, 실행은 Backend.

## 기능 통합이 필요한 부분

- **진행 상황 통합 리포팅**: 각 역할의 작업 상태를 하나의 대시보드/문서로 모으는 작업.  
    별도 도구(Notion, GitHub Projects, Jira 등 기존 협업 툴)를 그대로 활용하면 충분하며, 직접 만들 필요는 없습니다.
- **정량 지표 통합**: AI/RAG가 측정한 근거 일치율, Backend가 측정한 지연시간,  
    QA(PM 겸임)가 측정한 환각 억제율을 하나의 "정량 목표 대비 실측값" 표로 취합 — 측정 도구 자체는 각 역할이 만들고, PM은 결과를 모아 서사화합니다.
- **최종 발표자료**: 각 역할이 제공하는 다이어그램·수치·시연 화면을 하나의 스토리라인으로 통합.
- **암호화 표준** — 자체 암호화 알고리즘을 만들지 않고 TLS, KMS 등 표준 암호화 도구·클라우드 서비스 통합.
- **웹푸시 1차 경로·실패 모드 테스트** — 발송 측 장애는 기존 푸시 인프라의 장애 시뮬레이션 도구로 재현하되,  
    브라우저 알림 권한 거부와 iOS A2HS 미충족은 인프라 장애로 재현되지 않습니다 —  
    클라이언트 조건이므로 권한 재설정과 실기기 확인으로 나눠 검증합니다  
    (→ [ADR-0005](../adr/0005-webpush-primary-channel.md)의 `⚠️ 미해결` 항목).
- **개인정보보호법 준수 체크리스트** — 자체 법률 해석 대신 공개된 개인정보보호위원회 가이드라인/체크리스트 활용.
- **E2E 테스트 프레임워크** — Playwright, pytest 등 기존 테스트 도구로 시나리오만 작성.

## 다른 역할과의 인터페이스

| 받는 것 | 역할 | 주는 것 |
|---|---|---|
| 아키텍처 설계 초안, 리스크 목록, 가드레일 로직 구현체 | Tech Lead | 우선순위·일정 피드백, 적대적 테스트 케이스·검증 결과 |
| 근거 일치율/환각 억제율/가독성 지표 실측치, 측정 스크립트, 알림 발송 UI/로직 | AI-RAG·프론트엔드 | 평가 결과 취합·독립 재검증, 발표자료 반영, UX 데모 시나리오 조율, E2E 테스트 시나리오 |
| 지연시간·장애 실측치, 위치 미저장 구현 | Backend | 리스크 대장 업데이트, 검증 스크립트·통과 여부 |

## 관련 리스크

- **⑧ 일정 리스크** — 가장 직접적인 소관. 의존관계 지도와 버퍼 확보로 완화.
- **①·② (채널 제약, 안전 오작동)** — 기술 리스크지만, 데모/제출 일정에 영향을 주므로 조기 확인 여부를 PM이 추적해야 함.  
    특히 ②는 QA/보안 겸임으로서 가장 직접적인 소관이기도 합니다 — 실패 모드를 사전에 발견하고 시연에서 정직하게 다뤄야 합니다.
- **⑥·⑦ (평가지표 신뢰성)** — 심사 대응 논리를 PM이 최종 정리해야 하므로, 근거 부족 여부를 미리 파악하고 있어야 함.  
    독립적인 재검증(생성 모델과 다른 채점 방식 확인)으로 자기평가 편향을 막는 역할도 겸합니다.
- **⑨ 민감정보 처리** — 암호화·최소수집 원칙의 실제 준수 여부를 검증하는 최종 관문.
- **웹푸시 도달 실패** — 알림톡 템플릿 리스크는 소멸했고([ADR-0005](../adr/0005-webpush-primary-channel.md)),  
    그 자리에 **1차 채널 자체의 실패 모드**가 들어왔습니다.  
    ⚠️ 이건 "보조 채널이 잘 도는지"를 보는 항목이 **아닙니다** — 웹푸시가 1차이고 대체 채널이 없습니다.  
    검증 대상은 ADR-0005에 `⚠️ 미해결`로 남은 것들입니다: **알림 권한 거부 시 무엇이 남는가**(현재 답 없음),  
    **iOS 16.4+ 및 A2HS 미충족 단말에서 무엇이 보이는가**.  
    `리스크.md` 번호로 참조하지 않는 이유는 그 문서가 재작성 예정이기 때문입니다  
    ([이슈 #38](https://github.com/team-savers/savers-project/issues/38)).

## 관련 외부 승인

- **F. 해커톤 행정** — 참가신청서·기획서 제출 완료, **예선 제출본(~8/10 13:00, 실측 지표 반영판)** 과 본선 진출 통보 대기가 PM 직접 소관.
- **A·B (공공 API·위치/지도 API 승인)** — 신청 주체는 Backend지만,  
    리드타임이 길어 전체 일정을 좌우하므로 신청·승인 상태를 PM이 리스크 대장과 함께 추적.
- **C. 웹푸시(FCM)** — **1차 채널**의 발신 설정입니다. 발신 전 외부 심사가 없어 승인 대기 항목이 아니고,  
    PM(QA/보안 겸임)이 보는 것은 "심사가 났는가"가 아니라 **"배포본이 실제로 알림을 받을 수 있는 상태인가"** 입니다.  
    필요조건은 배포 URL 하나로 원격 점검할 수 있습니다 —  
    HTTPS·도달성·Firebase 앱 config·VAPID·서비스워커(+`sw.js` 안 config)·매니페스트 6항목.  
    ⚠️ 그 6개가 전부 통과해도 **"알림이 왔다"는 뜻은 아닙니다**(발송 측 자격증명·기기 권한은 원격에서 알 수 없음).  
    실기기 수신 확인은 별도이고, 특히 **앱이 닫힌 상태의 잠금화면 수신**이 시연에서 캡처할 경로입니다  
    (FCM 프로젝트·iOS 제약 확인은 AI-RAG·프론트엔드와 공유).
- **D. AWS 계정 / AI 플랫폼 계정** — 인프라 소유가 PM으로 넘어오며 AWS 계정 결제수단 등록 및  
    해커톤·스타트업 크레딧(AWS Activate 등) 신청 가능 여부 확인도 PM 소관이 됐습니다.  
    HyperCLOVA X(NCP) 계정 신청은 Tech Lead/AI-RAG와 공유.
- **E. 개인정보/법적 검토** — 개인정보처리방침·민감정보 동의 절차, 위치정보(세션 단위)·장애 여부(민감정보)  
    수집·이용 동의 문구가 실제로 설계·구현됐는지 검증하는 최종 관문까지 PM(QA/보안 겸임) 단독 소관.  
    장애 여부는 개인정보보호법상 **분리 동의**가 원칙이며,  
    지자체·복지관 대리등록 시 위탁 근거가 명확한지 확인(실서비스 확장 시 협의 주체로서도 PM이 관리).
