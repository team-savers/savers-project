# PM 역할 매뉴얼

## 담당 범위

전체 마일스톤 관리, 파트 간 통합, 리스크 관리, 본선 발표·시연 총괄. 코드를 직접 작성하는 역할이 아니라  
**다른 5개 역할의 산출물이 하나의 서비스로 맞물리도록 조율**하는 역할입니다.

## 직접 구현해야 하는 부분

PM의 "구현"은 코드가 아니라 **의사결정 도구와 프로세스 산출물**입니다. 다음은 외부 툴로 대체하기보다 프로젝트 특성에 맞춰 직접 설계해야 합니다.

- **일정 의존관계 지도**: [아키텍처.md](../공통_가이드/아키텍처.md)의 6단계 파이프라인을 기준으로,  
    어떤 모듈이 먼저 끝나야 다음 모듈 개발이 가능한지 명시한 의존관계 표.  
    5주라는 빠듯한 일정([리스크.md](../공통_가이드/리스크.md) ⑧)에서 병목을 조기에 발견하는 유일한 장치입니다.
- **모듈 간 인터페이스 확정 시점 관리**: 위치 매칭 엔진의 출력 스키마, RAG 검색 결과 포맷 등을  
    "언제까지 확정"할지 못박아야 통합 단계에서 충돌하지 않습니다.
- **리스크 트래킹**: [리스크.md](../공통_가이드/리스크.md)의 항목별로 담당자·완화 조치·확인 시점을 매핑한 리스크 대장.
- **시연 시나리오 및 예상 질의응답**: 킬러 데모(호우·도시침수 1종 × 페르소나 2 × 행정동 1곳)의 진행 스크립트와,  
    실패 모드가 발생했을 때 보여줄 대응(가드레일 오작동 시 폴백 등)을 사전에 문서화.
- **외부 승인 리드타임 추적**: [외부_승인.md](../공통_가이드/외부_승인.md)의 항목별 신청 주체·상태를 통합 추적.  
    특히 리드타임이 가장 긴 **C(알림톡 채널·발신 프로필·템플릿 승인)** 와 **A(공공 API 승인)** 는  
    예선 개시 직후(7/27~) 최우선으로 신청돼야 8/6 예정 "알림톡·PWA 통합" 일정이 밀리지 않으므로,  
    개별 담당자에게 흩어진 신청 상태를 PM이 한 곳에서 봐야 병목을 조기 발견할 수 있습니다.

## 기능 통합이 필요한 부분

- **진행 상황 통합 리포팅**: 각 역할의 작업 상태를 하나의 대시보드/문서로 모으는 작업.  
    별도 도구(Notion, GitHub Projects, Jira 등 기존 협업 툴)를 그대로 활용하면 충분하며, 직접 만들 필요는 없습니다.
- **정량 지표 통합**: AI/RAG Engineer가 측정한 근거 일치율, Backend/Infra가 측정한 지연시간,  
    QA가 측정한 환각 억제율을 하나의 "정량 목표 대비 실측값" 표로 취합 — 측정 도구 자체는 각 역할이 만들고, PM은 결과를 모아 서사화합니다.
- **최종 발표자료**: 각 역할이 제공하는 다이어그램·수치·시연 화면을 하나의 스토리라인으로 통합.

## 다른 역할과의 인터페이스

| 받는 것 | 역할 | 주는 것 |
|---|---|---|
| 아키텍처 설계 초안, 리스크 목록 | Tech Lead | 우선순위·일정 피드백 |
| 근거 일치율/환각 억제율 실측치 | AI/RAG Engineer | 평가 결과 취합, 발표자료 반영 |
| 접근성·가독성 지표 | Frontend/UX | UX 데모 시나리오 조율 |
| 지연시간 실측치, 인프라 장애 이력 | Backend/Infra | 리스크 대장 업데이트 |
| E2E 테스트 결과, 보안 점검 리포트 | QA/Security | 시연 가능 여부 최종 판단 |

## 관련 리스크

- **⑧ 5주 일정 리스크** — 가장 직접적인 소관. 의존관계 지도와 버퍼 확보로 완화.
- **①·② (알림톡 승인, 안전 오작동)** — 기술 리스크지만, 데모/제출 일정에 영향을 주므로 조기 확인 여부를 PM이 추적해야 함.
- **⑥·⑦ (평가지표 신뢰성)** — 심사 대응 논리를 PM이 최종 정리해야 하므로, 근거 부족 여부를 미리 파악하고 있어야 함.
