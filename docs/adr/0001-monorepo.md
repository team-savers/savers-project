# ADR-0001: 저장소 구조는 단일 모노레포로 한다

- **상태**: 승인 (Accepted)
- **날짜**: 2026-07-25
- **결정자**: 신호정 (Tech Lead)
- **관련 문서**: [개발자_가이드.md](../공통_가이드/개발자_가이드.md) 7절, [아키텍처.md](../공통_가이드/아키텍처.md) 4절, [리스크.md](../공통_가이드/리스크.md) ⑩

## 배경 (Context)

팀 자체 조사(`docs/참고_자료/KDT해커톤_수상작_GitHub_레포_전수조사.pdf`)에서 상위 입상팀은 하나의 GitHub org 아래
FE/BE/AI(/Infra/Data)로 레포를 분리 운영하는 패턴이 확인되었고, 초기 계획은 이 형식을 그대로 따르는 것이었다.

재검토 결과, 조사의 **본질적 결론**은 "레포를 여러 개로 쪼개라"(형식)가 아니라
**"AI를 인라인 API 호출이 아니라 독립적으로 배포 가능한 엔진으로 두고, 배포·운영 문서를 README에 정리하라"(본질)** 였다.
멀티레포는 그 본질을 달성하는 여러 구현 중 하나일 뿐이다.

우리 팀의 제약 조건:

- 인원 6인, 해커톤 단기 일정(예선 2026-07-27 시작, 본선 9월 초)
- Tech Lead 초반 집중 체제 → 후반에 cross-repo 통합 부채가 남으면 팀 전체가 정체될 위험
- 계층 간 계약(위치매칭 → RAG → 생성 → 발송)이 초반에 자주 바뀔 것으로 예상됨

멀티레포를 택할 경우의 비용: 문서·인프라 설정 중복과 드리프트, cross-repo PR 조율,
레포마다 반복되는 온보딩, 계약 1건 변경 시 여러 레포 동시 수정.

## 결정 (Decision)

**단일 모노레포**를 채택한다. 단, AI는 모노레포 **내부에서 독립 배포 가능한 서비스**로 유지해
조사에서 확인된 본질 조건을 충족시킨다.

```
savers/
  apps/
    frontend/              # PWA
    backend/               # FastAPI (데이터 수집·위치 매칭)
    ai-engine/             # 독립 배포: 자체 Dockerfile + README + 배포 스크립트
  packages/
    contracts/             # OpenAPI 스펙 + 공용 스키마 (단일 진실 공급원, SSOT)
  infra/                   # docker-compose, .env 템플릿, AWS IaC
  docs/                    # ADR(docs/adr/), 배포·운영 가이드
  .github/workflows/       # path filter로 계층별 CI 분리
  CODEOWNERS               # 폴더별 소유자
```

## 결과 (Consequences)

**긍정**

- 문서·인프라·env가 `infra/`·`docs/` 한 곳에 존재 → 중복과 드리프트 제거
- `docker-compose up` 한 번으로 전체 스택 로컬 구동, 온보딩 1회
- 계층에 걸친 변경을 단일 PR로 atomic 반영 → 계약 변경 비용 최소화(초반 잦은 변경에 유리)

**부정 / 완화**

| 리스크 | 완화 |
|---|---|
| 한 레포에 모든 변경이 몰려 소유권이 흐려짐 | `CODEOWNERS` + 브랜치 보호로 폴더별 소유권 분리 |
| CI가 전체 빌드로 비대해짐 | `.github/workflows`에서 `paths:` 필터로 계층별 독립 파이프라인 구성 |
| "AI 독립 배포"가 흐려져 인라인 호출로 축소 | `apps/ai-engine`에 자체 Dockerfile·README·배포 스크립트 **필수** ([리스크.md](../공통_가이드/리스크.md) ⑩) |
| 조사 패턴(멀티레포)과 형식이 달라짐 | 심사가 보는 실질(AI 독립 모듈 + 배포 문서 존재)은 모노레포에서도 충족 |

## 검토했으나 채택하지 않은 대안

1. **org + 멀티레포(FE/BE/AI/Infra)** — 조사 패턴 그대로. 6인·단기 일정에서 관리비용과 통합 부채가 이득을 초과.
2. **하이브리드(infra·docs 허브 레포 + AI 별도 레포)** — 멀티레포 비용을 일부 줄이지만 여전히 cross-repo 조율이 필요하고 모노레포보다 무겁다.

## 재검토 조건

팀 규모가 커지거나 계층별 배포 주기가 확연히 달라지는 경우에만 재검토한다.
그 전에는 org + 멀티레포로 재분할하지 않는다.
