# ADR-0023: 발송 채널은 명시 설정으로 고르고, 실발송 자격증명은 기동 시점에 검증한다

- **상태**: 제안 (Proposed) - 2026-08-28 작성.
  2026-08-28 오후 팀 채팅에서 김도혁 (Backend) 이 FCM 실발송 배선에 앞서
  결정 2건을 물었다.
  (1) `FCM_SERVICE_ACCOUNT_JSON` 이라는 이름을 파일 경로 계약으로 그대로 둘지,
  아니면 설정 규칙에 맞춰 새 이름으로 정리할지.
  (2) 자격증명이 없을 때 앱을 중단할지,
  아니면 명시적인 개발 모드에서만 기록 전용 발송기를 허용할지.
  Backend 는 이 두 결정 전까지 배선을 건드리지 않기로 했으므로,
  이 문서가 나오기 전까지 해당 작업은 멈춰 있다.
  **채팅에서 답한 판단은 이 저장소에서 확정이 아니므로 여기에 옮긴다**
- **날짜**: 2026-08-28
- **결정자**: 신호정 (Tech Lead) 작성 / 안은남 (PM, 인프라) 확인 대기.
  결정 2번이 자격증명 오류를 배포 시점의 기동 실패로 바꾸고,
  이행에 필요한 컨테이너 이미지와 파일 마운트, 배포 절차가 인프라 오너 소관이다
- **관련 문서**: [ADR-0007](0007-walking-skeleton.md) 이음매 표의 발송 행
  (`backend_core.dispatch` 의 `Dispatcher` 를 FCM Admin SDK 로 교체),
  [ADR-0013](0013-m1-measures-push-acceptance.md) (M1 의 끝점은 발송 접수이고,
  기록 전용 발송기 아래에서는 측정 자체가 성립하지 않는다),
  [ADR-0005](0005-webpush-primary-channel.md) (웹푸시가 1차 채널),

  [역할_일정/04-백엔드.md](../역할_일정/04-백엔드.md) 8/22 칸
  ("`firebase-admin` 설치 + `Settings` 가 키를 읽음"),
  [배포_절차.md](../공통_가이드/배포_절차.md) 3절,
  [이슈 181](https://github.com/team-savers/savers-project/issues/181)
  (compose 볼륨 마운트, 같은 자리에서 처리된다)

## 배경 (Context)

실발송 어댑터는 이미 있다.
[PR 135](https://github.com/team-savers/savers-project/pull/135) 가
`FcmDispatcher` 를 넣었고, 데이터 전용 메시지와 TTL,
접수와 전달의 구분까지 `dispatch.py` 안에 들어 있다.
없는 것은 어댑터가 아니라 **배선**이다.
`api/deps.py` 의 `dispatcher()` 는 조건 없이 `RecordingDispatcher` 를 돌려준다.

그래서 남은 결정은 하나로 좁혀진다.
**어떤 조건에서 어느 발송기를 고르는가.**
그 조건이 지금 저장소 어디에도 적혀 있지 않다.

착수 시점에 확인한 상태는 다음과 같다 - `확실한 사실`,
아래 위치를 직접 열어 확인했다.

| 항목 | 현재 상태 | 확인 위치 |
|---|---|---|
| 채널 선택 | 조건 없이 기록 전용 | `api/deps.py` 47 ~ 49행 |
| 자격증명 경로 변수 | `FCM_SERVICE_ACCOUNT_JSON`, 저장소 전체에서 소비자 0곳 | `infra/.env.example` 54행이 유일한 등장 |
| 설정 접두어 | `SAVERS_` 필수 (`env_prefix`) | `backend_core/config.py` 16행 |
| 컨테이너의 `firebase-admin` | 없음. 이미지가 `pip install .` 로 core 만 설치한다 | `apps/backend/Dockerfile` 19행, `pyproject.toml` 43행의 `fcm` extra |
| 자격증명 파일 마운트 | 없음. compose `backend` 서비스에 `volumes` 자체가 없다 | `infra/docker-compose.yml` `backend` 블록 |
| 배포 시 `.env` 기입 항목 | 세 개 | `배포_절차.md` 158행 |

지금 결정이 필요한 이유는 일정이다.
4대 지표 중 M1 (알림 도달 속도) 과 M4 (폐루프 2차 발송 성공률) 는
실발송 없이는 측정 자체가 성립하지 않고, 코드 프리즈가 8/29 다.

### 무엇이 조용히 통과하는가

기록 전용으로 도는 상태를 사람이 알아채는 경로와 못 알아채는 경로가 갈린다.

- **리허설에서는 드러난다.** 폰이 울리지 않으면 그 자리에서 안다.
- **숫자는 드러나지 않는다.**
  `RecordingDispatcher.send()` 는 `True` 를 돌려주므로
  (`dispatch.py` 53 ~ 55행) 파이프라인의 `accepted` 가 채워지고,
  `AlertRunSummary` 의 `meanLatencyMs` 와 `p95LatencyMs` 까지 정상적으로 계산된다.
  **그 값은 발송하지 않은 경로의 지연이다.**

이 문서가 막으려는 것은 두 번째다.
첫 번째는 사람이 잡지만, 두 번째는 제출 숫자로 그대로 들어간다.

## 결정 (Decision)

1. **발송 채널은 명시 설정 하나로만 고른다.**
   `SAVERS_PUSH_CHANNEL` 을 신설하고 값은 `recording` 또는 `fcm` 둘뿐이다.
   기본값은 `recording` 이다.
   **자격증명 파일이 있는지 없는지로 채널을 추론하지 않는다.**
2. **`fcm` 을 골랐는데 자격증명을 쓸 수 없으면 기동을 중단한다.**
   검증 시점은 첫 발송이 아니라 **기동**이다.
   검증 범위는 SDK import, 경로 존재와 읽기 가능,
   `credentials.Certificate()` 성립, 명명된 앱 등록까지다.
   이 구간에서 네트워크 호출은 일어나지 않는다 - `높은 신뢰`,
   Admin SDK 는 토큰 발급을 첫 발송까지 미룬다.
   **따라서 이 검증은 "자격증명이 서버에서 받아들여진다"까지는 보증하지 않는다.**
   그것을 확인하는 유일한 수단은 실기기 발송 1회이며,
   그것이 일정표 8/22 칸의 "실기기 도달 캡처"다.
3. **자격증명 경로 변수의 정본 이름은 `SAVERS_FCM_SERVICE_ACCOUNT_PATH` 다.**
   `FCM_SERVICE_ACCOUNT_JSON` 은 폐기하고 `.env.example` 에서 지운다.
   값은 **파일 경로**이며 JSON 문자열을 넣는 자리가 아니다.
   이름은 어댑터 생성자 인자 `service_account_path` 와 1대 1로 맞춘다.
4. **기록 전용으로 도는 동안 그 사실을 운영자에게 보인다.**
   기동 로그 한 줄과, `/internal/alerts/dispatch` 응답의 채널 필드 둘 다.
   이 라우트는 `packages/contracts/openapi.yaml` 에 없으므로
   필드 추가가 계약 변경이 아니다 - `확실한 사실`,
   계약에 있는 내부 경로는 `/internal/sessions/{token}/events` 하나다.
   지연 숫자와 그 숫자가 어느 채널에서 나왔는지가 같은 응답에 실려야 한다.
5. **환경 이름으로 채널을 판별하지 않는다.**
   `ENV=production` 같은 변수를 만들지 않는다.
   판별식이 하나면 CI 도, 배포 VM 도, 로컬도 같은 값을 읽는다.

근거는 넷이다.

- **바꾸려는 이름은 계약이 아니라 미사용 문자열이다.**
  저장소 전체에서 등장이 한 곳이고 그 값을 읽는 코드가 없다.
  계약이라면 `packages/contracts` 나 `Settings` 에 있어야 하는데 둘 다 없다.
  반대로 접두어 없는 이름을 유지하려면
  `Settings` 를 우회해 `os.environ` 을 직접 읽는 두 번째 진입점을 만들어야 하고,
  `.env.example` 57행은 접두어 없는 이름이
  "코드가 읽지 못하고 조용히 기본값으로 동작"하는 실패로 이어진다고
  이미 경고하고 있다.
  그리고 `_JSON` 접미사는 값의 형태를 잘못 알려준다.
  **이름과 값이 어긋나 있다는 것을 구현 담당자가 배선 전에 먼저 짚었고,
  그 확인 요청이 이 문서의 계기다.**
  이름이 제 몫을 했다면 물어볼 것이 없었을 자리다.
- **추론은 조용한 강등을 만든다.**
  "자격증명이 있으면 실발송, 없으면 기록"은
  경로 오타 하나가 채널을 바꾸는 규칙이다.
  그 강등은 200 응답과 정상적인 지연 숫자로 위장한다.
- **기동에서 죽는 것이 첫 발송에서 죽는 것보다 싸다 - 이 검증이 잡는 범위 안에서.**
  잡히는 것은 결정 2번에 적은 로컬 파싱까지이고, 그 범위를 넘는 실패는 그대로 남는다.
  첫 발송에서 죽으면 그 특보 1건을 잃는다.
  리허설 (8/31) 과 본선 (9/2) 사이에 그 실패를 복구할 창이 없다.
  기동 실패는 배포한 사람이 즉시 보고, 8/29 배포에는 여유 6h 가 남아 있다.
- **표기는 새 규칙이 아니라 이 저장소의 기존 규칙이다.**
  `api/deps.py` 59 ~ 62행이 대피소 캐시에 대해 같은 판단을 이미 적어 뒀다 -
  응답에 `availability: cache_only` 로 보이게 하고
  실데이터인 척 위장하지 않는다.
  생성 실패가 `official_fallback` 으로 응답에 드러나는 것도 같은 모양이다.

기본값을 `recording` 으로 두는 것은 이 넷과 별개의 제약이다.
`config.py` 3 ~ 5행이 기본값의 원칙을
"빈 설정으로도 새 클론이 돈다"로 못박고 있고,
CI 는 자격증명 없이 기동해야 한다.

### 검토하고 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 이름을 유지하고 `os.environ` 으로 직접 읽는다 | 설정 진입점이 둘로 갈린다. `Settings` 우회가 선례로 남고, 다음 키도 같은 길을 간다 |
| 자격증명 유무로 채널을 자동 전환한다 | 이 문서가 막으려는 실패 그 자체다. 오타 하나가 채널을 바꾸고 그 사실이 응답에 드러나지 않는다 |
| 첫 발송 시점에 검증한다 | 특보 1건을 잃는다. 발견 시점이 가장 나쁜 시점이 된다 |
| `fcm` 을 요청했는데 자격증명이 깨졌을 때, 기동은 시키고 발송만 끄고 표기한다 | 위 자동 전환과는 다른 대안이고 표기가 있으므로 조용하지도 않다. 그래도 기각한다 - **설정과 다르게 동작하지 않는다**가 이 문서의 규칙이기 때문이다. 기록 채널 표기는 운영자가 그것을 요청했을 때 정보이지만, `fcm` 을 요청한 서버가 기록만 하고 있으면 요청하지 않은 동작을 하는 것이다. 그 서버는 살아서 M1 과 M4 표본을 계속 만들어 낸다 |
| `ENV=production` 을 도입해 환경으로 가른다 | 판별식이 둘이 된다. CI 가 어느 쪽으로 판정되는지 매번 추론해야 하고, 그 추론이 틀리면 CI 가 실발송을 시도한다 |
| 기본값을 `fcm` 으로 둔다 | 새 클론과 CI 가 자격증명 없이 기동하지 못한다. `config.py` 의 기본값 원칙과 정면으로 충돌한다 |
| 배선을 본선 후로 미룬다 | M1 과 M4 두 지표가 측정 불가로 남는다. 미루는 선택지가 아니라 지표를 포기하는 선택지다 |

## 결과 (Consequences)

**긍정**

- Backend 의 배선 작업이 오늘 시작된다. 8/29 프리즈 안에 들어간다.
- 기록 전용으로 잰 지연 숫자가 M1 으로 제출되는 경로가 닫힌다.
  채널이 같은 응답에 실리므로 숫자와 출처가 분리되지 않는다.
- 자격증명 문제가 배포 시점에 드러난다.
  지금까지는 첫 발송까지 알 수 없었다.
- 로컬과 CI 는 아무 설정 없이 지금과 똑같이 돈다.
  기본값이 현재 동작이므로 이 결정으로 깨지는 테스트가 없다.
- 이름이 값의 형태를 말한다. 다음 사람이 JSON 문자열을 넣지 않는다.

**부정 / 완화**

| 리스크 | 완화 | 상태 |
|---|---|---|

| 채널이 `fcm` 이 되는 순간 `/internal/alerts/dispatch` 가 실제 푸시를 쏜다 | ADR-0007 이 Caddy 에서 `/internal/*` 을 프록시 이전에 404 로 끊어 뒀다. 인증과 레이트리밋은 없으므로, 그 차단이 유일한 방어라는 사실이 이 전환으로 실효를 갖는다 | 명시함, [이슈 25](https://github.com/team-savers/savers-project/issues/25) |

| 시드의 FCM 토큰이 가공값이라 실발송에서 거부된다 | ADR-0015 가 이미 지적한 항목이다. 실기기 토큰으로 갱신해야 실발송 경로가 성립한다 | 후속 조치, Backend |
| 이미지에 `firebase-admin` 이 없어 배선만으로는 실발송이 되지 않는다 | Dockerfile 이 `fcm` extra 를 설치하도록 고친다. 기동 검증이 이 누락을 배포 시점에 드러낸다 | 후속 조치, Backend |
| 설정 항목이 둘 늘어 배포 절차가 길어진다 | 배포 절차의 기입 항목이 셋에서 **다섯**이 되고 마운트가 하나 는다. 둘 중 하나만 채우면 `SAVERS_PUSH_CHANNEL` 이 기본값 `recording` 으로 남아 실발송이 아닌 채로 배포된다. 세션 DB 볼륨 (이슈 181) 과 같은 자리에서 처리한다 | 후속 조치, PM |

## 후속 조치

- **배선 구현** (Backend).
  `api/deps.py` 의 `dispatcher()` 가 설정을 읽어 두 발송기 중 하나를 고른다.
  기동 검증 로직은 `lifespan` 이 아니라 `backend_core` 쪽에 둔다 -
  [이슈 199](https://github.com/team-savers/savers-project/issues/199) 가
  같은 종류의 배치를 이미 지적하고 있다.
  이 작업에는 이슈가 아직 없으므로 착수 전에 하나 연다
- **Dockerfile 에 `fcm` extra 설치** (Backend).
