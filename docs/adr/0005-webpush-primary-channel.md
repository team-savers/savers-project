# ADR-0005: 1차 알림 채널을 카카오 알림톡에서 웹푸시(FCM)로 전환한다

- **상태**: 승인 (Accepted)
- **날짜**: 2026-07-26 (결정) / 2026-07-27 (기록) / 2026-07-28 (승인)
- **결정자**: 안은남 (PM), 이진호 (Frontend/UX), 신호정 (Tech Lead), 최혜리 (Backend/Infra)
- **관련 문서**: [ADR-0004](0004-pwa-over-native.md) (일부 대체), [리스크.md](../공통_가이드/리스크.md) ①, [외부_승인.md](../공통_가이드/외부_승인.md) C, [구현_범위.md](../공통_가이드/구현_범위.md) 4절, [역할_가이드/04-프론트엔드-UX.md](../역할_가이드/04-프론트엔드-UX.md), [AGENTS.md](../../AGENTS.md)
- **대체 관계**: [ADR-0004](0004-pwa-over-native.md)의 **"푸시는 알림톡 1차 / 웹푸시 보조"** 부분을 대체한다. ADR-0004의 본 결정(PWA 단일 형태, 네이티브·하이브리드 제외)은 **그대로 유효**하다.

## 배경 (Context)

[리스크.md](../공통_가이드/리스크.md)의 **①번(최우선 리스크)**은 처음부터 알림톡이었다.
알림톡은 발신 전 심사를 거친 **고정 템플릿 + 변수 치환**이 원칙이라, LLM이 매번 자유롭게 생성한
문장을 실시간 발송하는 방식과 정책적으로 충돌한다. 리스크 문서는 이것을
**"서비스의 핵심 가치제안(개인화 생성)과 직결"**되는 문제로 적었고,
[외부_승인.md](../공통_가이드/외부_승인.md) C절은 템플릿 사전승인을
**"예선 초반에 반드시 실제 정책을 확인해야 하는 최우선 항목"**으로 표시했다.

기존 완화책은 **렌더링 어댑터(변수 슬롯 매핑)** 였다 — 자유생성 문장을 `#{장소}`·`#{행동}` 같은
승인된 슬롯에 끼워 넣는 계층. 재검토 결과 이 완화책은 리스크를 **없애지 못하고 옮길 뿐**이었다.

1. **핵심 가치를 깎아 리스크를 사는 거래다.** 문장을 슬롯에 넣는 순간 문안 구조가 템플릿에 고정된다.
   리스크 ①이 지적한 "동적 생성 자유도가 얼마나 제약되는가"에 대해, 어댑터는 답이 아니라
   **제약을 수용하겠다는 선언**이다.
2. **성패가 우리 손 밖에 있다.** 발신 프로필 심사(통상 수 영업일) + 템플릿 심사가 모두 외부 심사이고,
   승인 거부 시 되돌릴 방법이 없다. 예선 제출이 **2026-08-10 13:00**인 2주 스프린트에서
   이 리드타임은 회수 불가능한 일정 리스크다.
3. **측정 대상과 전달물이 어긋난다.** 제출 지표인 근거 일치율·메시지 명확성은 **생성된 문안 그 자체**를
   채점한다. 그런데 실제 사용자에게 도달하는 건 슬롯에 치환된 문장이므로, 채점한 것과 전달된 것이
   달라진다. 지표의 의미가 훼손된다.
4. 어댑터 계층 자체도 3일 규모 작업이었다([역할_일정/04](../역할_일정/04-프론트엔드-UX.md)).

즉 이 리스크는 **완화 대상이 아니라 회피 대상**이었다. 채널을 바꾸면 원인이 소멸한다.

## 결정 (Decision)

**1차 알림 채널을 웹푸시(FCM)로 전환**하고, **카카오 알림톡은 예선 범위에서 제외**한다.

- **생성 문안은 변형 없이 그대로 전달한다.** 웹푸시에는 템플릿 사전승인이 없다.
  → **렌더링 어댑터(변수 슬롯 매핑)는 폐기하며, 재도입하지 않는다.**
- **알림의 액션 버튼에 의존하지 않는다.** 웹푸시 알림 버튼은 플랫폼별 최대 2개 제한이 있어 신뢰할 수 없다.
  **[집이에요]/[밖이에요] 분기는 랜딩 첫 화면**에서 수행한다.
- **발송 인프라**: Firebase Cloud Messaging. 프로젝트 `savers-45f1c` / 웹앱 `savers-web` /
  VAPID 키 발급 완료. 백엔드는 Admin SDK 자격증명으로 발송한다.
- **알림톡 대행사 선정(솔라피/알리고)은 예선 범위 밖**이 된다.
  → [구현_범위.md](../공통_가이드/구현_범위.md) 4절의 대행사 비교·선정은 이 결정으로 무효.
- **ADR-0004는 유지된다.** PWA 단일 형태라는 결정은 오히려 강화된다 — 이제 전달 경로까지 웹이다.

## 결과 (Consequences)

**긍정**

- **최우선 리스크(①)가 소멸한다.** 완화가 아니라 원인 제거다.
- **외부 승인이 임계경로에서 빠진다.** [외부_승인.md](../공통_가이드/외부_승인.md)에서 리드타임이 가장 길다고
  적힌 C절 항목(채널 개설·비즈니스 인증·발신 프로필·템플릿 승인)이 통째로 사라지고,
  A절(공공 API)만 남는다. 2주 스프린트에서 회수하는 시간이 크다.
- **비용이 0으로 내려간다.** 알림톡은 건당 과금(7.5~13원)에 SMS 폴백 단가까지 얹히지만 FCM은 무료다.
  → [비용_산정.md](../공통_가이드/비용_산정.md) 갱신 대상.
- **KPI의 측정 대상과 전달물이 일치한다.** 채점한 문안이 그대로 도달한다.
- 어댑터 3일을 통합 서비스워커·TMAP 보행 경로로 재배치했다.

**부정 / 완화**

| 리스크 | 완화 | 상태 |
|---|---|---|
| **iOS 웹푸시 제약이 승격됐다.** ADR-0004는 이 한계를 "알림톡 1차로 우회"한다고 적었는데, 그 우회로가 사라졌다. iOS는 16.4+ **및** 홈 화면 추가(A2HS) 상태에서만 웹푸시가 동작한다 | 시연 환경을 안드로이드·데스크톱 크롬으로 고정한다. iOS 사용자는 대리등록 절차에 A2HS 안내를 포함한다 | 완화됨 (잔여 리스크 명시) |
| **알림 권한 거부** — 알림톡에는 없던 새 실패 모드다 | 권한 요청을 페이지 로드 즉시 띄우지 않고 **사용자 제스처에서만** 수행한다. 거부 시 대체 도달 경로는 **미해결** | ⚠️ 미해결 |
| **첫 접촉 경로가 없다.** 알림톡은 전화번호만으로 도달했지만, 웹푸시는 **사전에 브라우저에서 FCM 토큰을 등록**해야 첫 알림이 간다 | 대리등록(보호자·복지관) 시점에 토큰을 등록하는 흐름과 그 시점의 자격증명이 필요하다. `packages/contracts` PR #10 리뷰에서 지적된 **`/v1/devices` 순환 의존**이 정확히 이 문제다 | ⚠️ 미해결 — 설계 필요 |
| **HTTPS 배포처 의존** — 웹푸시는 localhost 외에 HTTPS가 필수라, 배포처가 없으면 실기기 검증이 불가능하다 | 예선 배포처 확보를 선행 과제로 올린다([ADR-0003](0003-single-vm-seoul.md) 단일 VM) | 진행 중 |
| **"무설치" 하드 제약과의 긴장.** iOS의 A2HS 유도는 사실상 설치에 준하는 행위다 | 원칙의 정확한 문구는 **"당사자에게 설치 부담 없음 — 등록·설정은 보호자·복지관·지자체가 대행"**이다. A2HS를 **대리등록자가 수행**하면 원칙은 지켜진다. 다만 당사자가 스스로 해야 하는 상황이 생기면 이 결정이 원칙을 침식하므로, 대리등록 흐름 설계에서 반드시 흡수해야 한다 | 설계 제약으로 이관 |

## 재검토 조건

다음 중 하나가 확인되면 **웹푸시 1차 + 알림톡 보조의 이중 채널**로 재검토한다.

- 카카오 정책 확인 결과 **자유생성 문장의 알림톡 발송이 실제로 승인 가능**한 것으로 드러난 경우
  (리스크 ①의 신뢰도는 "높은 신뢰"이지 확정이 아니다)
- iOS 사용자 비중이 시연 또는 실서비스에서 **결정적**이 되어, A2HS 안내로 흡수되지 않는 경우

본선·실서비스 확장 단계에서는 도달률을 위해 이중 채널이 정답일 가능성이 높다.
이 결정은 **예선 스프린트의 범위 결정**이지, 알림톡을 영구히 배제하는 것이 아니다.
