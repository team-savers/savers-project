# ADR-0003: 배포 인프라는 서울 리전 단일 CPU VM으로 한다

- **상태**: 승인 (Accepted)
- **날짜**: 2026-07-25
- **결정자**: 안은남 (PM), 최혜리 (Backend/Infra)
- **관련 문서**: [CLAUDE.md](../../CLAUDE.md) Tech stack, [구현_범위.md](../공통_가이드/구현_범위.md) 5절, [역할_가이드/05-백엔드-인프라.md](../역할_가이드/05-백엔드-인프라.md), [아키텍처.md](../공통_가이드/아키텍처.md), [ADR-0001](0001-monorepo.md)

## 배경 (Context)

PM이 서버 인프라를 AWS 기반으로 하자고 제안했고, AWS 자체는 무난한 선택이라 이견이 없었다.
쟁점은 그 위에서 **어느 수준의 인프라를 구축할 것인가**였다.

초기 문서(구현_범위.md 5절, docs/역할_가이드/05-백엔드-인프라.md)에는 이중화를 AWS 관리형 서비스
(ALB, Auto Scaling, RDS Multi-AZ 등)로 구현한다고 적혀 있었다. 재검토 결과 두 가지 사실이 드러났다.

1. **이 아키텍처의 병목은 우리 컴퓨트가 아니라 외부 한국 API 왕복이다.**
   생성(HyperCLOVA X = NCP), 알림톡(카카오), 임베딩·번역·TTS가 모두 외부 API이고,
   KPI인 알림 도달 ≤30초는 이 외부 왕복과 파이프라인 단계 수가 지배한다.
   따라서 자체 서버의 이중화·오토스케일링이 데모 성패를 좌우하지 않는다.
2. **GPU가 필요 없다.** HyperCLOVA X는 API 전용이라 자체 호스팅이 불가능하고,
   임베딩도 API(또는 소규모 코퍼스라 CPU)로 처리되므로 GPU 인스턴스가 불필요하다.

여기에 팀 제약(6인, 예선 2026-07-27 시작의 단기 일정)을 더하면, 관리형 이중화 스택
(ALB/ASG/RDS Multi-AZ/NAT Gateway)을 실제로 구축하는 비용은 [리스크.md](../공통_가이드/리스크.md)의
일정 리스크(⑧)를 키우는 반면, 심사가 보상하는 실질
("AI 독립 배포 모듈" + "배포 문서 존재", [ADR-0001](0001-monorepo.md))에는 기여하지 않는다.

## 결정 (Decision)

배포 인프라는 **AWS 서울 리전(ap-northeast-2)의 단일 CPU VM**으로 하고,
[ADR-0001](0001-monorepo.md)의 `docker-compose`로 전체 스택을 그 VM 위에 올려 운영한다.

- **서울 리전 고정** — 국내 외부 API(HyperCLOVA X/NCP, 카카오, 파파고 등)와의 왕복 지연을 줄이고,
  ≤30초 지연시간 KPI 측정 조건을 일관되게 유지한다.
- **CPU 전용, GPU 없음** — 생성·임베딩이 외부 API 기반. GPU는 오픈 LLM 자체 호스팅으로
  방향을 틀 때만 재검토(현재 아님).
- **관리형 이중화는 유보** — ALB·ASG·RDS Multi-AZ는 예선/데모에 구축하지 않는다.
  대신 `apps/ai-engine`·`apps/backend` README에 **"확장 시 ALB+ASG/Multi-AZ로 전환" 경로만 문서화**해
  심사 요건(배포·운영 문서 존재)을 최소 비용으로 충족한다.

## 결과 (Consequences)

**긍정**

- 로컬 `docker-compose up`과 배포 환경이 동일 → 배포 문서가 단순하고 온보딩 1회로 끝난다.
- 인프라 구축에 쓸 시간을 "직접 구현 필수" 항목(가드레일, 위치 매칭, 청킹 전략, 지연시간 계측)에 집중.
- GPU·관리형 서비스·NAT Gateway 고정비를 제거해 월 비용을 CPU VM 수준으로 낮춘다.

**부정 / 완화**

| 리스크 | 완화 |
|---|---|
| 단일 VM = SPOF, 장애 시 전체 중단 | 서비스 고유 요구인 **오프라인 예비모드**(사전 캐시 대피소·행동요령)가 별도 완화책으로 이미 존재 |
| 데모 중 부하 급증 대응 불가 | 데모는 통제된 트래픽. 필요 시 인스턴스 사이즈 업(수직 확장)으로 1차 대응 |
| "이중화 없음"이 심사에 약점으로 보임 | README에 전환 경로를 문서화해 "설계는 있으나 규모상 유보"임을 명시 |

## 재검토 조건

실사용 트래픽이 단일 VM 수직 확장 한계를 넘거나, 가용성 SLA가 요구되는 경우에만
관리형 이중화(ALB+ASG, RDS Multi-AZ)로 전환한다. 그 전에는 구축하지 않는다.
