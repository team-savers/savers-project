# ADR-0009: 서버 셸 접근은 SSM Session Manager로 하고, 셸 권한은 2인으로 제한한다

- **상태**: 제안 (Proposed) — PR [#75](https://github.com/team-savers/savers-project/pull/75) 리뷰 지적에 따라 작성, PM·Backend/Infra 승인 대기
- **날짜**: 2026-08-07
- **결정자**: 신호정 (Tech Lead) 제안 / 김도혁 (Backend/Infra), 안은남 (PM) 승인 대기
- **관련 문서**: [ADR-0003](0003-single-vm-seoul.md) (단일 VM), [ADR-0008](0008-frontend-static-hosting.md) (프론트는 VM 밖), [서버_운영.md](../공통_가이드/서버_운영.md), [배포_절차.md](../공통_가이드/배포_절차.md), 이슈 [#25](https://github.com/team-savers/savers-project/issues/25)

## 배경 (Context)

[ADR-0003](0003-single-vm-seoul.md)이 정한 단일 VM은 #49로 실제로 떠 있고,
공개 주소와 TLS까지 붙은 상태입니다.
그런데 **"세우는 절차"만 문서에 있고 "세워진 뒤 누가 어떻게 들어가는가"는 어디에도 없었습니다.**
팀원이 로그를 보려면 담당자에게 개인 메시지로 묻는 것이 유일한 경로였습니다.

접속 방식과 권한 범위는 한 번 정하면 되돌리는 비용이 큽니다.
`.pem`을 한 번 공유하면 회수할 방법이 사실상 없고,
보안그룹 22번을 열어 두면 닫는 시점을 아무도 책임지지 않습니다.
그래서 문서를 쓰기 전에 결정으로 못박아야 하는 항목입니다.

결정을 미룰 수 없는 이유가 하나 더 있습니다.
**VM 안에는 비공개 키가 평문으로 있습니다.**
`infra/.env`의 HyperCLOVA X(NCP) 키가 그렇고,
셸에 들어갈 수 있는 사람은 그것을 전부 읽을 수 있습니다.
이 저장소는 공개이므로 키가 한 번 새면 재발급 외에 대응이 없습니다
([AGENTS.md](../../AGENTS.md) "Public repo, so secrets are a one-way door").

## 결정 (Decision)

**셸 접근은 AWS Systems Manager Session Manager로만 하고, 셸 권한은 김도혁·신호정 2인으로 제한합니다.**

- **SSH 인바운드(22번)를 닫습니다.** 보안그룹에 남는 것은 80·443뿐입니다.
- **`.pem` 키페어를 팀에 공유하지 않습니다.** 배포 담당자 외에는 인스턴스 키를 보유하지 않습니다.
- **IAM 정책은 이 인스턴스 하나로 범위를 좁힙니다.** 계정 전체 `ssm:StartSession`을 주지 않습니다.
- **셸 권한 등급은 둘뿐입니다.** 팀 전원은 자격증명 없이 공개 HTTPS로 상태만 확인하고,
  로그·재기동·설정 변경은 위 2인이 수행합니다.
- **22번을 닫는 것은 SSM 접속을 실제로 성공한 뒤 마지막에 합니다.** 순서를 바꾸면 잠깁니다.

세 방식을 비교한 결과입니다.

| 방식 | 개인별 회수 | IP 변경 대응 | 접속 기록 | 초기 비용 |
|---|---|---|---|---|
| `.pem` 공유 | **불가** — 전원 키 교체 | 무관 | 사람 단위로 남지 않음 | 없음 |
| 개인별 공개키 + SSH | 가능 | **매번 보안그룹 수정** | 서버 로그에만 | 낮음 |
| **SSM Session Manager (채택)** | **IAM에서 즉시** | 무관 (포트 없음) | CloudTrail에 사용자 단위 | IAM 역할 1회 + 인당 정책 |

`.pem` 공유가 탈락한 이유는 회수 불가입니다.
한 명이 빠질 때 전원의 키를 바꿔야 하는 방식은
6명 규모에서도 실제로는 아무도 바꾸지 않는 쪽으로 귀결됩니다.

개인별 SSH가 탈락한 이유는 IP입니다.
팀원이 집·카페·학교에서 접속하는데,
그때마다 보안그룹을 여는 작업은 결국 "0.0.0.0/0으로 열어두자"로 흐릅니다.

SSM의 대가는 최초 1회 IAM 역할 부착과 인당 정책 부여(30분 정도)이고,
그 대가로 포트를 하나도 열지 않은 상태를 유지합니다.

셸 권한을 2인으로 좁힌 근거는 **접근자 수가 곧 키 유출 경로의 수**라는 것입니다.
로그 열람이 필요한 팀원은 담당자에게 요청합니다.
이 규모에서는 요청-전달이 별도 권한 체계를 만드는 것보다 빠릅니다.

## 결과 (Consequences)

**긍정**

- 인바운드가 80·443뿐이라 SSH 대상 스캔·무차별 대입의 표면이 사라집니다.
- 퇴장·역할 변경 시 IAM 정책을 떼는 것으로 회수가 끝납니다. VM에 손대지 않습니다.
- 누가 언제 셸을 열었는지가 CloudTrail에 사용자 단위로 남습니다.
- 키 평문 노출 범위가 2인으로 한정되어, 유출 시 원인 추적 범위가 좁습니다.

**부정 / 완화**

| 리스크 | 완화 | 상태 |
|---|---|---|
| **순서를 틀리면 잠깁니다.** SSM이 되기 전에 22번을 닫으면 아무도 못 들어가고, 인스턴스 재생성 외에 방법이 마땅치 않습니다 | 22번 폐쇄를 마지막 단계로 고정하고 경고 블록을 붙였습니다 | ✅ [서버_운영.md](../공통_가이드/서버_운영.md) 2-5 |
| **QA가 검증을 직접 돌리지 못합니다.** 이슈 #25 같은 실측을 QA가 반복해야 하면 매번 담당자를 거칩니다 | 등급 표에 한 사람을 더 넣으면 되는 구조로 문서를 썼습니다. 반복되면 재검토합니다 | 아래 재검토 조건 |
| **AWS 콘솔·IAM 의존이 하나 늘어납니다.** 계정 접근이 막히면 셸도 막힙니다 | 배포 담당자가 인스턴스 키페어를 보유하므로 최후 경로가 남습니다 | 완화됨 |
| **세션 내용이 기록되지 않습니다.** CloudTrail에 남는 것은 세션 시작 사실이지 명령 이력이 아닙니다 | 예선 범위에서는 유보합니다. 필요 시 S3·CloudWatch 세션 로깅을 켜면 됩니다 | 유보 |
| **에이전트가 죽으면 접속 경로가 사라집니다.** `amazon-ssm-agent`가 멈춘 상태에서 22번이 닫혀 있으면 들어갈 수 없습니다 | Fleet Manager 등록 상태를 접속 실패 시 첫 확인 항목으로 둡니다 | ✅ [서버_운영.md](../공통_가이드/서버_운영.md) 2-2 |

## 재검토 조건

다음 중 하나면 등급 구성이나 접속 방식을 다시 봅니다.

- **QA(최혜리)가 배포 검증을 직접 반복 수행해야 하는 상황이 반복될 때** —
  2-3의 정책을 한 사람에게 더 붙이고 표만 고칩니다. 문서 구조는 그대로 둡니다.
- **셸 접근자 2인이 모두 부재한 채 장애가 발생했을 때** — 대기 인원을 1인 더 둡니다.
- **본선에서 세션 명령 이력이 감사 대상이 될 때** — 세션 로깅(S3·CloudWatch)을 켭니다.
- **`infra/.env`의 비밀값이 Secrets Manager·SSM Parameter Store로 옮겨질 때** —
  셸 접근자가 곧 키 열람자라는 전제가 깨지므로, 2인 제한의 근거를 다시 계산합니다.
