# ADR-0026: 안전한 경로가 없거나 경로 엔진이 실패하면 직선 경로를 그리지 않고 수직 대피와 119 로 넘긴다

- **상태**: 제안 (Proposed) - 2026-08-31 작성.
  2026-08-31 오전 팀 채팅에서 김도혁 (Backend) 이 발표 전 범위를 정리하면서
  이 항목 하나만 성격이 다르다고 짚었다.
  나머지는 현재 상태의 기록이고, 이것은 **경로를 실제로 붙일 때 적용할 설계 결정**이다.
  본인의 말도 "현재 구현 완료 상태가 아니다"였다.
  범위 동결은 [ADR-0025](0025-pre-demo-scope-freeze.md) 로 나눠 적었다.
  이 문서는 본선이 끝나도 남는다
- **날짜**: 2026-08-31
- **결정자**: 신호정 (Tech Lead) 작성 / 김도혁 (Backend) 확인 대기
- **관련 문서**: [ADR-0017](0017-route-engine-osmnx-networkx.md) 결정 2
  ("경로 없음" 뒤 대피소 재선정. 이 문서는 그것을 대체하지 않고 뒤를 잇는다),
  [ADR-0016](0016-shelter-cautions-not-exclusion.md)
  (후보가 하나도 남지 않을 때만 대피소 전량 제외로 간다),
  [ADR-0012](0012-verifier-rules-and-closed-loop.md) 285 ~ 296행
  (발송 폴백 문안 규칙. 119 버튼을 보호자 화면의 것으로 둔 자리이며,
  이 문서는 그것을 대체하지 않는다),
  [ADR-0025](0025-pre-demo-scope-freeze.md) 결정 2번 (배선은 발표 전 범위 밖.
  [PR 232](https://github.com/team-savers/savers-project/pull/232) 로 따로 올라가므로,
  그것이 머지되기 전까지 이 링크는 깨져 있다),
  [후속_과제.md](../공통_가이드/후속_과제.md) 24번
  (세션 로딩 실패 시 119 버튼이 같이 숨는다),
  `packages/contracts/openapi.yaml` (경로 응답 스키마가 아직 없다)

## 배경 (Context)

[ADR-0017](0017-route-engine-osmnx-networkx.md) 결정 2번이
R2 와 R3 링크를 먼저 지우고, 남은 그래프에서 최단을 고르고,
통과할 수 있는 길이 없으면 대피소를 재선정하는 데까지 정했다.
코드도 그렇게 있다.
`route_engine.py` 는 후보를 순회하며 재선정 횟수를 세고
(`reselection_count`, 70행), 후보를 다 소진하면 "경로 없음"을 돌려준다 (245행).

**정해지지 않은 것은 그다음이다.**
재선정할 후보가 더 없을 때 사용자 화면이 무엇을 보여주는가.

이 자리를 비워 두면 구현할 때 가장 손쉬운 답이 들어간다 -
출발지와 대피소를 직선으로 잇는 것이다.
거리 계산에 쓰는 `haversine_m()` 이 이미 `shelters.py` 에 있으므로
선 하나 그리는 데 새로 필요한 것이 없다.
**그 선은 도로망을 한 번도 보지 않은 선이고, 침수 회피의 정반대다.**

같이 정해야 하는 것이 셋 더 있다.

- 코어는 "경로 없음"과 **엔진 실패**를 다른 상태로 구분한다
  (`route_engine.py` 33 ~ 34행, 190행, 245행).
  화면이 이 둘을 어떻게 다룰지가 없다.
- 후보가 하나도 없을 때 가는 수직 대피 문안은 이미 있다.
  다만 그것은 "갈 곳이 없다"이고, 이 경우는 "대피소는 있는데 길이 없다"다.
- 119 링크는 피보호자 화면에 이미 있다
  (`EvacuationFlow.tsx` 619행, `EvacuationActions.tsx` 235행) - `확실한 사실`.
  다만 [ADR-0012](0012-verifier-rules-and-closed-loop.md) 285 ~ 296행은
  발송 폴백 문안 규칙이고, 거기서 119 버튼을 맡긴 화면은 **보호자 화면**이다.
  피보호자 화면에서 상시 노출을 보장한 문서는 없다.
  후속_과제 24번이 지적한 대로 조건부 렌더 안에 들어가 사라지는 자리가 실제로 있다.

배선이 아직 없으므로 지금 이 결정을 구현할 자리도 없다
([ADR-0025](0025-pre-demo-scope-freeze.md) 결정 2번).
**그 ADR-0025 는 아직 제안 상태이고
[PR 232](https://github.com/team-savers/savers-project/pull/232) 에서 심사 중이다.**
이 문서가 아래에서 그것을 인용하는 자리는 모두 확정이 아니라 제안을 가리키며,
ADR-0025 가 뒤집히면 이 문서의 적용 시점도 같이 바뀐다.
그래서 이 문서는 **적용 시점을 배선 시점으로 못박은 설계 결정**이다.

## 결정 (Decision)

1. **직선 경로를 그리지 않는다.**
   안전한 경로가 없을 때 출발지와 대피소를 잇는 선을 화면에 내지 않는다.
   위험 링크를 포함한 최단 경로도 내지 않는다.
   직선거리 표시는 계속 쓰되 그것을 경로라고 부르지 않는다 -
   거리는 거리이고 경로는 지나갈 수 있는 길이다.
2. **이 결정은 재선정을 대체하지 않는다.**
   [ADR-0017](0017-route-engine-osmnx-networkx.md) 결정 2번의 대피소 재선정이 먼저다.
   이 문서가 정하는 것은 **후보를 모두 소진한 뒤의 종단 동작**이다.
   재선정을 건너뛰고 바로 수직 대피로 가는 것이 아니다.
3. **엔진 실패도 같은 화면으로 보낸다.**
   "경로 없음"과 엔진 실패는 사용자에게 같은 문안이다.
   사용자가 할 일이 같기 때문이다.
   **다만 로그와 응답 필드에서는 두 상태를 구분해 유지한다.**
   원인 구분은 운영자의 것이고, 거기까지 합치면 사후 분석이 불가능해진다.
4. **문안은 대피소 전량 제외 문안을 재사용하지 않고 새로 쓴다.**
   전량 제외는 "안내할 대피소가 없다"이고 이 경우는 "대피소는 있는데 안전한 길이 없다"다.
   공통은 수직 대피와 119 이고, 다른 것은 대피소를 계속 보여준다는 점이다.
   대피소 이름과 거리는 화면에 남기되 경로 안내 단계로 넘기지 않으며,
   1차 행동은 수직 대피로 올린다.
5. **119 의 노출 조건을 화면 상태와 분리한다.**
   경로 실패 화면을 포함해, 피보호자 화면의 119 는
   세션이나 프로필 로딩 상태와 무관하게 눌리는 자리에 둔다.
   **이 화면에만 적용하는 규칙이 아니다** -
   화면마다 노출 조건이 갈리면 어디서 사라지는지 아무도 세지 못한다.
   [ADR-0012](0012-verifier-rules-and-closed-loop.md) 285 ~ 296행의 119 서술은
   발송 폴백 문안에 대한 것이고, 그 문단이 대상으로 삼은 화면은 보호자 화면이다.
   **이 결정은 ADR-0012 를 대체하지 않는다.** 그 결정의 적용 대상은 그대로이며,
   피보호자 화면의 노출 조건은 규정된 적이 없어 이 문서가 처음 정한다.
   `tel:` 링크라 다이얼러를 열 뿐 자동으로 걸지 않는다 - `확실한 사실`.
   후속_과제 24번과 같은 자리이므로 함께 고친다.
6. **상태는 계약에 싣고, 데이터 모양으로 추론하지 않는다.**
   경로 응답 스키마를 만들 때 상태 값에 "경로 없음"과 "엔진 실패"를 넣는다.
   프론트는 그 상태로 분기하며, **빈 좌표 배열을 보고 경로 없음이라고 판단하지 않는다.**
   계약이 상태를 말하지 않으면 추론이 들어가고, 추론은 조용히 틀린다 -
   [ADR-0023](0023-explicit-push-channel-selection.md) 결정 1번이 발송 채널에서 내린 것과 같은 판단이다.
7. **적용 시점은 배선 시점이다.**
   이 문서는 발표 전 구현 대상이 아니다 ([ADR-0025](0025-pre-demo-scope-freeze.md) 결정 2번).
   경로 API 와 계약이 생기는 PR 이 이 문서를 근거로 든다.

근거는 셋이다.

- **화면에 선이 있으면 사용자는 그 선을 따라간다.**
  "지나갈 수 있는 길만 고른다"가 이 기능의 정의인데,
  가장 위험한 순간에만 그 정의를 어기는 폴백이 된다.
  침수로 길이 막혔다는 것은 그 직선 위에 물이 있다는 뜻이기도 하다.
- **없는 길을 안내하지 않는 것이 이 저장소의 기존 판단이다.**
  대피소 전량 제외를 빈 목록으로 뭉개지 않고 사유와 함께 돌려주는 것,
  생성 실패를 공식 문안 폴백으로 드러내는 것이 같은 모양이다.
  경로에서만 지어내기로 하면 그 일관성이 깨진다.
- **사용자에게 합치고 로그에서 나누는 것이 각각의 목적에 맞다.**
  위급 상황에서 화면이 둘로 갈리면 읽을 것이 늘어난다.
  반대로 로그까지 합치면 "길이 없었다"와 "엔진이 죽었다"를
  사후에 구분할 수 없고, 둘은 고칠 것이 전혀 다르다.

### 검토하고 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 안전한 경로가 없으면 직선 경로를 표시한다 | 이 문서가 막으려는 것 자체다. 도로망을 보지 않은 선이고, 사용자는 선을 따라간다 |
| 위험 링크를 포함한 최단 경로를 표시한다 | R2/R3 제거가 이 기능의 정의다. 정의를 어기는 폴백은 기능이 없는 것보다 나쁘다 |
| 엔진 실패를 "경로 없음"과 다른 화면으로 분기한다 | 사용자가 할 일이 같다. 위급 상황에서 화면을 늘리지 않는다 |
| 대피소 전량 제외 문안을 그대로 재사용한다 | 두 상황에서 다음 행동이 다르다. 대피소가 있는데 없다고 읽히면 잘못된 정보다 |
| 빈 좌표 배열로 "경로 없음"을 표현한다 | 계약이 상태를 말하지 않으면 프론트가 추론한다. 빈 배열은 실패와 미계산을 구분하지 못한다 |
| 119 를 경로 실패 화면에만 노출한다 | 노출 조건이 화면마다 달라지면 어디서 사라지는지 아무도 못 센다. 후속_과제 24번이 그 사례다 |
| 이 결정을 발표 전에 구현한다 | 배선 자체가 범위 밖이다 ([ADR-0025](0025-pre-demo-scope-freeze.md)) |

## 결과 (Consequences)

**긍정**

- 배선 PR 이 열릴 때 폴백을 그 자리에서 다시 논의하지 않는다.
  가장 손쉬운 구현 (직선) 이 들어갈 창이 닫힌다.
- 계약에 상태를 싣기로 해서, 경로 응답 스키마 초안의 필수 항목이 하나 정해졌다.
- 로그 구분을 유지하므로 본선 이후 실패 분석이 가능하다.

**부정 / 완화**

| 리스크 | 완화 | 상태 |
|---|---|---|
| 이 결정이 코드 없이 문서로만 남는다 | 적용 시점을 결정 7번에 못박고, 배선 이슈가 이 문서를 근거로 든다 | 후속 조치, Backend |
| 결정 1번과 6번을 어겨도 지금은 자동으로 잡히지 않는다 | 강제는 결정 6번이 한다 - 계약에 상태 값이 있으면 직선을 그릴 자리가 스키마에서 닫힌다. 배선 PR 의 확인 3항목이 그 보조이고, 코드 표면이 생기면 스캔으로 올린다 | 후속 조치, Backend |
| 문안이 둘로 늘어 번역과 검수 대상이 는다 | 다국어 대상은 기존 문안과 같은 경로를 탄다. 문구 초안은 화면 오너가 쓴다 | 후속 조치, 김소원 |
| 수직 대피가 항상 안전한 것은 아니다 | 이 문서는 대피 판정을 하지 않는다. 정부 판정 우선 원칙은 그대로이고, 119 를 같은 화면에 두는 이유가 이것이다 | 명시함 |
| 상태 값 이름이 계약에서 바뀔 수 있다 | 이 문서는 상태가 계약에 있어야 한다는 것까지 정하고, 정본 이름은 스키마 PR 에서 정한다 | 명시함 |

## 후속 조치

- **경로 응답 스키마 초안** (Tech Lead).
  상태 값 둘과 좌표 배열의 관계를 계약에 적는다.
  구현보다 먼저다
- **배선 이슈에 이 문서 연결** (Backend).
  경로 API 와 파이프라인 연결 작업이 열릴 때 근거로 단다
- **경로 실패 문안 초안** (김소원).
  대피소 전량 제외 문안과 나란히 두고 다른 점이 읽히는지 확인한다
- **후속_과제 24번과 함께 처리** (프론트).
  119 노출 조건을 화면 상태와 분리한다
- **배선 PR 의 확인 3항목** (스키마 PR 은 Tech Lead, 배선 PR 은 Backend).
  (1) 계약 응답에 상태 값 둘이 실려 있는가,
  (2) 프론트가 빈 좌표 배열로 분기하지 않는가,
  (3) 실패 경로에서 좌표를 만들어 내는 코드가 없는가.
  `scripts/check_privacy.py` 같은 자동 검사는 지금 만들 수 없다 -
  훑을 코드 표면이 아직 없기 때문이고,
  배선이 생기면 이 세 항목을 그때 스캔으로 올린다
- **폴백 서술을 담은 세 문서 갱신** (배선 시점, Tech Lead).
  `아키텍처.md` 178행, `역할_가이드/04-백엔드.md` 36행, `구현_범위.md` 42행이
  모두 대피소 재선정까지만 적고 있다.
  지금은 그것이 현재 규칙 그대로라 고치지 않고, 배선과 같은 PR 에서 함께 고친다
- **이 문서 승인 후 상태 줄 갱신** (Tech Lead)
