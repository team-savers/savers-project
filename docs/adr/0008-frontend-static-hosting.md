# ADR-0008: 프론트엔드는 정적 호스팅으로 분리하고, 단일 VM에는 백엔드·AI 엔진만 올린다

- **상태**: 제안 (Proposed) — PR [#34](https://github.com/team-savers/savers-project/pull/34) 리뷰 합의에 따라 작성, PM·Backend/Infra 승인 대기
- **날짜**: 2026-08-01
- **결정자**: 신호정 (Tech Lead) 제안 / 안은남 (PM), 김도혁 (Backend/Infra) 승인 대기
- **관련 문서**: [ADR-0003](0003-single-vm-seoul.md) (**범위 부분 대체**), [ADR-0004](0004-pwa-over-native.md) (PWA 단일 형태), [ADR-0005](0005-webpush-primary-channel.md) (웹푸시 1차 = HTTPS 강제), [infra/README.md](../../infra/README.md), [후속_과제.md](../공통_가이드/후속_과제.md) 11번
- **대체 관계**: [ADR-0003](0003-single-vm-seoul.md)의 **"docker-compose로 전체 스택을 그 VM 위에 올려 운영한다"** 중 **프론트엔드 부분만** 대체한다. 서울 리전 고정·CPU 전용·관리형 이중화 유보는 **그대로 유효**하다.

## 배경 (Context)

ADR-0003은 "전체 스택을 단일 VM에"로 결정했고, 그때 `apps/frontend`는 스캐폴딩 전이었다.
#32로 프론트가 들어오면서 `apps/frontend/vercel.json`이 함께 커밋됐고,
`infra/docker-compose.yml`에는 frontend 서비스가 없다.
즉 **배포 구조는 코드로 이미 갈라져 있는데 기록만 없는 상태**였고,
PR #34 리뷰에서 이것이 후속 과제가 아니라 ADR 대상이라는 지적이 나왔다(김도혁).

기록이 없다는 것 자체가 문제인 이유는 두 가지다.

- 이 저장소는 공개이고 심사위원이 배포 구조를 문서에서 직접 읽는다.
  ADR-0003과 `vercel.json`이 서로 다른 말을 하면 어느 쪽이 진실인지 판단할 근거가 없다.
- [ADR-0005](0005-webpush-primary-channel.md)가 결과 표에 HTTPS 배포처 확보를
  "ADR-0003 단일 VM" 선행 과제로 걸어 두었다.
  배포처가 정해지지 않으면 실기기 웹푸시 검증이 착수되지 않는다.

## 결정 (Decision)

**프론트엔드 정적 산출물은 Vercel에 배포하고, 백엔드·AI 엔진은 ADR-0003의 단일 VM에 그대로 둔다.**

- **`infra/docker-compose.yml`에 frontend 서비스를 추가하지 않는다.**
  compose는 backend·ai-engine 두 서비스로 유지한다.
- **VM에는 정적 파일 서빙을 두지 않는다.** nginx 컨테이너와 인증서 갱신 운영을 떠안지 않는다.
- **API 호출은 교차 출처가 된다.** 프론트는 `VITE_API_BASE_URL`에 백엔드 절대 URL을 주입받는다
  (기본값은 빈 문자열 = 동일 출처이므로, 분리 배포에서는 반드시 설정해야 한다).
- **백엔드에 TLS 종단과 CORS 허용을 추가하는 것은 이 결정의 필수 후속 작업이다**(아래 "결과" 참고).
- **로컬 개발과 배포는 절차가 다르다.** 로컬은 `docker compose up`(백엔드·AI) + `npm run dev`(프론트),
  배포는 compose(VM) + Vercel 빌드다. 이 차이를 `infra/README.md`에 명기한다.

판단 근거는 넷이다.

1. **정적 산출물이라 VM에서 서빙할 이유가 없다.**
   빌드 결과는 파일 묶음이고, VM에 올리면 서빙·캐시·인증서 갱신 운영만 늘어난다.
2. **웹푸시가 HTTPS를 강제한다**([ADR-0005](0005-webpush-primary-channel.md)).
   단일 VM에서 HTTPS를 세우려면 도메인 + 인증서 + 리버스 프록시가 필요한데,
   정적 호스팅은 도메인 없이도 HTTPS 하위도메인을 즉시 준다.
   2주 스프린트에서 실기기 검증 착수 시점을 앞당기는 차이가 크다.
3. **비용이 늘지 않는다.** 무료 티어 범위이고, ADR-0003의 비용 최소화 방향과 충돌하지 않는다.
4. **ADR-0003이 인정한 SPOF를 일부 완화한다.**
   VM이 죽어도 프론트 자체는 뜨고, 이미 캐시된 서비스워커 화면이 남는다
   (오프라인 예비모드 요구와 정합. 신뢰도: 높은 신뢰 — 캐시가 이미 채워진 기기에 한정된다).

## 결과 (Consequences)

**긍정**

- 문서와 코드가 한 방향을 가리킨다. `vercel.json`의 존재 이유가 기록된다.
- HTTPS·CDN·프리뷰 배포를 인프라 작업 없이 얻는다. 실기기 웹푸시 검증의 선행 조건이 풀린다.
- 인프라 시간을 ADR-0003이 지목한 "직접 구현 필수" 항목에 그대로 남겨 둔다.

**부정 / 완화**

| 리스크 | 완화 | 상태 |
|---|---|---|
| **혼합 콘텐츠 차단.** HTTPS 페이지에서 `http://` 백엔드를 호출하면 브라우저가 막는다. 프론트를 HTTPS에 올린 순간 백엔드 TLS는 선택이 아니라 전제 조건이 된다 | VM 앞에 TLS 종단(리버스 프록시 + 인증서)을 세운다. 담당 Backend/Infra | ⚠️ 미해결 — 프론트·백엔드 실연동 전 필수 |
| **CORS.** 동일 출처가 아니게 되는데 `apps/backend`에는 현재 CORS 미들웨어가 없다 | 배포 출처(프리뷰 도메인 포함)를 허용 목록으로 받는 설정을 백엔드에 추가한다 | ⚠️ 미해결 |
| **기동 절차가 둘.** `docker compose up` 하나로 전체 데모가 서지 않는다 | 두 절차를 `infra/README.md`에 나란히 적는다. 데모 시연 순서도 그 문서를 따른다 | ✅ 이 PR |
| **외부 SaaS 의존이 하나 늘어난다** | 산출물이 정적 파일이라 이전 비용이 낮다. 어느 정적 호스팅으로도 `dist/` 업로드로 대체 가능하고, 최후에는 VM 편입으로 되돌릴 수 있다(아래 재검토 조건) | 완화됨 |
| **프리뷰 URL이 늘어나 FCM·카카오 도메인 허용 목록 관리가 필요하다** | 실기기 검증은 고정 프로덕션 도메인에서만 수행하고, 그 도메인만 등록한다 | 설계 제약으로 이관 |

## 재검토 조건

다음 중 하나면 compose 편입(= ADR-0003 원안)으로 되돌린다.

- 백엔드 TLS 종단을 어차피 세우게 되어, 그 프록시에 정적 파일을 얹는 추가 비용이 사실상 0이 되는 경우.
  이때는 배포처를 하나로 합치는 편이 운영 서술이 단순해진다.
- 외부 SaaS 의존을 제거해야 하는 요구(심사 기준·보안 요건)가 확인된 경우.

## 후속 조치 (문서 동기화)

ADR은 결정 시점의 기록이라 사후 편집하지 않는다는 규약을 따른다
([ADR-0005](0005-webpush-primary-channel.md) 후속 조치 절).
따라서 **ADR-0003에는 대체 표시만 넣고 본문은 고치지 않으며**,
ADR-0005 결과 표의 "HTTPS 배포처 의존 — 진행 중" 행도 편집하지 않는다.
그 행의 후속이 이 ADR이다.
