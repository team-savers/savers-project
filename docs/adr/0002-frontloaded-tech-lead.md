# ADR-0002: Tech Lead의 기여를 초반 집중형으로 구조화한다

- **상태**: 승인 (Accepted)
- **날짜**: 2026-07-25
- **결정자**: 신호정 (Tech Lead), 안은남 (PM)
- **관련 문서**: [개발자_가이드.md](../공통_가이드/개발자_가이드.md) 6절, [역할_가이드/02-테크리드.md](../역할_가이드/02-테크리드.md), [ADR-0001](0001-monorepo.md)

## 배경 (Context)

Tech Lead 역할은 통상 전 기간에 걸쳐 아키텍처·오케스트레이션·가드레일을 상시 소유하는 형태로 정의된다.
초기 담당 정의도 그렇게 되어 있었고, 그 안에는 성격이 전혀 다른 두 종류의 일이 섞여 있었다.

1. **한 번 정하면 오래 쓰는 일** — 모듈 경계, 계약(스키마·인터페이스), 골격, 설계 원칙
2. **반복·튜닝·운영** — 프롬프트 튜닝, 체인 확장, 통합 조율

해커톤 단기 일정에서 이 둘을 한 사람이 계속 함께 들고 있으면 두 가지 문제가 생긴다.

- **직렬화**: 계약이 늦게 확정되면 각 모듈이 서로의 입출력을 기다리며 순차 진행된다.
  4개 모듈이 하나의 파이프라인으로 이어지는 구조(위치매칭 → RAG → 생성 → 발송)에서는 이 비용이 특히 크다.
- **지식 사일로(bus factor 1)**: 계약·골격 지식이 Tech Lead 1인에게만 축적되면,
  그 사람의 가용 시간이 팀 전체 처리량의 상한이 된다.

## 결정 (Decision)

Tech Lead의 업무를 **front-load(초반 확정)** 와 **hand-off(반복·운영 이관)** 기준으로 분리하고,
프로젝트 초반에 집중 투입한다.

### 초반 집중 — Tech Lead 전담

1. **모듈 경계 + 계약 확정** — OpenAPI 스펙, 데이터 스키마, RAG 검색 인터페이스 → `packages/contracts`
2. **Walking Skeleton** — 재난 1건이 `API 수신 → 위치매칭 → RAG → 생성 → 발송`까지 얇게 관통하는 뼈대(더미 데이터 허용)
3. **가드레일 프롬프트 설계 원칙 + 초기 버전** — 원문 인용 강제, 원문 부재 시 폴백 규칙
4. **레포 스캐폴딩 · CI · docker-compose · 평가 하네스 골격**

### 이후 — 리뷰·자문 중심

반복 튜닝과 운영은 각 모듈 소유자에게 이관한다.

| 이관 영역 | 소유자 |
|---|---|
| 가드레일 반복 튜닝·검증 | 김도혁 (QA/Security) — 이미 가드레일 검증 담당 |
| 오케스트레이션 운영·확장 | 김소원 (AI/RAG) — RAG 담당과 인접 |
| 모듈 통합·일정 조율 | 안은남 (PM) — 통합은 본래 PM 소관 |

### 지식 사일로 방지 (필수)

- 초반 골격 작업 시 이관 대상자와 **페어링**하여 맥락을 함께 흡수한다.
- **모든 아키텍처 결정은 `docs/adr/`에 ADR로 기록**한다. 결정의 배경을 나중에 복원할 수 있어야 한다.
- 인터페이스는 **구두 합의 금지**. 반드시 `packages/contracts`에 코드/스펙으로 존재한다(SSOT).

## 결과 (Consequences)

**긍정**

- 계약이 조기에 확정되어 4개 모듈이 병렬로 진행된다.
- Walking Skeleton이 초반에 관통되므로 통합 리스크가 늦게 터지지 않고 초반에 드러난다.
- 계약·골격 지식이 문서(ADR)와 코드(contracts)에 남아 특정 개인에게 고이지 않는다.

**부정 / 완화**

| 리스크 | 완화 |
|---|---|
| 초반 Tech Lead 부하가 과중 | PM이 초반 일정에 버퍼를 확보하고, 같은 구간에 다른 산출물을 겹치지 않게 배치 |
| 이관이 형식적으로만 끝남 | 이관 대상자가 **Tech Lead 없이 1회 이상 직접 수정·배포**해보는 것을 이관 완료 조건으로 둔다 |
| 미성숙한 계약이 초반에 굳어버림 | `packages/contracts`에 버전을 두고, 계약 변경 시 ADR을 추가해 변경 이력을 남긴다 |

## 재검토 조건

Walking Skeleton이 예정 시점까지 관통되지 않으면, PM과 함께 MVP 범위를 재조정한다
(계약·골격이 미완인 상태로 각 모듈 상세 구현에 들어가지 않는다).
